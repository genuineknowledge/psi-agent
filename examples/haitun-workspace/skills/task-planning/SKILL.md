# Task planning（session `todo`）

本 skill 是 **何时建 todo / 如何维护** 的权威约定。Gateway / spa-v2 只**消费**已写入的清单（`N/M`、当前项）；**不**替你决定要不要拆步。先判该不该建表，再动手。

## 一句话

- **用户说目标；Agent 决定要不要拆。** 不必等「帮我列个 todo」。
- **`todo` = 本 Session 的可核对执行清单**（可持久、可被 UI 读），不是对用户的问卷。
- **有分拆价值才建表；没有就直接做** — 禁止为「显得专业」凑清单。
- **一旦写出清单，就必须随进程维护** — 禁止「建一张表 → 复读表格 → 当本轮结束」。

---

## 建表即承诺（刻意为之）

对 `todo` 的**写**（带 `todos=`，无论 `merge`）= 你认领了这份执行账本。之后只有三条合法出路：

| 出路 | 何时 | 要求 |
|------|------|------|
| **做完** | 本轮能推进的步骤 | 边做边 `merge=true` 勾选；相关项 `completed` / 废弃项 `cancelled` 后再给结果摘要 |
| **做到挡住** | 缺信息 / 权限 / 外部依赖 | 当前项保持诚实 status；用 `clarify` 或一句话说明 blocker；**不要**假装任务已完成 |
| **只建计划、暂不执行** | 用户明确只要计划 / 「先列出来别做」 | 条目保持 `pending`（或仅第 1 条 `in_progress` 且立刻停手等确认）；回复必须写明 **「计划已落盘，尚未执行」**；**禁止**用「已调用完成 / 任务完成」收尾 |

**禁止（本次收紧的核心）：**

- 写完清单就贴 Markdown 进度表然后收工，磁盘仍停在 `1/N` 却当回合成功结束
- 用户说「调用一次 todo / 建 3–4 步」时只建表不动手、也不声明「仅计划」——默认仍按 **立刻推进第 1 项** 执行；若用户只要演示建表，用出路三并说清楚
- 把「调用了 todo 工具」当成交付本身

只读 `todo()`（无参）**不**触发本承诺。

---

## 判定门（先过这扇门）

问自己三句（任一为「是」→ **必须** `todo`；全「否」→ **禁止** 建表）：

1. **多步可核对？** 完成过程需要 ≥3 个可独立勾掉的步骤，或用户一次塞了多项子目标？
2. **多产物 / 多文件 / 长工具链？** 要写文档、改多文件、调研+成稿+交付，或预计 ≥3 轮 tool？
3. **中途容易丢线？** 不做清单就容易漏步、重复做、或做完无法自检「还剩什么」？

| 门控结果 | 行为 |
|----------|------|
| **必须建表** | 开工前（或发现变复杂的当轮）`todo(..., merge=false)` 写出计划，立刻推进第 1 项。**产品语义**：`merge=false` 会在 AppData 开一条新的子任务分段（spa-v2「任务历史」），供事后回放 checklist |
| **禁止建表** | 直接执行；不要空喊「我先列个计划」却不写 `todo`，也不要写只有 1 条的装饰性清单 |
| **中途升级** | 开头以为一步能完、做到一半变大 → **当轮**改判为必须，用 `merge=false` 重开一版或 `merge=true` 补步骤。重开会归档上一段清单 |

### 必须建表（示例）

| 信号 | 示例 |
|------|------|
| ≥3 个依赖步骤 | 读材料 → 提纲 → 成稿 → 校验 → `[SEND:]` |
| 一次多项 | 「修 CI、改 README、再开 PR」 |
| 长链路 | 多轮 bash / 多文件 edit / 浏览器调研 + 写报告 |
| 多交付物 | 剧本杀全文 + 角色卡 + Word 打包 |
| 用户强信号 | 「分步做」「别漏」「先计划再执行」（加强信号，不是唯一条件） |

### 禁止建表（示例）

| 情况 | 示例 |
|------|------|
| 一步能完 | 读一个文件、答一个概念、跑一条命令、改一个typo |
| 纯对话 | 翻译、总结、闲聊、澄清概念 |
| 短 skill ≤2 步 | 固定 one-shot 配方足够 |
| 用户只要结果 | 「别啰嗦，直接给答案 / 直接改」 |
| 单次 clarify | 缺信息先问清楚 — 用 `clarify`，不要用 todo 代替提问 |

### 灰色（自行判断，默认偏「不做表」）

- 名义 2 步但每步很重（例如「写完整 Word 剧本」）→ 可拆 **2～4 条**有意义的阶段，不要拆成「写第 1 章 / 第 2 章…」刷条数。
- 已有清晰口头计划且本轮内肯定做完 → 口头执行即可，**可不**落 `todo`。

---

## 与 UI / 进度条的关系（刻意）

- **有 `todo` 文件** → 前端可显示 `N/M` 与当前项；这是清单的副作用，不是建表目的。
- **无 `todo`** → 任务仍可有侧栏/状态；**不要**为了喂进度条而建空表或假步骤。
- Agent **不**负责百分比圆环；只负责清单真伪与 status 及时更新。

## 配方

### A. 开始（必须建表时）

```
判定门 → 必须：
  todo(todos='[
    {"id":"1","content":"…","status":"in_progress"},
    {"id":"2","content":"…","status":"pending"},
    …
  ]', merge=false)
  → 立刻做第 1 项（禁止只建表不动手）
```

**拆法：** 通常 **3–7 条**，按依赖排序；每条是用户能听懂的**可核对产物/阶段**，不是微操作。  
**`content` 必须是字符串**（不要传 list/对象）。  
**不要**默认加「询问用户是否满意」；**不要**默认加「测试/验证」除非用户要求或项目惯例必须。

**禁止自指步骤（刻意收紧）：** 清单项描述**工作本身**，不要把「维护 todo / 回复用户 / 更新进度条 / 勾选清单」写成一步。这类元动作没有独立交付物，模型又常在回复后再忘勾，UI 会永久停在最后一项 `in_progress`。

| 禁止写入 content 的例子 | 应怎么做 |
|-------------------------|----------|
| 「更新 todo 清单状态」 | 做完真实步骤时立刻 `merge=true` 勾选，**不占一行** |
| 「回复用户 / 告知结果」 | 收尾摘要在对话里说，**不占一行** |
| 「同步侧栏进度 / 给用户看 N/M」 | UI 自动读文件，**不占一行** |
| 「收尾 / 结束本轮」 | 真实工作项全 `completed` 后再说话，**不占一行** |

好的最后一项示例：「确认 `segment-test-b.md` 已落盘且内容正确」「把结果 `[SEND:]` 出去」——仍是可核对产物，不是「点勾选」。

**软约束（C，刻意不为硬失败）**：`todo` 写入若命中自指文案，仍 `ok=true` 落盘，但返回 `warnings[]`；应立刻用真实步骤重写该项。前端在回合结束后若仍有 `in_progress` 会 toast 提示（A），**不会**自动改状态（避免谎报完成）。

### B. 推进（与执行同回合交织）

```
完成一步 → merge=true：旧项 completed，下一项 in_progress
发现新步骤 → merge=true：追加 pending
某步失败 → 旧项 cancelled + 追加修订项（merge=true）
```

**同时只有 1 个 `in_progress`。** 完成即标 `completed`，不要攒到最后一次性勾完。  
**每完成一个可核对阶段，先写 `todo` 再继续下一步**——维护是执行的一部分，不是收尾彩蛋。  
**最后一项也是真实工作：** 做完后必须再 `merge=true` 标 `completed`，**再**写结果摘要；禁止「摘要里写已完成、磁盘仍留一条 in_progress」。

### C. 收尾

```
相关项全部 completed（废弃项 cancelled）——此时磁盘上不应再有 in_progress
→ 给用户结果摘要（做了什么、如何验证）
→ 不要复读整张表，除非用户要看
```

若本轮只完成了部分步骤：摘要写清 **已完成 / 进行中 / 未开始**，磁盘 status 必须与之一致；**未全部完成就不得用「本轮任务已完成 / 已完成」口径收尾。**

### D. 只读

```
todo()   # 无参 → 完整列表 + summary
```

---

## 静默与播报

- 建表 / 改 status：**不要**逐步播报「我更新了 todo」。
- 开始：一句目标或直接开干；结束：结果摘要。
- 长任务可在**大阶段之间**给一行进度（刚完成什么、下一步什么）——不替代 Execution Bias。

---

## 不要

- 不要把礼貌收尾、clarify 选项写进 todo
- **不要**把「更新清单 / 回复用户 / 同步 UI」写成 todo 步骤（见上方禁止自指）
- 不要用 todo 代替 `clarify` / 自然语言提问
- 不要为侧栏进度、为「看起来在推进」而建 1 条装饰清单
- 不要「空过一张未维护的表」就视为结束（见「建表即承诺」）
- 不要与 `goal`（跨会话长期目标）或飞书个人 ToDo 看板 skill 混淆：本 tool 只服务**当前 Session 执行步骤**
