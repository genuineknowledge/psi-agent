## 1. 本次任务：把 SOP「核心原则」1、3、4、5 推进为 agent 代码

docx「核心原则」共 6 条（编号 1-6），本回 agent 化的四条为：

| 核心原则编号 | 原文要义 | 本次落地 |
|---|---|---|
| 1 必有产出 | 每次会议产出决定、行动项、负责人和截止时间；拒绝无结论的会 | `msop.core.01` 生效 |

## 2. 与「飞书会议 SOP agent 化方案」的差异盘点

   02 未生效），id 即对应 docx 核心原则编号，审计时可直指“按核心原则 N 判定”。

   均为契约损坏 → 本次运行显式失败，杜绝“把没定稿的条目当生效规则去判”。
4. **引擎 skill 版本化**：`skills/meeting-sop/weekday-alignment/SKILL.md` 由

## 3. 四条规则的判定口径与条款依据（正文在 meeting-sop.yaml）

- `msop.core.01` 必有产出（axis: session）：判定 会尾结论集合是否含 决定/
  行动项/负责人/截止时间；完全缺失 → 不符合，缺个别要素 → 部分符合，含糊到辨不出“谁+何时”
  → 证据不足。依据：核心原则 1。
- `msop.core.03` 会中控制时间（axis: session）：按 议程一 ≤5 分钟、议程二 ≤5 分钟、
  整场 ≤30 分钟 用时间戳核对；**“每人 ≤3 分钟”只适用于议程三成员个人汇报发言——
  主持人/小组负责人/Mentor/领导（一人或多人）承担主持职能（开场/议程推进/逐人点评/
  追问/打断分流/总结）时的发言不受该上限约束，不得以主持人累计/单次发言超 3 分钟判
  不符合**；超时打断/会后单独聊 = 执行控制；时间戳缺失不凭篇幅猜测。依据：核心原则
  3 + 会中·议程（口径 v1.2 澄清）。
- `msop.core.04` 会后纪要与闭环执行（axis: followup）：可观察锚点 = 会尾“更新 TODO”
  安排 + 跨场次开场复查验收；锚点皆无 → 证据不足留待下场复查；生效首场无上次行动项
  不判不符合。依据：核心原则 4 + 会后·必须项 + 议程一。
- `msop.core.05` 杜绝流水账（axis: session）：汇报/总结段是否讲问题、偏差、下一步；
  第一句发言不能是“做了什么”；议程一总结须与 TPMF 方向挂钩。依据：核心原则 5 +
  议程一/议程三。

## 4. 边界与不做（本回）

- `msop.core.02`（核心原则 2 会前准备落实到责任人）：证据在会前——组长逐一查看各人
  TODO List、成员会前自行梳理；单靠会中转写无法独立取证（会上体现只是间接信号），
  待 TODO 数据通道接入后另行 agent 化，故保持 `active: false`。
- 核心原则 6（频次/时长随成熟度逐步降低、周中对齐会可能取消）：属“是否发起/取消会议”
  的机制判断，docx 明确由后续 SOP 另行规定，不作为转写判定条目。
- 议程细则（议程一/二/三的内容、逐人点评点名说具体、纪要指定一人并会后同步）已作为
  判定标准/示例的依据写入 core.03/core.01/core.05 的 criteria，不单列规则。
- 不写正式记录、不计分、不进入绩效；输出仍是候选与观察（引擎既有边界）。
