# TODO 实事求是判定总纲（静态二层）

判断「todo list 写得是不是真的」只有这一套口径。SOP 红线：**TODO list 一定要实事求是，弄虚作假为红线**。

填没填 → [`company-todo-fill-check`]；做完没 → [`todo-completion-standard`]；填得规不规范 → [`todo-writing-standard`]；本文管的是**真不真**。

存在的理由：

- 真实性是文字看不出来的：同一条「已完成」，可能是真交付，也可能把没做的写成做完 —— 「形式主义、ctrl+C/V 应付」正是 CEO 对 TODO 的第一担心。
- 判真伪需要事实，事实在 **TPMF「方案执行与验收」闭环**里：任务系统进度、交付物、验收记录。**跟不进任务进度就判不了真伪** —— 这是本技能要与「方案执行与验收」模块联动的根本原因。
- 判错的三个方向都要防：把「无法跟进」判成「失实」（冤枉人）、把「失实」放成「无从验证」（红线失守）、只拿本人自填对本人自填（双标）。

## When to use

- 「他这周 todo 写得是不是实事求是」「这条是不是吹的 / 虚的 / 假的」「有人弄虚作假吗」「这条声明可信吗」「帮我核对 XX 的填报与实际进度」。
- 静态二层例行检查（周一三五 16:00 定时任务 `todo-check`，由用户在与 agent 对话中用 `schedule_manage` 自行设置）。
- 一次问询涉及多人、要给可比结论时（**最必须**加载的场景）。

## When not to use

- 判**谁没填**（整期空白）→ [`company-todo-fill-check`]（空白可能是已通过的请假免填，先查假）。
- 判**做完没**（完成度）→ [`todo-completion-standard`]（四档：已完成 / 推断已完成／待确认 / 进行中 / 未闭环）。
- 判**活走完整圈没有**（台账闭环五要素、逾期回流）→ [`company-todo-audit`]。那是「闭环判定」，不是真伪判定。
- 判**填得规不规范**（格式 / 三层结构 / 按时按质按量）→ [`todo-writing-standard`]。
- 搬运个人 ToDoList → [`feishu-todo-board-sync`]。
- 绩效评价 / 打分 → 真实性是事实判定，不是绩效评价（见 Boundaries）。

## 流水线：顺序不能乱

```
company-todo-fill-check（① 填没填，含请假豁免）
        ↓
todo-completion-standard（② 做完没，E1-E3 四档）
        ↓
todo-truthfulness-check（③ 真不真：声明-事实对照，本文）
```

- 整期空白 → 先①（可能是请假免填）；填了才谈②③。
- 某条「消失」→ ②判「推断已完成／待确认」；本文不再给它落「失实」。
- 颠倒顺序会把「休假没填」读成「失实」——方向是加重考核，且不会立刻暴露。

相邻口径的分界（同一张表、不同层，互不覆盖）：

- **填得规不规范** → [`todo-writing-standard`]：格式 / 结构 / 按时按质按量，判「这一期填得合不合规」。**不合规 ≠ 失实**：格式差可能是水平问题，不是「写了假的」。
- **活闭环没有** → [`company-todo-audit`]：台账闭环五要素（验收人 / 截止 / 勾选交付 / mentor 打分评语 / wiki 回写），判「活走完整圈没有」。**已闭环 ≠ 属实**：闭环是执行侧状态，本文判的是填报声明与事实一不一致——一条走完五要素的 todo，声明照样可能夸大；反之，失实嫌疑也不等于没闭环。audit 的 E1 取证（`completed_at`）本文复用，但用途不同。

## 声明-事实对照（claim–fact reconciliation）

一条 TODO 声明含四个要素，每个要素都要能找到事实，找不到就是「无法跟进」的候选：

| 声明要素 | 事实源 | 证据级 |
|---|---|---|
| 声称的状态（已完成 / 进行中 / 计划中） | 任务系统里该执行人自己的 `completed_at`、任务状态 | E1 |
| 交付物与给用户的价值 | 交付物文档 / 产物 / 链接、验收记录、mentor 评价 | E2 |
| 截止时间与完成标准 | 任务 deadline、验收记录、后续填报 | E1/E2/E3 |
| 上级验收 | 验收状态机：已申请验收 → 验收中 → 通过 / 驳回 | E2 |

**验收通过才算完成**（SOP 硬要求）：声明「已完成」而验收状态不是「通过」→ 不算属实，最多「存疑／待跟进」；查不到验收状态本身是「无法跟进」违规，先催补验收信息。

E1-E3 定义沿用 [`todo-completion-standard`]：E1 = 任务系统里**该执行人自己**的 `completed_at`（不是 `task.status`，多人任务里 task.status 会骗人，字段在 `assignee_related[]` 里）；E2 = 第三方确认（验收人明确说通过、群 / 文档评论确认、下游接手）；E3 = 本人自填（ToDoList、看板、自评）。

## 四个档位（唯一允许的结论词）

| 档位 | 什么时候用 | 最低证据 |
|---|---|---|
| **属实** | 声明与硬证据一致 | E1 或 E2 |
| **存疑／待跟进** | 有载体但证据不足、声明含糊、验收未通过却写完成 | E3 或部分证据 |
| **失实（涉嫌弄虚作假）** | 声明与事实矛盾：E1 显示未完成却写「已完成」；状态倒退；凭空出现；与上一期填报矛盾 | E1 或可复核的矛盾 |
| **无法跟进** | 缺载体（无任务 / 无交付物线索）、缺验收人、缺 deadline、缺标准 | 任意（**本身记违规**，提示补全） |

**只准用这四个词。** 禁止「基本属实」「应该没问题」「大概是真的」这类自造档位 —— 模糊词是双标的藏身处。

判不准 → `存疑／待跟进` 并写清缺什么，**不要**私自往两头靠。

**失实是红线结论：机器只报「涉嫌失实 + 证据链」，必须人工确认后才定性**。检测到疑似失实，把条目连同证据单列「待人工确认」清单给 mentor / 上级，不在报告里直接断言「弄虚作假」。

「无法跟进」≠「失实」：查不到只是没证据 / 没载体，不是假的；但**查询失败**（读表 403、任务无权限）和**确实无记录**必须分开写。

## 检测维度（D1-D6，逐条对应 SOP 注意事项）

| 维度 | 检查什么 | 判定要点 |
|---|---|---|
| **D1 可跟进性** | 每条 TODO 是否有可核对载体：任务 / 交付物线索 / 验收人 / deadline / 标准 | 缺载体 → `无法跟进`（违规，提示补全）|
| **D2 时间合规** | 所有项（包括 todo、大目标与小目标）不应有**过去的时间点**；deadline 明确 | 出现过去的时间点 → 违规 |
| **D3 进度真实性** | 声明状态 vs E1/E2 最新进度 | 见四档：矛盾 → `失实` 嫌疑 |
| **D4 前后一致性** | 与上一期填报 / wiki 快照对比：状态不回退、不凭空出现、不矛盾 | 可复核矛盾 → `失实` 嫌疑；无证据矛盾 → `存疑／待跟进` |
| **D5 闭环要素** | 以 TPMF 闭环为标准、以用户为中心：说清为**用户**带来什么价值而非做什么事；申请上级验收；TPMF 小组长还须突出和**友商**的比较 | 缺要素 → 闭环不完整，`存疑／待跟进` |
| **D6 对齐与粒度** | 个人 TODO 与**小组** TODO 对齐；粒度过大的小目标可拆成**子目标** | 不对齐 → 违规并提示 |
| **D7 重要全覆盖** | 工作树（思维导图）上 @ 到本人的事项，是否都能在当期填报（大目标 / 小目标 / TODO 任一层）中找到承接 | 先 `feishu_worktree_read` 取每人 @ 清单；有事项无承接 → 违规并提示补列（列出是哪件事、工作树路径）；语义判不准 → `存疑／待跟进`，不许硬配对 |

SOP 原文（引用依据时用）：小目标如果粒度过大，可以拆解成子目标；大目标、小目标和子目标都需要以 TPMF 闭环为标准、以用户为中心、说清为用户带来什么价值，而不是要做什么事，都需要申请上级验收、验收过了才算完成；TPMF 小组长的目标闭环中还要重点突出和友商的比较；个人 TODO 要与小组 TODO 对齐；所有重要的 todo 都需要列出来（不重要的可以不列，也可以写一个百分比估计近两天不重要事情的比例）。

### 数据依赖分档（先行版只跑可先行维度）

实事求是主检测（D1/D3/验收状态机）依赖数据层改造——任务系统接入、过程文档与交付物记录尚未落地，E1/E2 取证链条无从取材。**数据层就绪前，例行检查只跑可先行维度**，其余单列「待数据层」说明，不硬查、不判违规：

| 维度 | 可先行性 | 说明 |
|---|---|---|
| D2 时间合规 | ✅ 可先行 | 看板文本 vs 今天 |
| D4 前后一致性 | ✅ 可先行 | 上一期填报取 wiki 快照（sync 维护） |
| D5 价值表述 / 友商比较 | ✅ 可先行 | 「只写动作不写价值」、小组长缺友商 → 违规提示（验收状态机部分除外） |
| D6 对齐与粒度 | ✅ 可先行 | 小组目标读 wiki 工作树，取不到标 `unavailable` |
| D7 重要全覆盖 | ✅ 可先行 | 工作树 @ 清单经 `feishu_worktree_read`（需 mindnote 授权） |
| D1 可跟进性 / D3 进度真实性 / 验收状态机 | ✗ 待数据层 | E1/E2 取证链条落地后启用；报告单列「待数据层」，不把「查不到」读成「查无此事」 |

判定纪律对先行维度同样生效：四档词表、证据不足一律「存疑/待跟进」、失实必须人工确认、取证对称性。

## 进度跟进：与「方案执行与验收」模块的联动

判定前先拉最新进度，判定中拿进度对声明：

- 对声明「已完成」的条目：**强制取证** E1 → E2 → E3 全链（E1 拿不到再 E2，E2 拿不到再 E3，不许跳）。
- 对声明「进行中」的条目：核对任务系统状态与进度行一致（进度行说 Day4 完成、任务系统没动 → 存疑）。
- 对「待验收」条目：查验收状态；验收记录 / 评价经 `feishu_message_search` / `feishu_thread_read` / mentor 反馈记录取。
- 任务系统经 `feishu_api` 调 task v2（`/open-apis/task/v2/…`，接口表见 [`feishu-task`]）；交付物与看板用 `feishu_doc_read` / `feishu_sheet_read`。
- D4 的「上一期填报」取 LLM wiki 历史快照（`wiki_read`；快照由 [`company-todo-sync`] 每周期维护）——拿最新快照对比本条在上一期怎么写的，别只凭记忆。

读任务 / 交付物失败（无权限、机器人不是成员、缺授权）→ 照实报 `unavailable`，按取证对称性处理（见下），不顺势判。

## 防误判纪律（与完成度总纲同源，不许放宽）

1. **取证对称性（硬规则）**：一次问询涉及多人时，对每个人跑完同一条链；某人某级取不到 → 该级标 `unavailable`，**把同批全体降到同一深度重判**，报告写明原因。宁可整批弱，不拼一强一弱。
2. **先验印象隔离**：本人自评（「我最近有点 delay」）、历史表现、他人评价一律不作证据，只进报告「背景」区并标来源。
3. **查询失败明说**：查不到 ≠ 无记录；读表失败、查假报错必须写「查询失败」，不得顺势判。
4. **缺写 ≠ 失实**：整期空白是 [`company-todo-fill-check`] 的领域；「没填」不是「写了假的」的证据。
5. **消失 ≠ 失实**：到期后从后续填报消失 = 「推断已完成／待确认」（见 [`todo-completion-standard`]），不给消失落「失实」。
6. **不合规 ≠ 失实、已闭环 ≠ 属实**：格式/按时问题归 [`todo-writing-standard`]，闭环状态归 [`company-todo-audit`]，本文只对「声明与事实的出入」负责（见「流水线」的分界段）。
7. 报告逐条必带 **档位 + 证据等级 + 依据出处**；收尾给「要定论还缺什么」清单；失实条目单列待人工确认。

## 报告格式

```
| 条目 | 档位 | 证据等级 | 依据 |
|---|---|---|---|
| 记忆系统（已完成） | 属实 | E1 | 任务 t100062 completed_at=…，验收通过 |
| NL2KE（已完成） | 失实（涉嫌弄虚作假） | E1 | 任务系统无 completed_at，填报却写完成 —— 待人工确认 |
| date 算子层（进行中） | 存疑／待跟进 | E3 | 进度行与任务系统状态不符，缺 E1 记录 |
| 搭建测试平台 | 无法跟进 | E3 | 无任务、无交付物、无验收人，缺 deadline |
```

多人时按人分组，每组开头写这个人**实际达到的取证深度**；收尾列「要定论还缺什么」（哪条需要谁确认、哪条要查哪个任务）。

## 评测记录落盘

每次检查的结构化结果（人、日期、条目、条目类型、命中维度、档位、证据等级、依据、命中规则）写入 workspace 评测数据目录 `.todo-eval/YYYY-MM-DD.json`，并同步到飞书 bitable（`feishu_bitable_create_records`）——为评测数据体系与后续复盘积累素材。落盘失败要明说，不静默丢结论。

## 例行检查任务模板（todo-check 先行版）

仓库不携带 schedule 实体（公司约定）——生产 workspace 用 `schedule_manage` 按下面模板建（周一三五 16:00，`fire=prompt`），正文自包含、不依赖建任务时的对话上下文：

```yaml
name: todo-check
description: 每周一三五 TODO 静态二层例行检查（先行版:只跑可先行维度,待数据层维度单列不硬查）
cron: "0 16 * * 1,3,5"
visibility: silent
fire: prompt
```

正文要点（建任务时写全, 链接/code 用真实值）:

1. 读团队 TODO 看板当期列（wiki 链接先 `feishu_api` get_node 换 obj_token;表结构现场探,不写死）。
2. 静态一层豁免:整期空白先 `feishu_leave_query`（approval_code=99EEC396-536A-4C7A-8B2D-412584E35CE3,只算已通过）;请假免填者整块跳过。
3. 逐人逐条跑**可先行维度**（本文档「数据依赖分档」表）:D2/D4/D5(价值与友商)/D6/D7。
   - D7 先 `feishu_worktree_read`（mindnote_token 用工作树 obj_token,需 mindnote 授权）,拿每人 @ 清单再对照填报;判不准标「存疑」,不许硬配对。
4. 报告:四档词表 + 每条证据;待数据层维度（D1/D3/验收状态机）单列「待数据层」说明,不判违规。
5. 投递:报告推对应 mentor;`feishu_message_send` 显式发送（定时触发回合没有会话可回,不调用就是没发）。
6. 判定结果落盘 `.todo-eval/YYYY-MM-DD.json`（人/条目/维度/档位/证据/规则）,落盘失败明说。
7. 防误判纪律全程生效:查不到 ≠ 失实;查询失败明说;失实只报嫌疑,人工定性。

## Boundaries

- 不编造任务号、验收人、完成时间；查不到就是 `unavailable`，不是「应该有」。
- 「失实」必须人工确认；不因为某人档位难看就放宽，也不因为印象好就升档。
- 真实性是事实判定，不是绩效评价：报告不加评价性措辞，不向无关成员披露。
- 硬证据与自填表冲突时以硬证据为准，把冲突**明写出来**，不静默选一个。
- 判定只回答「真不真」。要不要处理（催办 / 问责 / 改截止）由用户拍板。
