# 技术方案撰写规范与检查闭环(规范即配置)

真知《技术方案撰写 SOP(试行版)》的两层要求:**写什么(结构)**和**怎么写(硬闸门)**。
本文档把 SOP 结构化写死在文档里, 海豚读文档执行 —— 与
[`todo-writing-standard`](../todo-writing-standard/SKILL.md) 同一模式:
**规则是文字, 不是代码**。

参考模板: 仓内/知识库中的 **RFC-0001-ontology-based-memory**(SOP 指定); 结构以该文顺序为准。

## When to use

- 「帮我按技术方案 SOP 检查这篇 / 这篇 RFC 合不合规」—— **检查**, 见 [引擎段](#引擎段通用闭环)。
- 「帮我起草技术方案 / 写一份 RFC 草案」—— **帮写**。
- 用户贴了飞书文档链接或 wiki 节点, 要结构审查、硬闸门审查、缺章清单。
- 检查后发现缺章/违规, 要 **补救** 草案(只补结构与硬缺口, 不替人拍「做不做」).
- 用户已同意「这是中事、要先写方案」—— 通常由
  [`proposal-need-remind`](../proposal-need-remind/SKILL.md) 提醒后转入本文.

## When not to use

- 还在判断「算不算中事 / 要不要写方案」→ 先用
  [`proposal-need-remind`](../proposal-need-remind/SKILL.md)(提醒者一层); 本文管撰写与元素检测.
- 要给出**最终评审结论**(可立项 / 叫停)并当作组织拍板 → 先跑本文检查, 再加载
  [`proposal-review-standard`](../proposal-review-standard/SKILL.md) 给**建议档位**;
  **海豚不得替验收人做最终「做/不做」决定**。
- 判 TODO 填没填、写得规不规范 → [`todo-writing-standard`](../todo-writing-standard/SKILL.md)。
- 判 todo 做完没 → [`todo-completion-standard`](../todo-completion-standard/SKILL.md)。
- 周期看板缺写、请假免填 → [`company-todo-fill-check`](../company-todo-fill-check/SKILL.md)(方案无此轴)。
- 批量巡检公司方案库、写 Bitable 台账、定时 sync/audit → **第一版不做**, 见文末。

## 与 TODO / 小方案的关系

[`todo-writing-standard`](../todo-writing-standard/SKILL.md) 已写伏笔: TODO 将演进为「小方案」,
与方案 SOP **共享 schema 机制**。当前:

| | 本文 `proposal-writing-standard` | `todo-writing-standard` |
|---|---|---|
| 管什么 | **单篇 RFC/技术方案** 怎么写、结构是否合规 | **周期看板** 上 TODO 怎么写 |
| 载体 | 飞书 docx / wiki | 电子表格看板 |
| 节奏 | 对话/提交触发 | cron 提醒与检查 |

两套 skill **并行**, 别缠进同一条周期管线。小方案演进那天: 优先扩展 schema 段, 不新增第三套引擎。

## 五段结构: 哪一段会变, 哪一段不许变

| 段 | 内容 | 变化时 |
|---|---|---|
| [**引擎段**](#引擎段通用闭环) | 采集 → 拆章 → 按规则集检查 → 报告 → (可选)补救 | **不变** |
| [**内容 schema 段**](#内容-schema-段结构定义) | RFC 头 + 11 章顺序与每章要点 | 换章序/换头字段时整段替换 |
| [**规则集段**](#规则集段硬闸门) | 结构 + 动机/诚实/决策/证据闸门 | 增删规则行 |
| [**载体段**](#载体段数据源映射) | doc/wiki 怎么读、Status 在哪 | 换载体时改映射 |
| [**参数段**](#参数段口径值) | 术语、豁免文案、报告模板 | 改值/改文案 |

**段间只通过引用关联。** 引擎段不许出现具体章名列表、具体 Status 枚举的副本 —— 要用时写
「按 schema 段」「按规则集段」「按参数段」。

## 内容 schema 段: 结构定义

### RFC 头部(文档最前)

| 字段 | 要求 |
|---|---|
| **Feature Name** | 小写蛇形命名, 如 `ontology-based-memory` |
| **Start Date** | 方案启动日期 |
| **RFC PR / Issue** | 关联 PR 或 Issue; 无则写 `N/A` |
| **Status** | 见参数段; 常见 `Draft` / `待审核` / `已生效` |

头部让评审者三秒内知道「这是什么、什么时候、什么状态」。

### 正文 11 章(顺序固定, 缺章即结构违规)

顺序与参考 RFC-0001 一致; **读完动机觉得不值得, 评审可在任意后续层叫停**:

| # | 章名 | 要点(校验时对照) |
|---|---|---|
| 1 | **总结** | 一段话讲清做什么; 目标列为**可验证条目**, 禁空泛形容词 |
| 2 | **术语** | 不自明术语先定义; **无特殊术语时可省略本段**(不算缺章) |
| 3 | **动机** | 谁/场景/痛点/验收人; 见规则集「动机闸门」 |
| 4 | **指南(guide)层级介绍** | 整体思路: 特点/模块、各解决什么、如何配合; 可特点列表+对比表; 不堆接口 |
| 5 | **参考(reference)层级介绍** | 实现细节(接口/数据结构/交互); 标题须含「默认收起」; **可整章 N/A** |
| 6 | **缺点** | 代价/风险/未确认假设, 每条具体; 见「诚实闸门」 |
| 7 | **决策依据和备选方案** | 关键选择 + 被考察过的备选; 见「决策闸门」 |
| 8 | **数据集和预实验** | 有效性主张时必填; 见「证据闸门」与参数段豁免 |
| 9 | **前人的艺术** | 同类方案简述 + 本方案差异与取舍 |
| 10 | **未解决问题** | 未决项 + 尽量标触发时机(online/offline) |
| 11 | **未来可能性** | 预留拓展方向(可短) |

**豁免(不算缺章, 须在报告里说明):**

- 第 2 章术语: 全文无自明术语 → 可省略。
- 第 5 章参考层: 无实现细节可写 → 可标 `N/A`(参数段文案)。
- 第 8 章数据集: **方案无「更好/有效/性能」类主张** → 可省略内容, 但**章序仍在**(
  可留短节写「本方案不涉及有效性对比」或参数段的省略说明); **不得静默删除整章标题行**。

## 规则集段: 硬闸门

每条形状:**触发条件 + 判定对象 + 判定逻辑 + 违规文案 + 报告去向**。
增删规则 = 改这张表。**判定对象全部是方案正文(按 schema 段拆章后的文本)**。

| 规则 | 触发条件 | 判定对象 | 判定逻辑 | 违规文案 | 报告去向 |
|---|---|---|---|---|---|
| **结构** | 每次检查 | 全文章序 | RFC 头四字段齐全; 11 章顺序可辨; 仅允许参数段列出的豁免 | 「缺第 N 章 <章名>」/「RFC 头缺 <字段>」 | 作者 + 请求方 |
| **动机闸门** | 每次检查 | 第 3 章 | 一句话能说清谁/场景/痛点; 有明确验收人(或 TODO 待填); 禁「降本」「提效」「智能化」等空话当需求 | 「动机不满足: <具体缺项>」 | 同上 |
| **诚实闸门** | 每次检查 | 第 6 章 | 缺点具体、有代价; 只报喜或泛泛而谈 = 违规 | 「缺点章未诚实列出风险/假设」 | 同上 |
| **决策闸门** | 每次检查 | 第 7 章 | 每个**关键**设计选择至少有一个被认真考察并否掉的备选; 只有默认 = 违规 | 「<选择点> 未见被否掉的备选」 | 同上 |
| **证据闸门** | 文中有有效性/性能主张 | 第 8 章 | 须数据集/基线/指标或明确「待探索」; 量化无来源 → `[待调研]`, 禁编造 | 「声称 <主张> 但缺实验/design 或待探索声明」 | 同上 |
| **写法(软)** | 每次检查 | 总结/动机/全文 | 精炼、可追问、事实可追溯; 数字须能指出来源 | 「写法提示: <项>」(不算硬违规, 单列) | 同上 |

**动机是第一道闸门:** 动机不过, 应在报告醒目位置建议「不必继续深读后续设计」(措辞用参数段),
但检查仍应列出已读到的其他违规, 供作者一次改完。

## 载体段: 数据源映射

当前载体:**飞书云文档 docx** 或 **知识库 wiki 节点**(背后多为 docx)。

| 要素 | 落在哪 | 怎么拿 |
|---|---|---|
| 方案全文 | docx `document_id` 或 wiki `obj_token` | wiki 链接先 `GET /open-apis/wiki/v2/spaces/get_node` 换 `obj_token`; 再 `feishu_doc_read(file_type="docx", token=...)` |
| RFC 头 Status | 文档开头几段 / 头部表格 | 从 read 结果解析, 不另建库 |
| 章节边界 | 正文标题(「总结」「动机」等) | 按 schema 段章名切分; 标题变体(「第 3 章 动机」)归一后匹配 |
| 本地草稿 | 用户 workspace 文件 | `read` / 用户粘贴; 检查逻辑同 doc |

**硬规则:**

1. **读不到文档** → 报告「采集失败」, 不得输出「通过/违规」假装检过。
2. **wiki 节点** → 必须先 get_node, 禁止把 node_token 当 document_id 直读(404)。
3. **写回文档**(帮写/补救) → 经 `feishu_doc_append_content` 或用户确认后的 edit 路径;
   **默认「生成 → 作者确认 → 写入」**, 不 silent 覆盖整篇。
4. 权限: 读他人文档可能需要 `user_key`; 整条链路用同一 `user_key`。

第一版**不**维护 Bitable 方案台账; 需要公司级方案库时再扩展载体段。

## 参数段: 口径值

| 参数 | 当前值 |
|---|---|
| Status 枚举 | `Draft` / `待审核` / `已生效` |
| 参考模板名 | `RFC-0001-ontology-based-memory` |
| 参考层省略文案 | 「参考层级介绍: N/A(无额外实现细节)」 |
| 数据集章省略条件 | 全文无「更好/有效/性能/指标」类有效性主张 |
| 待调研占位 | `[待调研]` |
| 动机不过时的建议语 | 「建议先补齐动机或叫停立项; 后续章节仅作结构参考」 |
| 检查报告投递 | 默认回复当前对话; 可选 `feishu_message_send` 私聊作者/验收人(须用户明确要求) |

术语与违规文案以本文为准; 引擎段不另造词。

**第一版无 cron.** 检查由对话触发; 若要「每周巡检 Draft 方案」后置, 用 `schedule_manage` + `fire=prompt`
引用本文检查流程即可, 不另写 skill。

## 引擎段: 通用闭环

**不含具体章名、Status 字面量、工具 URI。** 一律「按 schema 段」「按规则集段」「按载体段」。

闭环:**采集 → 按 schema 拆章 → 按规则集逐条判 → 出报告 → (可选)补救**。

### 帮写

SOP 约定:**人定方向 → Agent 出草案 → 人改 → 再检查**。

1. **采集** —— 用户口述/要点/旧文档; 可选读 wiki 工作上下文。
2. **搭骨架** —— 按 schema 段生成 RFC 头 + 11 章标题与每章占位说明。
3. **填内容** —— 用户已给的信息写入对应章; **缺验收人/痛点/备选/数据 → 标 TODO 或 `[待调研]`, 不瞎编**。
4. **澄清** —— 动机说不清、无验收人、关键选择无备选时 **先问**, 再写长文。
5. **交付** —— 输出 markdown/飞书可粘贴稿; 用户确认后可 `feishu_doc_create` + `feishu_doc_append_content`。

帮写完成后 **应主动提议** 走一遍检查流程(仍用本文规则集)。

### 检查(主场景)

1. **采集** —— 按载体段读取全文。
2. **拆章** —— 对照 schema 段, 列出: 已识别章节 / 缺章 / 顺序错乱 / 豁免项。
3. **硬闸门** —— 按规则集段逐条判, 每条违规带**章节 + 原文摘录(短) + 规则名**。
4. **汇总** —— 使用下面报告模板; 动机闸门失败时在顶部加参数段建议语。
5. **评审档位(可选)** —— 若用户要「能不能立项」, 加载
   [`proposal-review-standard`](../proposal-review-standard/SKILL.md) 给建议档位;
   **本文只负责合规与缺口, 不负责最终拍板**。

```text
技术方案 SOP 检查报告 — <Feature Name 或文档标题>

RFC 头: <字段摘要> | Status: <值>
参考: <是否对齐 RFC-0001 结构>

结构
  通过: <列表>
  违规: <列表, 每条 章+依据>
  豁免: <术语省略 / 参考层 N/A / 数据集省略 + 理由>

硬闸门
  动机: 通过 | 违规 — <依据>
  诚实(缺点): ...
  决策(备选): ...
  证据(数据): ... | 不适用(无有效性主张)

写法提示(软): <列表, 可为空>

建议下一步(不含拍板):
  - 优先补齐: ...
  - 可选: 加载 proposal-review-standard 出建议档位
```

### 补救

针对检查报告的违规项, **生成补丁草案**, 不自动写入飞书 unless 用户确认:

| 违规类型 | 生成什么 |
|---|---|
| 缺章 | 该章最小可用模板(含章内必填要点) |
| 动机/缺点/备选/数据 | 针对缺口的问题清单 + 示例句(标注「需作者替换为真事实」) |
| 空话动机 | 改写引导问题, 不替用户虚构场景 |

补救后 **再跑一遍检查**, 直到硬闸门全绿或用户停止。

## Boundaries

- **不替评审人拍板** 「做/不做/优先级」—— 只报缺口、依据与(可选)review 档位。
- **不编造** 数字、实验结果、用户场景、验收人姓名。
- 读文档失败 → 明说失败, 不猜结构。
- 章标题识别歧义 → 标「待人工确认」, 不硬判缺章。
- 本文不管 TODO 周期填报、任务闭环、请假 —— 见各对应 skill。

## 别做的事(第一版)

- 不做 Bitable 方案库、sync/audit、评价卡回写(对标 `company-todo-review` 后置).
- 不做「周一三五方案缺写检测」—— 方案不是周期格填报。
- 不在引擎段复制 11 章全名列表 —— 只在 schema 段维护一份。
