# 方案撰写 · 检查 · 落盘跟进(一体 · SOP v2)

**权威规范:** 《真知方案撰写执行跟进与验收 SOP》**版本 2.0(试行)** —— 四时期主线 + 产品/技术两型.
**刻意为之(2026-09):** 旧 skill 曾按《技术方案撰写 SOP(试行版)》的 **RFC 头 + 11 章**写(那是另一份关联文档 / RFC-0001 模板).
**现一律按 v2.0 四期骨架审查与撰写.** 11 章 RFC 形态不再作为硬结构闸门;
若用户稿仍是旧 11 章, 检查报告标明「结构不符 v2」, 帮写时改写成四期.

关联: v2 文末「关联 SOP: 真知技术方案撰写 SOP」仅作格式/历史参考, **不替代** v2 骨架.

通过后建定时、同方案顶替 / 异方案分组 —— 仍写死在本文(原独立 followup 已废弃).

## When to use

- 「按方案 SOP 检查 / 合不合规 / 帮我起草或改技术方案」.
- 用户丢来方案链接或粘贴稿.
- 检查后补救、落盘后同步跟进定时.

## When not to use

- 「算不算中事 / 要不要写方案」→ [`proposal-need-remind`](../proposal-need-remind/SKILL.md).
- 组织拍板档位 → 先本文检查通过, 再可选
  [`proposal-review-standard`](../proposal-review-standard/SKILL.md).
- 材料已到对照 → `proposal-acceptance-poc` / `proposal-acceptance-doc`.
- 公司看板 TODO → `todo-writing-standard` / `company-todo-*`.

**壳:** [`proposal-followup`](../proposal-followup/SKILL.md) /
[`proposal-intake`](../proposal-intake/SKILL.md) → 跳转本文.

## 内容 schema 段: v2.0 四期

### 文首元信息(建议表, 硬要求见规则集)

| 字段 | 要求 |
|---|---|
| **方案标题** | 非空 |
| **方案类型** | `技术方案` / `产品方案` / `联合`(v2 §2) |
| **状态** | 如 预备期 / 待评审 / 实验中 / 实施中 / 跟进验收中(与时期一致即可) |
| **`proposal_id`** | 稳定短 id(小写蛇形或文档 token); **同方案改版勿改**; 兼定时组键. 缺则从标题 slug / `document_id` 派生并写回文首 |
| 创建人 / 审核人(验收人) | 审核人或验收人**非空**(可写角色名); 纯「待指定」→ 动机闸失败 |
| 关联 SOP | 应写明对齐 **执行跟进与验收 SOP v2.0** |

### 四个时期(顺序固定; 缺期=结构违规)

v2: **四个时期是唯一主线.** 撰写服务于决策; 实验决定是否投入; 实施形成结果; 跟进验收决定是否关闭.
**不是**「整篇一次写完再一起做」——但**成稿检查**时: 预备+实验+实施 三节须可辨;
跟进验收期允许占位(「待执行后填写」), 不算缺期.

#### 1. 预备期(上级决策后进入下一阶段)

须可识别下列块(标题可略异, 语义须在):

| 块 | 要点 |
|---|---|
| **结论先行** | 建议做什么 / 为什么做 / **需要什么决策** |
| **目标用户与问题依据** | 为谁、什么问题; **事实 / 推断 / 待验证** 分开写 |
| **价值主张** | 客户价值 / 为什么是我们 / 怎么最快验证 / 投入产出 |
| **实施路径** | 现状 → 目标的主要路径(可表) |
| **核心决策点** | 可选方案、取舍、推荐理由 |

#### 2. 实验期(POC 证不出优势则回退预备期)

| 块 | 要点 |
|---|---|
| **差异化量化对比与测评** | 与现状/旧版/竞品/替代 **同口径**; 数字可追溯; 无依据标「待验证」 |
| **正反反驳** | 评审者最可能质疑的 ≥3 点 + 回应; **最坏情况** |
| **备选方案** | 每个关键设计选择有被认真考察并**否掉**的备选; **必须含**「直接采用业界最强」与「不做」选项(可表内一行) |

技术方案: Critical 能力指标 + 护栏意识可在此预埋, 实施期验收标准再钉死.

#### 3. 实施期

| 块 | 要点 |
|---|---|
| **里程碑倒排** | 时期/节点/产出/负责人/**可解析 DDL**; Test Task 可作里程碑 |
| **验收标准** | 测试范围(主/异常/回退); 指标、基线、目标值、观察周期; 技术案须 Critical + 护栏 |
| **风险与回退** | 停止线、降级、稳定版本 |
| **非目标与展望** | 边界; 展望不计入本期范围 |

#### 4. 跟进验收期

| 块 | 要点 |
|---|---|
| 实际结果表 | 指标目标 vs 实际(未执行可「待填写」) |
| 验收结论 | 验收人/日期/通过与否/遗留(未执行可占位) |

### 实施计划行(执行性闸门 · 海豚落地定时用)

取自**实施期 · 里程碑倒排**(及可并入的 Test Task 节点). **每行**:

| 列 | 要求 |
|---|---|
| 步骤/节点名 | 非空 |
| **DDL** | `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM`(本机墙钟). **禁止**仅有 `T+N 周` 而无锚定日起点; 若只用相对周, 须同时给出 **锚点日**(如 Start=`2026-09-08`)并写明换算后的绝对日 |
| 负责人 | 姓名/角色/open_id; 不可全表空到无法投递 |
| **验收门** | 恰好: `无需` / `文档` / `POC`(落表枚举; **业务名**见下「三类里程碑」) |
| 标准指针 | 指向验收标准节或可观察指标; `无需` 可 `—` |

#### 三类里程碑(业务名 → 验收门 · 识别方式 · 定时/验收分流)

**刻意为之:** 对人说话用「无交付物 / 交付物 / 场景闭环」; 落进里程碑表与定时 YAML 仍写枚举
`无需` / `文档` / `POC`(与 acceptance skill、既有闸门兼容). **先认业务类, 再落枚举.**

| 业务类 | 落表枚举 | 一句话 | 到点催办侧重 | 材料到达后 |
|--------|----------|--------|--------------|------------|
| **无交付物** | `无需` | 过程/仪式/对齐节点, **没有**可交的独立产物 | 只问进度, 可勾自报 | **不**索要材料; **不**进 acceptance-* |
| **交付物** | `文档` | 要交**可读产物**(说明/设计/验收文/链接清单等) | 催交文档或链接 + 标准指针 | [`proposal-acceptance-doc`](../proposal-acceptance-doc/SKILL.md) |
| **场景闭环** | `POC` | 要跑通**可复现场景**: 场景 + 样本 + 及格线 + 评测报告 | 催交评测/检测报告 | [`proposal-acceptance-poc`](../proposal-acceptance-poc/SKILL.md) |

**识别顺序(建定时 / 检查执行性时逐行跑; 勿跳步默认成场景闭环):**

```text
0. 行上已写合法验收门枚举 → 直接采用; 业务名与枚举冲突时以枚举为准并在报告里点名不一致
1. 否则读「产出 / 节点名 / 验收标准指针」原文, 按下面信号表打分
2. 命中唯一类 → 写入验收门枚举 + 在 detail 里带业务类标签(如「交付物·文档」)
3. 两类信号同时强 → 问作者一句二选一; 未答清前该行执行性=失败, 不建该步定时
4. 三类都弱 → 默认「无交付物」(无需), 并在检查报告标「弱信号·已按无交付物」; 作者可改
```

| 信号(任一即可偏该类; 多条更稳) | → 业务类 |
|-------------------------------|----------|
| 节点是获批/对齐/站会试跑/口头同步/权限开通/排期冻结; 产出写「—」「无」「过程」「仪式」; 标准指针空或「—」; **明确不要求**交文/交测 | **无交付物** |
| 产出是 doc/docx/wiki/设计说明/验收文档/接口契约/迁移手册/报告正文; 标准是「文档须含…章节/字段」; 动词是「提交/上传/写完/评审文档」且**没有**样本集+及格线 | **交付物** |
| 明示 POC/评测/试跑/A-B; 有**业务场景**+**样本/数据集**+**及格线/阈值**; 「可复跑」「同口径对比」「检测报告」; 实验期指标落到该节点验收 | **场景闭环** |

**反例(防误判):**

| 原文像… | 易错成 | 正解 |
|---------|--------|------|
| 「写完 POC 方案文档」 | 场景闭环 | **交付物**(交的是文, 不是跑批结果) |
| 「上线后观察一周」无无**样本/及格线 | 场景闭环 | **无交付物**或补标准后再定; 缺门槛勿冒充 POC |
| 「交接口文档 + 用 3 条用例跑通并出报告」 | 只交付物 | **场景闭环**(有可复跑门槛); 文档可作附证 |
| 「方案获批」 | 交付物 | **无交付物** |

帮写/补救时: 每行验收门旁可用括号标业务类, 如 `文档(交付物)` / `POC(场景闭环)` / `无需(无交付物)`.

至少 **1** 行完整; 行内 DDL 为 `[待填]` → **执行性失败**(可建稿, 不可同步定时).

## 规则集段: 硬闸门

映射 v2 纪律: 结论先行; 数字可追溯; 事实/推断/决策分开; 主文只留影响决策的信息.

| 规则 | 判定 | 违规文案 |
|---|---|---|
| **结构** | 预备+实验+实施 三期可辨且块齐全; 跟进验收可占位; 文首有 `proposal_id`(或可派生并写出) | 「缺\<时期/块\>…」 |
| **动机** | 结论先行 + 目标用户/问题清楚; **审核人或验收人非「待指定」空壳** | 「动机/决策入口不满足…」 |
| **诚实** | 风险与回退具体; 或正反反驳含最坏情况与代价 | 「未诚实写风险/最坏情况」 |
| **决策** | 核心决策点有推荐; 备选含被否项且含「业界最强/不做」 | 「缺被否备选或缺不做/业界最强选项」 |
| **证据** | 有有效性/能力主张时实验期有同口径对比或明确「待验证」基线计划; 纯工程落点且声明无竞品对比可 N/A 但须留实验期节说明 | 「声称…但缺对比/待验证未标」 |
| **执行性** | 里程碑表 ≥1 行; 每行真实 DDL(可从锚点换算写出)+ 验收门枚举 | 「缺里程碑/绝对 DDL/验收门」 |
| **写法(软)** | 事实推断分开; 精炼 | 不单独硬失败 |

**通过:** 全部硬闸门绿. 动机不过仍列全部分违规.

**旧 11 章稿:** 结构闸失败; 帮写输出 v2 四期, 不把 11 章当合规.

## 载体段

| 要素 | 怎么拿 |
|---|---|
| 全文 | `feishu_doc_read` / wiki / 粘贴 / `read` |

| 里程碑 | 「里程碑倒排」表; 无则扫含节点/负责人/时间的表 |

| 参数 | 值 |

## 引擎段: 通用闭环

### A. 检查

```text
1. 采集全文; 识别是否旧 11 章壳
2. 按 v2 切四期 + 找里程碑表
3. 硬闸门逐条(含执行性 / 绝对 DDL)
4. 出报告(模板见下)
5. 全绿 → C.同步定时
   有硬违规 → 不建定时; 列须改项(旧壳则建议改写为四期)
```

```text
方案 SOP v2 检查报告 — <标题> (proposal_id=<id>)

结构(四期): 通过|违规(细节)
硬闸门: 动机/诚实/决策/证据/执行性 …
里程碑摘要: <行数; 各类计数 无交付物/交付物/场景闭环; DDL 形态; 或「缺失」>
定时: 已同步 prop-<id>-* | 未同步(原因)

建议下一步(非组织拍板): …
```

### B. 帮写 / 补救 / 落盘

1. **按 v2 四期**搭文首 + 预备/实验/实施/跟进验收占位.
2. 里程碑须问清或与作者确认 **绝对 DDL**(或锚点日+相对周并换算写进表); 不瞎编日期.
3. 每关键决策点备选含「业界最强」「不做」.
4. 用户确认后落盘 → 再跑 A; 通过则 C; 不通过则撤掉该 `proposal_id` 旧定时组.

### C. 同步定时

**前置:** 硬闸门全绿; ≥1 条真 DDL; 有 `receive_id`.

**工具死写死(刻意为之, 勿与触发器串台):**

| 要用 | 禁止 |
|------|------|
| **`schedule_manage`** | **`trigger_manage`**(那是事件触发器, 不是到点催办) |
| 参数名 **`schedule_name`** | **`trigger_name`**(传了等于没传名 → create 全失败) |
| `once_at` + `fire="tool"` + **`tool="feishu_proposal_nudge"`** | `fire=prompt` / 只挂 `feishu_message_send`(到点无卡) / 手写 `TASK.md` |

**为何是 nudge 不是裸 message_send:** `fire=tool` 一次只能调一个工具. 方案催办约定是**同拍**私聊正文 + 可勾进度卡; `feishu_proposal_nudge` 内部先发文字再 `feishu_todo_card_send`. 把卡只做成「同步定时当下发一次」不够——`-pre`/`-ddl` 到点也必须再带卡.

```text
1. 解析 proposal_id
2. list → delete 全部 prop-<proposal_id>-* (同方案顶替)
3. 逐行跑「三类里程碑」识别 → 落枚举; 组装 items_json:
   title=节点;
   detail=DDL + 业务类 + 验收门枚举 + 标准指针
   (例: "DDL 2026-09-20 · 交付物·文档 · 见§验收标准3.2")
4. 按里程碑每行 create -ddl / -pre(DDL-12h), tool 一律 feishu_proposal_nudge;
   text/subtitle 按业务类选文案(见下「跟进文案」)
5. (可选) 同步当下再调一次 feishu_proposal_nudge, 让用户立刻有卡可勾
6. 回执表: 定时名 | 业务类 | 验收门 | 到点=文字+卡
```

**create 样板(字段名逐字照抄; 改的是值不是键):**

```text
schedule_manage(
  action="create",
  schedule_name="prop-<proposal_id>-s1-ddl",
  once_at="YYYY-MM-DD HH:MM",
  fire="tool",
  tool="feishu_proposal_nudge",
  tool_args='{"receive_id":"<chat_id或open_id>","text":"【方案跟进】…","items_json":"[{\\"title\\":\\"M1 …\\",\\"detail\\":\\"DDL … · POC\\",\\"done\\":false},{\\"title\\":\\"M2 …\\",\\"detail\\":\\"…\\",\\"done\\":false}]","title":"方案进度 · <proposal_id>","subtitle":"到点催办 · s1-ddl","receive_id_type":"chat_id"}',
  visibility="silent",
  description="方案跟进 · <节点> · DDL · 文字+进度卡"
)
```

`-pre` 同构: 只改 `schedule_name` / `once_at` / `text`(【方案提醒】) / `subtitle`. **每条定时的 `items_json` 都应带齐全部里程碑行**(到点刷新整卡), 不要只塞当前一步.

| 情况 | 行为 |
|------|------|
| 同 `proposal_id` 改版通过/落盘通过 | **顶替**该前缀组后重建 |
| 不同 `proposal_id` | **新组**; 不动其它 id |
| id 被改名 | 视为新方案; 旧组不自动删(须用户声明承接) |

纪律: 只用 `schedule_manage`+`schedule_name`; `once_at`+`fire=tool`+`feishu_proposal_nudge` 一次写齐; 催办禁止「组织验收通过」; 勾选≠验收.

### 跟进文案(按业务类)

| 定时 | 业务类 | 正文要点(可润色, 语义勿改) |
|------|--------|---------------------------|
| **-pre** | 任一 | 「【方案提醒】距「\<节点\>」(类别) DDL 约半天…」 |
| **-ddl** | **无交付物** | 「【方案跟进】「\<节点\>」到点. 这步无独立交付物, 进度怎样?」(可勾自报; **勿**索要链接) |
| **-ddl** | **交付物** | 「【方案跟进】「\<节点\>」到点. 请交交付物(文档/链接)并对照: \<标准指针\>. 勾选≠验收.」 |
| **-ddl** | **场景闭环** | 「【方案跟进】「\<节点\>」到点. 请交场景闭环材料(评测/检测报告; 须含场景·样本·结果对及格线). 勾选≠验收.」 |

材料贴来后: 交付物 → `proposal-acceptance-doc`; 场景闭环 → `proposal-acceptance-poc`;
无交付物 → 只更新进度语义, **不要**假装跑验收对照.

## Boundaries

- 不替组织拍板做/不做; 不编造 DDL/验收人/实验数字.
- 不把旧 11 章 RFC 当 v2 合规.
- 不管公司看板缺写周期.
- `proposal-followup` / `intake` 仅为壳.
