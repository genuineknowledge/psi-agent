# 动态三层 · 同级对比与带人 scale-up

CEO 纪要原话：动态三层是「同级 peer 之间的对比（不关键，天然可拉对比表）」与「体现好后，带人的 scale up（评价组织贡献外溢）」。本文是这两件事的**唯一口径**，且尊重「不为主」：产出是**客观对比表与 scale-up 信号**，不是排名、不是奖惩、不是绩效结论。

## 与其它层的分界（同一批数据、不同视图，互不替代）

| 层 / skill | 回答什么 | 视图 |
|---|---|---|
| `todo-completion-standard` | 一条做完没 | 单条（纵向时间） |
| `todo-truthfulness-check` | 声明真不真 | 单条 |
| `company-todo-audit` | 台账闭环没有 | 单条/团队统计 |
| `todo-alignment-check`（`#798` 合入后） | 目标/价值对不对齐 | 单人 |
| `todo-growth-profile`（`#800` 合入后） | 一个人长期成长 | **人 vs 自己** |
| **本文 `todo-peer-contrast`** | 同级之间客观对比、带人 scale-up | **横向 / 外溢** |

**本文只做后两个视图。** 人 vs 自己（个人成长）是 `todo-growth-profile` 的地盘，本文不重复判成长；本文只把同一基准下的人**并排**呈现，并把「开始带人」作为外溢信号单列。

## 数据源（全部复用既有权威存储，不臆造新表）

1. **mentor Bitable 台账历史周期表**（`feishu_mentor_ledger_cycle_table` 每周期一张表：状态 / mentor打分 / mentor评语 / 外部成果 / 友商对比 / 任务GUID）；
2. **`.todo-eval/` 连续性序列**（`company-todo-audit` 已按 (cycle, person, item) 落盘）；
3. **LLM wiki 快照链**（`company-todo-sync` 维护）。

指标口径与 `todo-growth-profile`（#800）同源：闭环率 / 按时率（请假顺延豁免）/ 回流次数 / 持续逾期段 / mentor打分趋势 / 承担层级迁移（todo → 小目标 → 大目标 → 带人）/ 外部成果累计——**每条必须可回溯**到台账行 / 快照页 / `.todo-eval` 记录。

## 同级基准怎么定（`peer.same_level_by`）

当前口径：**同一 `mentor` 名下成员 = 同级基准**（config `peer.same_level_by: mentor`）。原因：台账天然按 mentor 隔离且每周期同表，可比性最强、口径最干净。

- `#798`（`sync_org_tree` 组织树）合入后可升级为「组织树同层」——**届时改 config 的 `same_level_by` 值即可**，本文判定流程零改动（规则是文字不是代码）。
- **严禁跨组/跨层对比**：不同 mentor、不同层级不自动比（除非用户明确点名要拉，且报告注明基准差异）。

## 视图 A：同级对比表（客观、可拉）

把同一 `mentor` 名下成员按 config `peer.indicators` 拉成一张表：

- **只列同口径、同周期（或同窗口）的可比数字**；跨了周期窗口就分开列，不许混。
- 表头/正文**明示**：`事实呈现，不是绩效评价，不排名奖惩`；报告按人分行、按指标分列，不设「总排名」行。
- 表后**可以**给「需要该 mentor 关注的差异点」（谁的回流次数连续走高、谁的持续逾期段变长），但**不下谁好谁坏的结论**——差异点是否处理由 mentor 结合上下文拍板。
- 样本 < config `peer.min_cycles`（当前 3）的人，**该人整列标「样本不足」**，不进对比、不硬解读。

示例形态：

```text
同级对比表 · 周期 8.19–9.02 · mentor 孙逊团队（事实呈现，不排名奖惩）
| 成员 | 闭环率 | 按时率 | 回流次数 | 持续逾期段 | mentor打分趋势 | 层级迁移 | 外部成果 |
| 张三 | 8/10 | 9/10 | 1 | 0 | 3→4 | 升(todo→小目标) | 3 |
| 李四 | 3/10 | 5/10 | 4 | 2 | 3→2 | 平 | 0 |
需 mentor 关注的差异点：李四回流次数与持续逾期段连续走高，建议 mentor 关注（不下好坏结论）。
样本不足：王五（覆盖 1 个周期，低于 min_cycles）。
```

## 视图 B：带人 scale-up 观察（组织贡献外溢）

「体现好后，带人的 scale up」的信号，从台账与评测记录里取**客观轨迹**：

1. **名下开始有人**：某人的台账角色从「只有自己是负责人」变为「台账里出现 `mentor = 该人` 的行」（数据源：台账周期表按 `mentor` 字段反查，或用 wiki 快照的组织关系）。
2. **名下规模与质量**：名下行数（N 人 × 周期）、名下成员的闭环率 / 打分趋势（同视图 A 口径，只做描述）。
3. **本人负载形态**：本人是否仍在大量自担高负载 todo，还是开始下放（可用承担层级迁移里的「带人」档做提示信号）。

**输出 = 客观信号**，例：`张三自 9 月起名下有 2 人，下属闭环率 8/10，本人外部成果持续 3 项——呈现如下，是否 scale up 由 mentor/上级结合上下文拍板。` **不下「带得好/带得不好」的结论**；带人只是外溢信号，不是个人排名依据。

## 纪律（与其它判定 skill 同源，不许放宽）

- **不排名、不奖惩、不绩效评价**：对比表是事实呈现；本人自评 / 他人评价 / 历史印象不作证据，只进「背景」并标来源。
- **严禁跨组/跨层自动对比**；用户点名跨组拉表时必须注明基准差异。
- 取证对称：一次拉表涉及多人时用同一数据源、同一周期窗口、同一深度；某级 unavailable → 把同批全体降到同一深度，报告写明。
- **样本不足明说**（`peer.min_cycles`），不硬解读。
- 查不到 = unavailable 明说，不顺势补数。
- 结果只给该 mentor / 被问者，不向无关成员披露别人的数字。

## 判定口径

指标清单、同级基准、样本下限读 `config/todo-sop.yaml` 的 `peer` 段（用户可编辑，换公司只改该文件）。本文保留两视图的纪律与「从哪取数」，与其它判定 skill 同一模式。

## Boundaries

- 本文不是个人成长档案（`todo-growth-profile`），不做人 vs 自己；只做横向对比 + 带人外溢。
- 本文不判单条完成度 / 真伪 / 闭环 / 对齐——那些各归其位（见分界表）。
- 对比 / scale-up 观察是事实呈现；要不要处理由 mentor / 上级 / 用户拍板。
- 不向无关成员披露他人数字；跨基准对比只在用户明确点名时进行并注明差异。
