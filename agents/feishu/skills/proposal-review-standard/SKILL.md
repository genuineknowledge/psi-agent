# 技术方案评审结论口径

判断「这篇 RFC/技术方案建议怎么处置」只有这一套**建议档位**。
结构/硬闸门怎么判, 见 [`proposal-writing-standard`](../proposal-writing-standard/SKILL.md);
**本文只管评审结论怎么表述**。

**刻意为之:** 真知 SOP 写「人定方向、Agent 打磨、人拍板」。海豚可以给依据、缺口与建议档位,
**不得**替验收人/决策会做最终「做/不做」决定, 不得在报告里写「建议立项, 请领导批准」类 binding 语句。

## When to use

- 结构检查之后, 用户问「能立项吗」「评审结论是什么」「动机过不过」。
- 验收人要看 **一页纸建议**: 通过深评 / 打回补齐 / 动机叫停 / 吃不准交人。
- 同一篇方案要给 **可比、可审计** 的结论表述(禁止「基本可行」).

## When not to use

- 还在问「算不算中事 / 要不要写方案」→ [`proposal-need-remind`](../proposal-need-remind/SKILL.md)(提醒者一层); 本文是已有方案后的评审档位。
- 只问「缺哪章、动机写得规不规范」→ 只用 [`proposal-writing-standard`](../proposal-writing-standard/SKILL.md), 不必强行给档位。
- TODO 完成度、看板填报 → [`todo-completion-standard`](../todo-completion-standard/SKILL.md) /
  [`todo-writing-standard`](../todo-writing-standard/SKILL.md)。
- 假勤/报销分级 → [`admin-finance-governance`]。

## 加载顺序

```text
用户要评审结论
    ↓
若无现成检查报告 → 先按 proposal-writing-standard 跑检查(采集→拆章→硬闸门)
    ↓
本文: 根据检查结果 + 全文阅读, 给出唯一建议档位 + 依据表
    ↓
明确写: 最终拍板由 <验收人/评审会> 决定
```

## 四个档位(唯一允许的建议结论词)

| 档位 | 什么时候用 | 最低条件 |
|---|---|---|
| **可进入深评** | 动机闸门通过; 结构无硬违规; 缺点/备选/证据无 blocking 违规 | 检查报告硬闸门全绿, 或仅 soft 写法提示 |
| **需补齐后重提** | 值得继续, 但有可修复硬违规(缺章、缺点空、无备选、数据诚实问题等) | 动机闸门**通过**; 列出必须补齐项 |
| **叫停·动机不过** | 动机闸门失败: 说不清谁/场景/痛点, 或空话需求 | 不必等其它章修完再叫停 |
| **待人工深评** | 模型对技术深度/风险吃不准, 或文档过长/权限不足导致检查不完整 | 报告须写清「缺什么信息才给得了档位」 |

**只准用这四个词。** 禁止「基本可行」「建议立项」「大概率过」「应该能批」—— 模糊词是越权拍板的藏身处。

判不准技术细节 → 用 **待人工深评**, 不要私自升到「可进入深评」.

### 与 Status 字段的关系

| 建议档位 | 可建议作者改的 Status(须经作者/验收人确认) |
|---|---|
| 可进入深评 | 保持 `Draft` 或改为 `待审核`(若用户要求写回) |
| 需补齐后重提 | 保持 `Draft`, 列出补齐清单 |
| 叫停·动机不过 | 保持 `Draft`; **不建议** 改为 `待审核` |
| 待人工深评 | 不改 Status; 说明待谁深评 |

海豚 **默认不自动改** 飞书文档 Status; 用户明确要求且确认后才 `feishu_doc_update_block` 等写回。

## 档位判定规则(硬)

1. **动机不过 → 档位必须是「叫停·动机不过」**, 不得因后面 guide 层写得好而升级。
2. **动机过 + 任一硬闸门违规(非 soft)** → 「需补齐后重提」, 除非检查不完整 → 「待人工深评」。
3. **动机过 + 硬闸门全绿** → 「可进入深评」; soft 写法提示写入报告但不降级。
4. **检查采集失败 / 只读到片段** → 「待人工深评」, 不得给「可进入深评」.

## 报告模板

每条依据必须:**章节(或 RFC 头) + 规则名(来自 proposal-writing-standard 规则集) + 摘录或事实**。

```text
技术方案评审建议 — <Feature Name>

建议档位: <四档之一>

依据摘要:
| 项 | 结论 | 章节 | 规则 | 依据 |
|---|---|---|---|---|
| 动机 | 通过/失败 | 动机 | 动机闸门 | <一句话> |
| 结构 | ... | 总结/… | 结构 | ... |
| 缺点 | ... | 缺点 | 诚实闸门 | ... |
| 备选 | ... | 决策依据… | 决策闸门 | ... |
| 证据 | .../N/A | 数据集… | 证据闸门 | ... |

必须补齐(若档位为「需补齐后重提」):
1. ...
2. ...

写法提示(软, 不单独降级): ...

说明: 以上为 Agent 建议档位, 最终是否立项/深评/叫停由 <验收人> 与评审流程决定。
```

## 与 proposal-writing-standard 的分工

| | proposal-writing-standard | 本文 |
|---|---|---|
| 产出 | 结构清单、违规项、补救草案 | **单一建议档位** + 依据表 |
| 能否说「立项」 | 否(只列缺口) | 仅四档之一, 且带免责声明 |
| 硬闸门定义 | 规则集段 | 引用, 不复制 |

## Boundaries

- 不替验收人做最终决策; 报告末尾必须有免责声明(见模板).
- 不因作者职级/口头承诺给档位开绿灯 —— 只看文档与检查结果.
- 多人评审对称: 同一篇文档多次问询, 档位与依据须一致(除非文档已更新, 须注明版本/时间).
- 第一版无评价卡、无 Bitable 回写; 需要时后置对标 `company-todo-review`.
