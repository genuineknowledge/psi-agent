# TODO 填报情况判定(空白 ≠ 没填)

回答「谁没填 todo」「我的填报是否合规」这类问题时,**表格里的空白格子不是结论,是一个待查的问号**。
同一个空白有三种完全不同的成因,处置也不同:

| 空白的成因 | 归类 | 怎么说 |
|---|---|---|
| 该人该日**没有**已通过的请假 | **缺写** | 照常计入缺写,该说就说 |
| 该日落在**已通过**的请假区间内 | **请假免填** | 不计入缺写,也不计入连续性中断 |
| 日期/人名对不上,或表结构没读明白 | **待人工确认** | 明确说「没判定」,不要归到前两类 |

**为什么必须先查请假**:漏判的方向是「加重考核」——把休假的人说成连续缺写,当着一屋子人给出
确定语气的结论,而且错误不会立刻暴露(被说的人得自己回来申诉)。查一次请假的成本远低于此。

## 一条硬顺序:查假在下结论之前

```
读表(拿到空白格子的 人 × 日期 清单)
        ↓
feishu_leave_query(approval_code=<请假模板 code>, date_from=<最早空白日>, date_to=<最晚空白日>)
        ↓
逐个空白格子比对 on_leave[].hit_dates
        ↓
才可以说「缺写」
```

**顺序颠倒即出错**:先写好「连续三期缺写」的结论再去查假,查到了也往往只是在结论后面补一句,
而「连续性不满足」这个判断本身已经错了。

本租户的假勤模板 code(已探明,`approval_code` 是**模板**编号不是实例编号):

| 用途 | approval_code |
|---|---|
| 请假 Leave | `99EEC396-536A-4C7A-8B2D-412584E35CE3` |
| 补卡 | `09D3F0F3-2A0B-4E05-B40D-9D5565D2A27B` |

拿不到或换了租户:`feishu_api` 打 `GET /open-apis/approval/v4/tasks/query`(带 `topic=3`),
看返回里的 `definition_code` / `process_code`。

## 只算已通过,查不到就算没请假

`feishu_leave_query` 只把**已通过**的申请算作请假,这是刻意的,别自己放宽:

- **审批中**的不算 —— 人还得上班,这期的 todo 该填;等批下来,下一期自然看得到。
  返回里的 `skipped_not_approved` 会把这些列出来,**要在汇报里提一句**,否则一堆待审申请看起来
  就像没人请过假。
- **没走审批流程**的请假(口头请假、HR 后台直接改的)这里查不到 → **按未填写处理**,由本人当场
  申诉。这比「必须有人记得把请假补填进某张表」少一个失败点。
- 不要用**打卡记录反推**请假。缺卡同时对应出差 / 外勤 / 忘打卡 / 请假,反推会把前三种误判成请假、
  静默顺延截止日 —— 方向是放宽考核,比漏判更难发现。
- `needs_fix` 里的申请**必须报出来**,不能悄悄丢掉:丢掉等于把「确实请了假」变成「没请假」。

## 只查几个人时:必须看 `unmatched_filter`

`names_json` 姓名和申请人 id 都收(工具内部把申请人 id 解析成姓名,两种写法任一命中即算;
申请人 id 是 `user_id`,本租户形如 `dg429f6d`,不是 `ou_` 开头的 open_id),
但**空结果有两种病因,分不开就会误判**:

- 名单里没对上任何请假记录的写法进 `unmatched_filter`;
- 通讯录本身查不着(应用没有通讯录权限、范围没覆盖)进 `name_lookup_error`。

只看 `on_leave` 是空的就说「这几个人都没请假」是错的 —— 这跟「名单写法没匹配上」长得一模一样,
而这个缺陷真出过一次:名单传中文名时全被过滤掉,三个已批长假的人被当众判成缺写。
`unmatched_filter` 非空且 `name_lookup_error` 有值时,**按查询失败处理**,不要判缺写。

更省事的做法:**别传 `names_json`**,查整个窗口的全部请假再自己比对 —— 那样根本没有名单
匹配这一环。名单只在人特别多、想减小返回时才用。

## 日期怎么对齐

表头日期和请假返回的日期格式往往不一样,这是最容易错的一步:

- 表头常是 `7.24` / `8.19` 这种**点分、无年份**的写法;`feishu_leave_query` 返回的
  `hit_dates` 是 ISO(`2026-08-19`)。比对前先把表头日期补上年份归一成 ISO。
- 无年份的表头**默认按当年**解释。跨年场景(12 月的表里出现 `1.5`)不要自己猜,归到
  **待人工确认**。
- 区间是**闭区间**,两个端点都算请假。
- 一个人可能有多段请假,`on_leave[].leaves` 是列表,要全看,别只取第一段。

## 汇报格式

先给结论,再给依据。三类各自列清,**不要把请假免填的日期混进缺写里凑数**:

```
缺写:8.21(无已通过请假记录)
请假免填:8.19、8.24(请假 2026-08-19 ~ 2026-08-19、2026-08-24 ~ 2026-08-25,已通过)
待人工确认:无
连续性:未构成连续缺写(8.19/8.24 为请假,8.21 为单期缺写)
```

要点:

- 说「连续 N 期缺写」之前,**先把请假免填的期次剔掉再数连续**。请假把连续性打断了就不能说连续。
- 结论里带上**依据**(哪个请假实例、什么区间),对方才能核。只说「已核对请假」等于没说。
- 全员汇报时,`full_period_applicants`(整个窗口都在假上的人)单独列一组,不要和缺写的人并列。
- 查询失败(读表 403、查假报错)要**明说查询失败**,不要因为「查不到请假记录」就顺势判缺写 ——
  查不到和查询失败是两件事。

## 填了之后问「做完没」:换口径

本技能只判**填没填**。用户接着问「他这些活做完了没」「完成情况怎么样」「这条闭环了没」时,
**换用 [`todo-completion-standard`]**,按那份总纲的四档
(`已完成` / `推断已完成／待确认` / `进行中` / `未闭环`)和 E1-E3 取证链判。

两者的分界就是**同一个空白格子的两种读法**,别混:

- **整期空白**(那一期压根没填)→ 本技能:先查请假,分 缺写 / 请假免填 / 待人工确认。
- **表填了、但某一条不在里面**→ 那边:判 `推断已完成／待确认`(消失既不算已完成也不算未闭环)。

顺序是**先本技能再那边** —— 没确认这一期填了没有,就去数某条「消失」,会把休假者的整期空白
读成「所有条目都没闭环」。**填报缺失不是完成度证据**,别拿本技能的「缺写」去给条目判未闭环。

## 问「写得规范吗」:换口径

本技能只判**填没填**,不判**填得对不对**。用户问「格式规范吗」「三层结构对不对」「有没有 deadline」
「谁不合规」,或者要**帮成员把零散任务写成规范 todo list 填进表**时,换用
[`todo-writing-standard`]。那份技能持有内容格式规范(层级/必含要素/粒度)与执行纪律
(按时/按质/按量、mentor check)。

两者的关系:那份技能的**按时**规则直接引用本技能 —— 判「未填 = 违规」之前必须先走本技能的
查假硬顺序,三类产出直接对应过去(**缺写 = 违规,请假免填 = 不违规,待人工确认 = 不判违规**)。
所以顺序是**先本技能、再那边的其余规则**。

## 权限

看板表要么该 app 是协作者,要么走 `feishu_auth_start()` 让本人授权后带 `user_key=<sender_open_id>`。
`feishu_leave_query` 同样收 `user_key`,tenant 优先、被拒才回落用户身份。整条链路用**同一个**
`user_key`。

## 别做的事

- 别看到空白就说这人没填 —— 本技能存在的全部理由。
- 别把表头日期和请假日期不做归一就直接字符串比。
- 别用打卡反推请假。
- 别把 `skipped_not_approved` / `needs_fix` / `unmatched_filter` 咽掉不报。
- 别在读表失败时给出填报结论。
