# TODO 完成度判定总纲

判断「某人的活做完了没」只有这一套口径。假勤/报销分级看
[`admin-finance-governance`]，本文管的是**完成度**。

存在的理由：同一次问询里给不同人套不同尺子，是最难被发现的错误 —— 每个人的判定各自都
说得通，合起来却是双标，而受害者是被严判的那个人。**已实际发生过**：同一批人里，一人凭
「填报里任务消失」被判「已完成」，另一人同样的消失被判「没闭环」，只因为前者顺手查了任务
系统、后者只看了自填表。

## When to use

- 「某人的 todo 完成情况怎么样」「这周谁做完了」「他这条闭环了没」「看看 XX 的进展」。
- 读一篇个人 ToDoList / 周志 / 团队看板后要给出完成情况结论。
- 一次问询涉及多个人、要给可比结论时（**最必须**加载的场景）。

## When not to use

- 派活、建任务、交办 → [`work-assignment-delegation`]、[`feishu-task`]。
- 把个人 ToDoList 搬进团队看板 → [`feishu-todo-board-sync`]（那个 skill 只搬运，不判完成度）。
- 判**谁没填**（表里的空白格子算不算缺写）→ [`company-todo-fill-check`]。那是「填没填」，
  本文是「填了的做完没」，见下面的分界。
- 判**写得规不规范**（三层结构、必含要素、deadline、条数上限），或帮成员把零散任务组织成规范
  todo list → [`todo-writing-standard`]。那是「怎么写、写没写、写得对不对」，与完成度无关：
  一条写得完全合规的 TODO 可以毫无进展，一条写得潦草的也可能早已闭环，**别拿格式合规当完成度
  证据**，反向亦然。
- 判请假是否合规、报销能不能放行 → [`admin-finance-governance`]。
- 评估某人能力成长阶段 → [`project-deep-learning`]。完成度是事实判定，不是绩效评价。

## 四个档位（唯一允许的结论词）

| 档位 | 什么时候用 | 最低证据 |
|---|---|---|
| **已完成** | 有硬证据 | E1 或 E2 |
| **推断已完成／待确认** | 只有弱信号：到期后从后续填报里消失，或后续出现明确承接它的下游工作 | E3 |
| **进行中** | 未到期，或填报里仍在推进（有进度行、有阶段结论） | 任意 |
| **未闭环** | 已到期，且既无硬证据也无消失/承接类弱信号；或填报里的词法本身表示未启动（写的是「计划」「准备」「打算」） | 任意 |

**只准用这四个词。** 禁止「基本完成」「应该做完了」「大概闭环了」「疑似完成」这类自造档位 ——
模糊词是双标的藏身处，一旦允许，同一个证据强度就能被说成两种结论。

判不准 → 用 `推断已完成／待确认` 并写清缺什么，**不要**私自往两头靠。

### 核心裁决：消失算什么

**到期后从后续填报里消失 = `推断已完成／待确认`，对所有人一律如此。**

- 不能升成 `已完成`：消失可能是做完了，也可能是悄悄放弃了、忘了填、挪进别的条目里。
- 不能降成 `未闭环`：消失是真实信号，多数人做完就不再写进下一期。
- 要升到 `已完成` 只有一条路：补 E1 或 E2 硬证据。

同一次问询里，A 的消失和 B 的消失**必须**得到同一个档位。这条被违反过一次，写在这里就是
为了不再违反。

### 消失 vs 没填：先分清是哪一种空白

「消失」和「没填」看到的是**同一个空白格子**，但成因不同，判错方向相反：

- 那一期他**根本没填表**（整格空白、整期缺席）→ 这不是完成度问题，先走
  [`company-todo-fill-check`]：空白可能是**已通过的请假免填**，照它的硬顺序查完假再说。
  没填 ≠ 没做完，更不能因此给条目判 `未闭环`。
- 那一期他**填了表，但这一条不在里面**（其余条目照常写）→ 才是本文说的「消失」，
  判 `推断已完成／待确认`。

**顺序**：先确认这一期表填了没有；填了才谈某条的消失。颠倒过来就会把休假的人的整期空白
读成「所有条目都没闭环」，那是最重的误判 —— 方向是加重考核，且不会立刻暴露。

## E1-E3 取证链

从强到弱，**每个人都从 E1 开始往下走**：

| 级 | 是什么 | 怎么取 |
|---|---|---|
| **E1** | 任务系统里该执行人自己的 `completed_at` | 读任务详情，看 `assignee_related[]` 里**那个人**的 `completed_at`。详见 [`feishu-task`]。**`task.status` 不是**（那是整个任务的状态，多人任务里会骗人） |
| **E2** | 第三方确认：验收人明确说通过、群里/文档评论里有人确认完成、下游明确接手 | `feishu_message_search` / `feishu_thread_read` 查群消息与话题；`feishu_doc_read` 读文档与评论 |
| **E3** | 本人自填：ToDoList 文档、周志、看板单元格、自评 | `feishu_doc_read` 读个人 ToDoList；`feishu_sheet_read` 读看板 |

E1 拿不到常见原因：这条活压根没进任务系统、机器人不是任务成员、缺该用户授权。
`POST /open-apis/task/v2/tasks/search` 只吃 user token，且只能搜到**那个授权用户本来看得见**
的任务 —— 拿 A 的授权填 B 的 id 搜不出东西，这不是越权通道（见 [`feishu-task`]）。

## 取证对称性（硬规则）

一次问询涉及多人时：

1. **对每个人跑完同一条链** E1→E2→E3。不许对一个人查到任务系统就收工、对另一个人只看自填表。
2. 某人某级取不到 → 该级标 `unavailable`，**并把同批全体降到同一深度重新判**，报告里写明
   为什么降（「张三无任务系统记录，故全体按 E3 口径判定」）。
3. 只有全体都在同一深度上，结论才可比。

降档的代价是结论更弱（更多 `推断已完成／待确认`），这是**对的** —— 宁可整批弱，不要一强一弱
拼出个假的对比。

## 先验印象隔离

以下一律**不作为完成度证据**：

- 本人自评（「我这周 delay 比较多」）
- 历史表现、上期的逾期记录
- 他人对这个人的评价

它们只能进报告的「背景」区且必须标来源。判定只看**本期证据**。带着「这人平时爱拖」的印象去
看他的表，就会把中性信号读成负面 —— 这是本次事故里牛志宇那一侧的实际成因。

## 报告格式

逐条一行，三个字段缺一不可 —— 档位、证据等级、依据出处：

```text
| 条目 | 档位 | 证据等级 | 依据 |
|---|---|---|---|
| 记忆系统 | 已完成 | E1 | 任务 t100062 验收通过 |
| 8.19 POC ×4 | 推断已完成／待确认 | E3 | 8.21/8.24 填报中消失；未查到任务记录 |
| 词法语法 | 未闭环 | E3 | 8.21 填报写「计划」，未启动 |
| date 算子层 | 进行中 | E3 | 8.26 仍有进度行，未到期 |
```

多人时按人分组，每组开头写这个人**实际达到的取证深度**。

收尾必须给「要定论还缺什么」清单（哪条需要谁确认、哪条要查哪个任务），不留模糊结论。
把每一条 `推断已完成／待确认` 都列进去 —— 那正是需要人补一句话就能定论的部分。

## Boundaries

- 不编造任务号、验收人、完成时间。查不到就是 `unavailable`，不是「应该有」。
- 不因为某人档位难看就私自放宽，也不因为印象好就升档。档位只由证据决定。
- 完成度是事实判定，**不是绩效评价**。不要在报告里加评价性措辞，不向无关成员披露某个人的
  完成情况。
- 硬证据和自填表冲突时以硬证据为准，并把冲突**明写出来**（不要静默选一个）。
- 判定只回答「做完没」。要不要催办、要不要改截止时间，是另一件事，得用户拍板。
