# 方案需求提醒(决策分级 · 提醒者一层)

公司制度把事情分成 **大事 / 中事 / 小事**, 并规定不同决策动作.
**中事** 的制度动作是: **拟定方案(须含多种方案与分析) → 直属上级共同决策**.

本文只做 **提醒者一层**: 对话里疑似中事(或吃不准)时, **提醒**对方先走方案小闭环,
并可接到 [`proposal-writing-standard`](../proposal-writing-standard/SKILL.md)
(权威 **执行跟进与验收 SOP v2.0** 四期: 预备/实验/实施/跟进验收) 帮写/检查.

**刻意为之 · 只要提醒、不要二层:** SOP 的 agent 化当前 **不要求全流水线监督**
(不扫「谁该写未写」、不半强制卡住、不因未交方案拒绝对话).
产品交付面就是 **特化常见必写方案场景 + 可跳过提醒**; **不做、也不规划** 监督者二层.
后人勿把「未实现二层」当成待办缺口来补.

**刻意为之:** 一层宁可略多提醒, 也不要在证据不足时假装「小事可自决」而漏提醒;
但提醒必须可跳过, 用户说「先不写 / 这是小事」后本回合不再纠缠.

**加载硬闸门(与 system Skills 段同口径):** 命中改计划 / 跨角色协作 / 要额外资源 /
「能不能自己定」/ **不能兼得取舍** / **模块联动** / **要他人配合** / **动 SOP** /
**调度人力** / **阶段做完但下一层不知怎么做(勿直接开工)** 等信号时,
**必须先读本文再答**, 禁止只给排期/推进 checklist 或直接催开工而跳过分级提醒.
系统提示里的 decision-grade gate 覆盖「none clearly apply → read none」.

## When to use

- 用户在商量「能不能自己定」「要不要找人一起定」「要不要写方案」.
- 对话里出现: 改原计划、找人协作、要额外资源、TODO/项目有可控风险、跨人决策.
- **特化 · 必写方案**(命中即至少按中事提醒, 见下节): 产品/技术上的**不能兼得取舍**; 技术**模块联动**; 改动需**他人人力配合**; **新建或改已有 SOP**; **调度人力**的管理决策; **一阶段做完、下一阶段不知怎么做**时仍要往下干.
- 用户只问「怎么推进 / 怎么排」但内容已含上列信号 —— **仍必须加载本文**(识别力核心; 勿等用户点名方案).
- 派活/交办时事项看起来超过「本人职责内可自决」([`work-assignment-delegation`](../work-assignment-delegation/SKILL.md) 可并行; 需要方案时用本文提醒 + 方案 skill).
- 用户贴了意图但还没文档, 不确定要不要上方案.

## When not to use

- 用户已经在写/改方案, 或丢来方案要检查/改成成品 → 只用
  [`proposal-writing-standard`](../proposal-writing-standard/SKILL.md)
  (按 v2.0 四期; 通过即同步跟进定时; 不通过只改稿; 旧 11 章壳判结构违规并改写).
- 用户要评审档位 → [`proposal-review-standard`](../proposal-review-standard/SKILL.md)
  (口径同 v2.0; 可进入深评亦同步定时).
- POC/交付文档材料到达 → [`proposal-acceptance-poc`](../proposal-acceptance-poc/SKILL.md) /
  [`proposal-acceptance-doc`](../proposal-acceptance-doc/SKILL.md).
- 假勤/报销等行政财务分级 → [`admin-finance-governance`](../admin-finance-governance/SKILL.md)(另一套阈值, 勿混用本文的大中小).
- 要 **强制**「不写方案不许继续」→ **本文禁止**; 本产品面只要提醒, 不做二层监督.

## 分级口径(制度原文要点 · 判定表)

准确识别事之大小是成员必修课; 海豚用同一套词, 不另造「重要/一般」.

### 小事 → 个人决策(不提醒写方案)

同时更贴近下列特征时倾向小事(有一条「中事信号」则升档, 见下):

- 仅涉及 **本人职责范围内** 的工作
- **不影响** TODO 事项进度
- **不涉及** 与他人协作
- **不涉及** 给公司带来损失等风险

**决策规范:** 个人决策即可.

### 中事 → 提醒拟定方案(本 skill 主目标)

出现任一信号即 **至少按中事提醒**(可标「疑似中事」):

- 涉及 TODO 事项的 **可控风险**
- **改变** 原有计划
- **寻求** 与他人合作
- 需要 **额外资源** 等
- 以及下一节 **特化 · 必写方案** 中的任一硬信号(命中后勿降成小事)

**决策规范:** 拟定方案, 方案中要有 **多种方案及其分析**; 由 **直属上级共同决策**.

### 特化 · 必写方案(决策 SOP 在方案 SOP 的体现)

制度大中小是通用轴; 下列是 **产品 / 技术 / 管理** 上「一旦出现就必然需要方案」的特化硬信号.
命中任一条 → **至少按中事**输出方案入口提醒(可标「特化·必写方案」), **禁止**用「本人职责内小事」挡掉.
提醒话术仍走一层: 可跳过, 不半强制卡住.

#### 产品(与技术共用的取舍原则)

| 硬信号 | 判定要点 | 提醒时点明 |
|--------|----------|------------|
| **体验/能力不能兼得的取舍** | 设计功能时存在不同用户体验(或产品能力)的取舍, 选 A 就削弱/放弃 B; **不能两头都要满** | 产品取舍须多方案+分析, 再与上级共同决策 |
| 同上原则落在技术 | 技术路径上出现 **互斥决策点**(性能 vs 复杂度、兼容 vs 重构、自研 vs 采购等), 一旦不能兼得 | 技术取舍同样须方案, 勿口头拍板 |

**刻意为之:** 「有取舍」不等于「有两个备选按钮」——关键是 **选了就不可兼得**. 若只是顺手优化、无牺牲另一侧, 不单靠本条升档.

#### 技术(额外)

| 硬信号 | 判定要点 | 提醒时点明 |
|--------|----------|------------|
| **模块联动** | 改动要与其他模块/系统/服务对接、联调、改契约或共享状态 | 跨模块联动须方案对齐边界与回滚 |
| **需他人配合** | 落地依赖其他同学/组的人力(联调、评审、代改、值班接手等), 不是自己改完就上 | 要别人配合 → 中事协作信号, 先方案再排人 |

与通用表「寻求与他人合作 / 额外资源」同向; 本表把 **模块边界** 与 **对人依赖** 说死, 避免只谈排期漏提醒.

#### 管理

| 硬信号 | 判定要点 | 提醒时点明 |
|--------|----------|------------|
| **SOP 化 / 改 SOP** | 要把一件事写成或升格为 SOP, **或** 修改已经 SOP 化的流程/口径/检查项 | 动 SOP 必方案, 勿私自改制度文本就当生效 |
| **调度人力的管理决策** | 排班、借调、加人盯一项、跨人重新分工、停某人当前活去救火等 **调度人** 的决定 | 调度人力须方案(谁、何时、代价、对原 TODO 的影响) |

#### 研发节奏(阶段边界)

| 硬信号 | 判定要点 | 提醒时点明 |
|--------|----------|------------|
| **阶段做完、下一层不知怎么做** | 当前阶段(里程碑/迭代切片/模块一期)已告一段落或快完成, 下一阶段路径不清、选项未比选, 却要 **直接开工 / 先写代码再想** | **先写方案再开下一阶段**; 提醒「不要直接开工」——可先对齐多方案与验收门, 再动手 |

典型话术信号: 「这一期做完了接下来呢」「下一层不知道怎么做」「先把架子搭起来再说」「边做边看下一阶段」.
**刻意为之:** 本条拦的是 **阶段跃迁时的盲目开工**, 不是拦阶段内已对齐的日常实现; 用户已有书面方案/已共同决策的下一阶段, 不单靠「还在写代码」触发.

### 大事 → 提醒会议民主讨论(不是「只写方案就够」)

出现任一信号即按大事提醒:

- 涉及 TODO 事项的 **不可控风险**
- 可能给公司带来 **重大损失**
- 对项目与公司有更好的建议等(重大方向/组织级议题)

**决策规范:** 相关会议 **民主讨论、集体决策**, 由 **第一责任人拍板**.
大事提醒里可提「必要时仍可准备书面材料」, 但 **主路径是会议集体决策**, 不要把大事降级成「写个方案私了」.

### 共同纪律

凡经组织决策的, 必须坚决贯彻、落实到底 —— 提醒里可带一句, 不展开说教.

## 引擎: 提醒闭环(一层)

```text
本回合用户意图 / 事项描述
    ↓
按上表粗分: 小事 | 疑似或确定中事 | 大事 | 吃不准
    ↓
小事 → 不打断主任务; 不提方案(除非用户主动问)
中事 / 吃不准 → 输出「方案入口提醒」+ 依据信号; 询问是否现在帮写/检查
大事 → 输出「会议集体决策提醒」+ 依据信号; 不假装中事方案可替代
    ↓
用户同意写方案 / 已扔来草案 → 加载 proposal-writing-standard
  (检查通过或落盘通过稿 → 同步 prop-<id>-* 定时)
用户跳过 → 尊重; 本回合不再半强制追问
```

### 提醒话术要求

1. **先给档位词**(只用 `小事` / `中事` / `大事` / `暂无法判定`), 再给 **1–3 条命中的制度信号**(摘自用户原话或上下文, 短).
2. 中事提醒必须点明制度要求: **多种方案 + 分析**、**直属上级共同决策**.
   若命中特化硬信号, 用一短语点名哪一类(取舍 / 模块联动 / 他人配合 / 动 SOP / 调度人力 / **阶段边界勿直接开工**), 勿只说「比较重要」.
3. 明确这是 **建议**, 例如: 「按制度这更像中事, **建议**先写方案再决策; 你也可以说明为何按小事自决.」
   阶段边界类可加: 「**建议先写下一阶段方案, 不要直接开工.**」
4. **一次提醒即可**; 用户已拒绝或已声明自决后, 同话题不反复刷屏.
5. 用户愿意写时: 主动提出按 **执行跟进与验收 SOP v2.0**(四期骨架)帮起草或检查飞书文档,
   再进 `proposal-writing-standard`(勿再按旧 RFC+11 章模板起草).
6. **禁止** 二层语气: 「必须先交方案才能继续」「不写方案我拒绝对话」「已为你创建强制待办」等.
   也禁止另一端: 明知阶段边界不清却只回「那就先开干」而不给方案入口提醒.

### 吃不准时

- 输出 `暂无法判定`, 列出缺哪类信息(是否改计划 / 是否协作 / 是否要资源 / 风险是否可控 /
  是否有不能兼得取舍 / 是否模块联动 / 是否动 SOP / 是否在调度人力 /
  是否阶段做完但下一层路径未定).
- **默认按「疑似中事」给一条轻提醒**(一层策略: 漏提醒比多提醒更糟), 并问一句澄清.
- 不要为了显得果断而硬判小事; 特化硬信号一旦坐实, 立刻升到「特化·必写方案」话术.

### 与派活的衔接

若同时命中交办([`work-assignment-delegation`](../work-assignment-delegation/SKILL.md)):

- 交办记录照常走;
- 另加一句中事/大事提醒;
- 需要方案时协助接收者形成可评审草案 → 转 `proposal-writing-standard`, 不在本文展开四期正文.

## Boundaries

- **无方案表、无定时扫描** —— 只在对话/交办当下提醒; SOP agent 化只要提醒面, 不要全流水线.
- **不做二层**(刻意为之): 不维护「谁该写未写」名单, 不半强制卡住, 不把未写方案当拒绝对话理由.
- 不与 `admin-finance-governance` 的金额/假别阈值混用.
- 不替上级做中事共同决策, 不替第一责任人拍大事板.
- 提醒不是 v2.0 四期结构检查; 检查交给 `proposal-writing-standard`.
- 阶段边界不清时提醒「先方案、勿直接开工」; 用户仍坚持先干则尊重(一层可跳过), 但本回合须先给过提醒.

## 别做的事(一层硬边界)

- 不因「疑似中事」拒绝回答或拒绝执行用户明确要求的下一步(除非另有安全/权限硬规则).
- 不把「提醒过了」写成「用户已同意写方案」或「方案已通过」.
- 不在本 skill 内复制四期骨架全文 —— 需要时引用 `proposal-writing-standard`.
