# HaiTun 反馈收集（确认后再写）

把「随口吐槽 / 报 bug / 夸一句」在**用户明确同意落盘之后**写成多维表一行。  
本 skill **只做一层**：识别 →（必要时澄清）→ **问是否落盘** → 用户答应 → 写入 → 短确认。  
**不做**状态流转后私聊提出人（二层另文）。

配置：`config/haitun_feedback.yaml`（`app_token` / `table_id` / 列名）。可用环境变量
`HAITUN_FEEDBACK_APP_TOKEN`、`HAITUN_FEEDBACK_TABLE_ID` 覆盖。

## When to use

满足**任一**即 LOAD（先对话确认，**不要**一上来就写表）：

- 显式口令：`海豚 bug：…` / `报个 bug` / `记一条意见` / `记个爽点` / `写进反馈表`
- 内容像在评 **HaiTun / 海豚一号 / 飞书机器人 / 桌面端安装包** 的缺陷、体验或亮点（含截图 + 吐槽）
- 用户回答「要落盘 / 帮我记一下 / 好的写吧」且本会话刚讨论过反馈内容

## When not to use

- **派活 / 交办**（「让张三修这个」）→ `work-assignment-delegation`
- 纯产品**使用教学**、查文档、写方案，没有「这是问题 / 这是意见 / 这个爽」味道
- 外部客户不可能填公司内表时：本表只收**内部试用者 / 驻场对接人**；对外仍走代录
- **二层回执**（状态变了通知原提出人）→ 未接线前不要用本 skill 冒充已闭环

## 对话节奏（刻意为之：先确认，再落盘）

**禁止**在用户未明确同意「落盘 / 记一下 / 写进表」之前调用写入工具。

### A. 拿不准是不是反馈

一句澄清即可，不要连环追问：

> 您是在反馈 **bug / 意见 / 爽点** 吗？需要我帮您落盘到反馈表吗？

用户说「不是 / 不用」→ 正常继续对话，**不写表**。  
用户说「是 / 要」但未指类型 → 再问一句更像哪一类，或标「待分类」后走 B。

### B. 能认出类型（或用户已点名）

先口头对齐，**仍不写表**：

> 貌似您在谈 **{bug | 意见 | 爽点}**（若还能判断端：B 端飞书 / C 端桌面可顺带一句）。需要我帮您落盘吗？

用户肯定（「好的」「落盘」「记一下」「帮我写」）→ 才进入「写入」。  
用户否定 → **不写**，可顺手答一下对方的问题本身。

### C. 用户本轮就带了落盘口令

例如「帮我记进反馈表：……」「报个 bug：……」→ 视为已同意落盘，可跳过再问一遍「要不要写」，但仍要在回复里点明判定的类型，再写入。

同会话连续多条、同一缺陷 → **合并成一行**（描述里用换行列点），勿刷屏多行。

## 工具

| 步骤 | 工具 |
|------|------|
| 读配置 | `read` → `config/haitun_feedback.yaml`（相对 **agent** 包根） |
| 写一行 | `feishu_bitable_create_records`（**仅在用户同意落盘之后**） |
| 附件（可选） | `feishu_drive_upload`（parent 指向 bitable）再把 `file_token` 写入附件列；失败则把「有图未上传」写进描述，**不要因此放弃整行** |
| 提出者 | `<feishu_context>` 的 `sender_open_id` / `sender_name`；桌面无飞书上下文时用用户自称或「未知」 |

`user_key` 取 `sender_open_id`；`identity` 用配置默认（通常 `bot`）。

## Instructions

### 0. 配置闸门

1. 用户**已同意落盘**时再 `read` 配置；`app_token` / `table_id` 皆空且无环境变量 → **不要空写**。回复：「反馈表尚未配置 app_token/table_id，请先在 `config/haitun_feedback.yaml` 填好多维表坐标。」可先整理待写入草稿给用户看。
2. 列名以配置 `fields.*` 为准，须与表头**逐字一致**。

### 1. 分类（端 × 类型）

写入**一张表**的两列（配置里的 `surface` / `kind`）。

**端（B / C / 待分类）**

| 信号 | 取值 |
|------|------|
| 飞书机器人、群聊机器人、ToB 网页应用、`feishu` 会话 | B |
| 桌面安装包、本机控制台、spa、ToC | C |
| 说不清 | 待分类（描述里可写「端未确认」；**不要**为分类卡住落盘） |

**类型（bug / 意见 / 爽点 / 待分类）**

| 信号 | 取值 |
|------|------|
| 坏了、报错、不符合预期、复现步骤、崩溃 | bug |
| 希望改成…、建议、不好用但非明确缺陷 | 意见 |
| 好用、爽、省事、想安利 | 爽点 |
| 用户也说不清 | 待分类（描述首行可标 `[待分类]`） |

### 2. 用户同意后：组字段 → 写入

必填尽量少：

1. **详细描述** — 用户原意 + 必要上下文。保留原话要点，可轻微整理，**不编造**未说的复现步骤。
2. **提出者** — 显示名。
3. **提出者open_id** — 有则写（给二层回执用）。
4. **日期** — 当天（多维「日期」列用**毫秒**时间戳；文本列则 `YYYY-MM-DD`）。
5. **端** / **类型** — 上节。
6. **状态** — `bug` / `意见` / `待分类` → 配置 `default_status`（默认「待确认」）；**爽点**以表选项为准（可空或「—」）。

```text
feishu_bitable_create_records(
  app_token="<from config or env>",
  table_id="<from config or env>",
  user_key="<sender_open_id>",
  identity="bot",
  records_json='[{"详细描述":"…","端":"B","类型":"bug","提出者":"张三","提出者open_id":"ou_…","日期":1725…,"状态":"待确认"}]'
)
```

列名用配置映射后的中文名。

### 3. 落盘后回用户（短）

- 一两句：已记入；带上端/类型；有表链接可附。
- **不要**复述整段、不要承诺「已派人修」「已通知研发」。
- 工具失败：说清原因；可展示草稿请手工补，**勿谎称已写入**。

### 4. 与旧「6 张 sheet」

默认路径是 **一张多维表 + 端/类型列**。若仍是 6 张电子表格，临时可用 `feishu_sheet_append` 按端×类型选 sheet，优先迁一张 bitable。

## 边界（刻意为之）

| 做 | 不做 |
|----|------|
| 先对齐类型并问「要落盘吗」 | 未同意就自动 `create_records` |
| 拿不准时用 A 段那句澄清 | 连环盘问端/优先级/复现 |
| 同意后尽快写一行 | 用一堆字段逼用户填完再写 |
| 留下 open_id 供二层 | 在本 skill 里扫状态变更并发回执 |
