# 周中对齐会会议 SOP（判定引擎 + 口径速览）

> 判定口径读 `config/meeting-sop.yaml`，用户可编辑，换公司/换会议只改该文件；本文保留
> 引擎与通用纪律，参数值与业务条目以该文件为准（与 todo-sop 同一模式）。口径当前版本
> **v1.2（2026-09-09，在 v1.1 定稿基础上澄清：主持人豁免）**：
> 已生效 4/5 条——`msop.core.01` 必有产出、`msop.core.03` 会中控制时间、
> `msop.core.04` 会后纪要与闭环执行、`msop.core.05` 杜绝流水账；
> `msop.core.02`（会前准备落实到责任人）证据在会前、本引擎无法独立取证，保持未生效。
> 口径 v1.2 澄清内容：主持人/小组负责人/Mentor/领导（一人或多人）承担主持职能
> （开场/议程推进/逐人点评/追问/打断分流/总结）时的发言不受"每人 ≤3 分钟"上限约束，
> 该上限只适用于议程三的成员个人汇报发言（见 `msop.core.03`）。
>
> 由 `meeting_pipeline_run` 按 `MeetingJob.analysis_sop_skills` 显式注入每次分块与
> 合成分析请求；注入内容 = 本文（引擎纪律）+ `config/meeting-sop.yaml` 全文（口径快照）
> + 代码渲染的「生效判定清单」（生效范围与条目正文的机器可验证投影）。三者必须一致，
> 冲突时以「生效判定清单」与口径文件为准。让"按哪一版规则、哪一条判断"可审计。

## 口径速览（人工会话可只读引用，用于回答"有没有/是什么"）

回答"会议有没有某条评价约束"这类问题时，先读本文件与 `config/meeting-sop.yaml` 再答，
不得凭印象说"没有"。当前生效条目（口径 v1.2）：

| 规则 ID | 条目 | 判定要点（摘要） |
|---|---|---|
| `msop.core.01` | 必有产出 | 会尾须有 决定/行动项/负责人/截止时间；缺结论集合 → 不符合，缺个别要素 → 部分符合 |
| `msop.core.03` | 会中控制时间 | **总时长 ≤30 分钟**；**"每人 ≤3 分钟"只约束议程三成员个人汇报发言**；主持人/组长/Mentor/领导 的主持职能发言不受该上限约束；议程一/二各 ≤5 分钟；时间戳缺失 → 证据不足 |
| `msop.core.04` | 会后纪要与闭环执行 | 会尾"更新 TODO"安排 + 跨场次开场复查验收 两个锚点；都无 → 证据不足 |
| `msop.core.05` | 杜绝流水账 | 汇报/总结段讲 问题、偏差、下一步；第一句发言不能是"做了什么"；议程一总结须与 TPMF 方向挂钩 |

引用纪律：可以说"口径里有这条、内容是什么、按哪一版"；**不得**在人工会话里据此给人
打判定/处罚（人工会话的判定无效），也不得把 `msop.*` 规则 ID、口径版本名等内部标识
当结论展示给员工时冒充正式记录。

## 使用边界

- 定时分析链路（`meeting_pipeline_run`）按本文件 + 口径文件注入判定；人工会话**只读引用**
  用于解释口径，不得冒充"本次判定结论"。
- 只判断**原始转写中明确出现**的事实；智能纪要仅辅助定位话题，不能作为 SOP 判断证据。
- 产出的是**候选与观察**：不写正式记录、不触发处罚或绩效，结论供固定收件人人工查看。

## 判定引擎（本文件生效部分）

1. **证据层级**：原文 > 纪要辅助；区分事实、发言人陈述、Agent 推断。
2. **SOP 符合性逐条判定**：按注入的「生效判定清单」对每一条 `active: true` 业务规则
   （`rules[].id`）**逐一**给出 `judgment_states` 四态之一（符合/部分符合/不符合/
   证据不足），引用规则 id 并附原文依据（时间+发言人）；同一场次同一规则只判一次，
   清单内任何一条不得遗漏。`active: false` 的条目与证据不足条目一律写
   "证据不足/待补充证据"，不允许"默认通过"，也不得臆测。
3. **四条生效规则判定要点**（详细口径以清单正文为准）：
   - `msop.core.01` 必有产出：核对会尾是否出现 结论/决定、行动项、负责人、截止时间
     四要素；缺结论集合 → 不符合；只缺个别要素 → 部分符合。
   - `msop.core.03` 会中控制时间：以时间戳/时长证据核对总时长 ≤30 分钟与议程时间盒
     （议程一/二 ≤5 分钟）；"每人 ≤3 分钟"只约束议程三成员个人汇报发言——主持人/
     组长/Mentor/领导 的主持职能发言（开场/点评/追问/打断/总结）不受该上限约束，
     不得以主持人累计/单次发言超 3 分钟判不符合；时间戳缺失 → 时长判定一律证据不足。
   - `msop.core.04` 会后纪要与闭环执行：找会尾"更新 TODO"安排与跨场次开场复查验收
     两个锚点；都观察不到 → 证据不足，留待下一场复查确认。
   - `msop.core.05` 杜绝流水账：看汇报/总结段是否讲 问题、偏差、下一步，而非报菜名；
     第一句发言不能是"做了什么"；议程一总结须与 TPMF 方向挂钩。
4. **输出结构（保证纪要首屏可见）**：`meeting_summary` 必须以「**本场 SOP 判定**」
   开头，紧接着逐条列出全部生效规则（`msop.core.*` + 四态 + 一句原文依据），
   再写会议要点；`analysis_text` 保留完整分析；正负面候选放
   `positive_negative_overview`。纪要卡片首屏取自 `meeting_summary`，不得把 SOP 判定
   压到长文末尾（会被卡片截断导致收件人看不到）。
5. **负面观察**：描述可观察行为本身，不贴标签；给出 正确做法 / 立即补救 / 预防措施。
6. **输出归属**：每条判断可回到 会议号 + 日期 + 原文片段，不得出现无出处结论。
7. **规则引用**：涉及业务条目时引用口径文件中 `rules[].id`（如 `msop.core.01`），
   不编造规则 ID；判断所述标准以「生效判定清单」正文为准。

## 会议评价与后续建议（定时任务的固定产出）

每场定时分析除逐条 SOP 判定外，**必须**产出「本场会议评价」与「后续建议」，与判定一起
出现在 `meeting_summary`（纪要卡片首屏，见上文第 4 条输出结构）里；详细论证放
`analysis_text`。判定 + 评价 + 建议三段合计控制在摘要长度内（≤1200 字），不得因为写满
分析而挤掉判定或建议。

1. **本场会议评价**（2–4 句）：这场会对推进 TPMF 起了什么作用——做成了什么、离用户/市场
   更近还是更远、主要偏差或风险在哪；只写有原文依据的判断，没依据写"待补充证据"。
2. **后续建议**（可执行）：
   - **行动项**：做什么 + 负责人 + 截止时间（取自会议原文；原文没定负责人/截止的，
     明确写"待指定"而不是替人指定）；
   - **改进建议 2–3 条**：针对会中暴露的准备、流程、协作或汇报质量问题，给可执行动作；
   - **下次会议关注点 1–3 条**：需要复查/复盘的事项，与 `msop.core.04` 的闭环锚点对应。
