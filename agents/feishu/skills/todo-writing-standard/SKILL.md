# TODO 填报规范与自动化闭环(规范即配置)

公司 TODO 填报有两层规范:**内容格式**(怎么写)和**执行纪律**(按时/按质/按量)。
本文档把两层规范结构化写死在文档里,海豚读文档执行 —— 与
[`company-todo-fill-check`](../company-todo-fill-check/SKILL.md)(请假判定口径)、
[`todo-completion-standard`](../todo-completion-standard/SKILL.md)(完成度四档)同一模式:
**规则是文字,不是代码**。

存在的理由:填报规范原本全靠人肉执行,同一份规范在不同人手里松紧不一;而产品要卖给别家公司,
规范必然被替换。所以规范本体和执行流程必须**物理分离**在同一份文档的不同段里,换公司时只动
定义、不动引擎。

## When to use

- 「帮我把这几件事写成 todo list」「整理一下填到看板表里」—— 帮写,见 [引擎段](#引擎段通用闭环)。
- 「检查 todo 填得规范吗」「谁不合规」「格式对不对」—— 检查。
- 定时任务在 [参数段](#参数段口径值) 定义的时间点触发的提醒与检查。
- 检查发现违规后要给出规范版内容 —— 补救。

## When not to use

- 判**谁没填**(整期空白算不算缺写、请假免填怎么算)→
  [`company-todo-fill-check`](../company-todo-fill-check/SKILL.md)。本文的按时规则直接引它,
  不自己另写一套查假顺序。
- 判**做完没**(某条 todo 闭环了没)→
  [`todo-completion-standard`](../todo-completion-standard/SKILL.md)。本文只管**怎么写、写没写、
  写得规不规范**,不判完成度。
- 把**一篇现成的个人 ToDoList 文档**按 `@人名` 拆开搬进看板 →
  [`feishu-todo-board-sync`](../feishu-todo-board-sync/SKILL.md)。那是文档到表的搬运,
  本文是零散输入到规范内容的组织。
- 发 todo 卡片、勾选卡片 → [`feishu-todo-card`](../feishu-todo-card/SKILL.md)。
- 派发 todo 卡与飞书任务、写 mentor 台账、判闭环回流、收 mentor 打分 →
  TODO 管理体系三件套,见下面的分工。
- 请假是否合规、报销能不能放行 → [`admin-finance-governance`]。

## 与 TODO 管理体系的分工

仓里另有一套 TODO 管理体系三件套,和本文**管的是同一张看板表的不同环节**,别混用:

| | 本文 `todo-writing-standard` | 体系三件套 |
|---|---|---|
| 管什么 | **内容怎么写、写没写、写得规不规范** | 派发、交付、评价、闭环 |
| 权威载体 | 看板表(填报文本本身) | Bitable 台账 + 飞书任务 |
| 产出 | 规范内容草稿、违规报告、提醒 | todo 卡、飞书任务、台账行、打分 |
| 判定 | 填报是否合规(格式/按时/按量) | 是否闭环(五要素) |

- [`company-todo-sync`](../company-todo-sync/SKILL.md) — 采集看板表并派发卡与任务(`0 15 * * 1,3,5`)。
- [`company-todo-audit`](../company-todo-audit/SKILL.md) — 按闭环五要素判上周期、未闭环回流(`30 14 * * 1,3,5`)。
- [`company-todo-review`](../company-todo-review/SKILL.md) — mentor 打分评语回写台账与 wiki。

**顺序**:本文的检查判「这一期填得合不合规」,体系的 audit 判「上一期的活闭环没有」。
本文在**填报侧**(表上的文本),体系在**执行侧**(任务与台账)。同一期里两者都跑,互不替代:
填得规范不等于做完了,做完了也不等于填得规范。

**两处口径不要互相覆盖**:

- **mentor 的复核**有两套标记,分属两层,别拿一套去判另一套:本文只认**看板表上的 mentor check 列**
  (复核「这一期填报写得对不对」);体系的 audit 认**台账里的 `mentor打分` / `mentor评语`**
  (评价「这条活干得怎么样」)。台账有打分不代表看板表上有 check,反之亦然。
- **定时撞点**:体系的 audit 是 `30 14 * * 1,3,5`,与本文参数段的 14:30 提醒同一分钟 ——
  建任务前先 `schedule_manage(action="list")`,把本文的提醒挪开几分钟。

## 五段结构:哪一段会变,哪一段不许变

换公司、换需求时只允许改前四段。**引擎段一字不动**就是本技能的可扩展性检验标准:

| 段 | 内容 | 变化时 | 举例 |
|---|---|---|---|
| [**引擎段**](#引擎段通用闭环) | 通用闭环:采集 → 按 schema 生成/校验 → 按规则集检查 → 按角色报告 → 按节奏调度 | **不变** | 帮写/检查/提醒的执行流程 |
| [**内容 schema 段**](#内容-schema-段结构定义) | 结构定义:层级/字段/必填/类型/粒度 | 换 schema 定义 | 三层 TODO → 小方案(带跟进/验收字段) |
| [**规则集段**](#规则集段纪律规则) | 纪律规则,每条 = 触发条件 + 判定对象 + 判定逻辑 + 违规文案 + 报告去向 | 增删规则条目 | 按时/按质/按量、24h check、请假免填;后续加跟进/验收 |
| [**载体段**](#载体段数据源映射) | 数据源映射:哪张表、哪些列、映射到哪个 schema 字段 | 换适配配置 | Excel 看板表 → 多维表格/任务系统 |
| [**参数段**](#参数段口径值) | 口径值:数量上限、时限、定时节奏、术语 | 改值 | 5 条、24h、周一/三/五 14:30/14:50 |

**段间只通过引用关联,不许互相写死。** 具体地:

- 引擎段不许出现具体层级名(「大目标」)、具体数字(「5 条」)、具体列名或表 token。要用时写
  「按 schema 段的层级」「按参数段的条数上限」。
- 规则集段不许复制 schema 段的字段清单,只引用「schema 段的必含要素」。
- 判定参数一律从规则集段/参数段读,不在引擎段里重复一份口径 —— 重复的那份迟早和定义对不上。

违反这条的征兆:改了参数段的数字,行为却没变(因为引擎段里还硬写着旧值)。

### 当前是哪一份 schema

本迭代以**真知三层 TODO** 作为第一份 schema 实例。已定的演进方向是 TODO 将变成「小方案」、
增加跟进与验收环节 —— 那一天的正确改法是:**换 schema 段、规则集段加跟进/验收条目,
引擎段一字不动,不新增 skills**。若换内容结构就得再堆一个 skill,说明做成了特化而非扩展。

与既有资产同源:引擎通用、场景差异全部收进可替换的定义,这与
[`card-dsl`](../card-dsl/SKILL.md) 的「卡片 = 词汇表(XML 元素) + 渲染引擎(`feishu_card_render`)」
是同一思想(TODO 管理 = schema + 规则集 + 引擎):业务只声明「有什么」,协议与流程限制全部由引擎
消化。「小方案」的内容结构与方案 SOP 同源,后续共享同一套 schema 机制,而不是各堆一个 skill。

### 按需下沉(不预先建设)

若实测发现某条规则靠模型不够可靠(典型是**精确条数计数**),把**那一条**的判定下沉为确定性工具;
判定参数仍从规则集段/参数段读,不与引擎重复口径。需要时下沉单项,不预先建通用引擎代码。

## 内容 schema 段:结构定义

真知 TODO list 的三层结构。**这是当前 schema 实例,换公司时整段替换。**

| 层级 | 时间粒度 | 数量 | 必含要素 | 结构关系 |
|---|---|---|---|---|
| **大目标** | 3-6 个月 | 1 或多个 | 事情描述、时间、标准 | 与组织上一级大目标对齐;成果来自外部 |
| **小目标** | 1 周-1 个月 | 1 或多个 | 事情本身 + 标准 | 大目标的拆解;大目标可暂无小目标(暂不做),但至少 1 个大目标有对应小目标 |
| **TODO** | 1-2 天,最长 3 天 | 1 或多个 | 时间节点 + 标准;能有 deadline 必须有 | 小目标的拆解;不是「要干什么」而是「什么时间干成满足什么标准的什么事」 |

三条判定要点,校验和生成都以它们为准:

1. **TODO 的写法是硬要求。** 「不是要干什么,而是什么时间干成满足什么标准的什么事」——
   只写动作(「写文档」「调接口」)即缺要素,必须带时间节点与标准。
2. **粒度超限即违规。** TODO 超过 3 天说明没拆到位,该拆成多条。
3. **大小目标对应关系要成立。** 小目标必须挂在某个大目标下;至少 1 个大目标有对应小目标。
   大目标暂无小目标是允许的(暂不做),但全部大目标都没有小目标不允许。

**持续性 TODO**(长期反复做、无自然终点的)简单写明即可,不强求 deadline —— 但要写清是持续项,
不能拿它规避 deadline 要求。

## 规则集段:纪律规则

执行纪律三条。每条的形状是**触发条件 + 判定对象 + 判定逻辑 + 违规文案 + 报告去向**,
增删规则就是增删这张表的行。**判定对象全部是看板表** —— 不看聊天记录、不看打卡、不看口头承诺。

| 规则 | 触发条件 | 判定对象 | 判定逻辑 | 违规文案 | 报告去向 |
|---|---|---|---|---|---|
| **按时** | 参数段的检查时间点 | 载体段的当期列 + 请假事实 | 填报日当天填写;已通过请假区间内记「请假免填」,其余未写 = 违规 | 「<日期>当期未填报,且无已通过请假记录」 | boss 视图 + 该成员 mentor |
| **按质** | 同上 | 载体段的当期单元格文本 | 按 schema 段写:三层结构合法、必含要素齐全、TODO 有 deadline | 「<日期>填报缺<缺失要素>」/「层级关系不成立」 | 同上 |
| **按量** | 同上 | 当期单元格的 TODO 条数 | 每期条数 ≤ 参数段的条数上限 | 「<日期>填报<N>条,超出上限<上限>条」 | 同上 |
| **mentor check** | 填报后经过参数段的 check 时限 | 载体段的 mentor check 列 | 时限内该列有 check 标记;超时未标记 = 违规 | 「<日期>填报已超<时限>未见 mentor check」 | **只给 mentor** |

### 按时:查假在下结论之前

按时规则的请假判定**完全走 [`company-todo-fill-check`](../company-todo-fill-check/SKILL.md)**,
本文不复制那套口径。硬顺序不许颠倒:

```text
读表(拿到空白的 人 × 日期 清单)
        ↓
feishu_leave_query(按那份技能的模板 code 与日期窗)
        ↓
逐个空白比对 on_leave[].hit_dates
        ↓
才可以说「未填 = 违规」
```

顺序颠倒即出错:先写好违规名单再查假,查到了往往只在结论后补一句,而「违规」这个判断本身
已经错了。错误方向是**加重考核**,且不会立刻暴露 —— 被判的人得自己回来申诉。

那份技能的三类产出(缺写 / 请假免填 / 待人工确认)直接对应本文的按时判定:
**缺写 = 违规,请假免填 = 不违规不计入,待人工确认 = 不判违规**。
`skipped_not_approved`(审批中)与 `needs_fix`(日期读不出来)必须在报告里提一句,咽掉等于把
「确实请了假」变成「没请假」。读表或查假失败时**明说查询失败**,不得顺势判违规。

### 按质:结构检查查什么

逐项对照 schema 段,缺一项报一条,每条带依据(哪一层、缺什么):

- 三层是否都在,层级标记是否可辨(照 schema 段的层级命名)。
- 每层的**必含要素**是否齐全 —— 按 schema 段那张表逐层核,不在本段重复一份清单。
- TODO 是否有 deadline(能有 deadline 的必须有;持续项标明即可)。
- TODO 的时间粒度是否超过 schema 段的上限。
- 大小目标对应关系是否成立。

### 按量:条数怎么数

数**当期单元格里的 TODO 条数**,不数大目标与小目标。跨行、编号断续、一行写多条这些形态都有,
数不准时**报「待人工确认」而不是给个数**。这一条是最典型的「模型不够可靠」候选:
真出现误计,就按[按需下沉](#按需下沉不预先建设)把它做成确定性工具,参数仍从参数段读。

### mentor check:超时只提醒,不代 check

mentor check 的标记**只认载体段指定的 mentor check 列** —— 聊天里说过、口头确认过都不算。
超过参数段的 check 时限仍未标记时,**只提醒 mentor,海豚绝不代替 mentor 打 check**。
代 check 等于把复核环节变成走过场,而且错误不可见。

## 载体段:数据源映射

当前载体是**飞书电子表格看板表**:**列 = 日期,行 = 人**。

| schema/规则 要素 | 落在载体的哪里 | 怎么拿 |
|---|---|---|
| 当期填报内容 | 当期日期列 × 该人行 的单元格 | 读 `feishu_sheet_read(token, "SHEET_ID!A1:Z60")`;写 `feishu_sheet_write(token, range, values_json)` |
| 人 | 人名列 | 现场读表头与人名列定位 |
| 期次 | 表头日期行 | 现场读,格式往往是 `8.19` 这类点分无年份写法 |
| mentor check | **mentor check 列** | 同一张表上的独立列,现场按表头认列 |
| 请假事实 | 不在表上 | `feishu_leave_query`,见按时规则 |

**表结构一律现场探,不许写死。** 表头是哪一行、人名在哪一列、mentor check 是哪一列、
`SHEET_ID` 是什么,每次都读出来。换公司换表就是换这一段的映射,引擎段不感知。

三条来自实战的硬规则(与 [`feishu-todo-board-sync`](../feishu-todo-board-sync/SKILL.md) 同源,
那边已踩实):

1. **wiki 链接先换 token。** 链接是 `/wiki/` 开头时后面那串是 **node_token,不能直接当文档 id**:
   先 `feishu_api` 打 `GET /open-apis/wiki/v2/spaces/get_node` 换 `obj_token` + `obj_type`,
   再决定读法。顺序错了就是一路 404。链接本来是 `/sheets/` 的,那串就是 `obj_token`。
2. **目标单元格非空先报警。** 不许直接盖。把现有内容摘出来给用户看,等明确确认才写。
3. **不给表里没有的人新增行。** 报为 skipped。

日期归一:表头 `8.19` 这类无年份点分写法,**比对前先补年份归一成 ISO**(`feishu_leave_query`
返回的 `hit_dates` 是 ISO)。无年份表头默认按当年解释;跨年场景(12 月的表里出现 `1.5`)
不要自己猜,归到**待人工确认**。

权限:表要么该 app 是协作者,要么走 `feishu_auth_start()` 让本人授权后带 `user_key=<sender_open_id>`。
整条链路(get_node → sheets query → read → write)用**同一个** `user_key`。

## 参数段:口径值

**换公司时改这一段的值即可,其余段不动。** 当前值经方案确认定死:

| 参数 | 当前值 |
|---|---|
| 每期 TODO 条数上限 | **5 条** |
| mentor check 时限 | 填报后 **24h** |
| 提醒时间点 | **周一/三/五 14:30**(本机墙钟) |
| 检查时间点 | **周一/三/五 14:50**(本机墙钟) |
| mentor check 标记形态 | 看板表上的 **mentor check 列**有标记即算 |
| 检查报告投递 | **私聊**:boss 视图给 boss,mentor 视图给对应 mentor |
| 层级术语 | 大目标 / 小目标 / TODO |
| 违规文案 | 见规则集段那张表的「违规文案」列 |

术语与文案全在文档内,报告与提示语随文档走 —— 引擎段不许自己造词。

### 定时节奏怎么落

| 时间 | 动作 |
|---|---|
| 14:30 | 提醒当天未写且无请假的成员(私聊) |
| 14:50 | 检查是否规范(是否已写、格式是否合规),出报告 |

两条都用现成的 `schedule_manage` 建**周期**任务,不写新工具:

```text
schedule_manage(action="create", schedule_name="todo-remind",
                cron="30 14 * * 1,3,5", description="TODO 填报提醒",
                content="按 todo-writing-standard 的提醒流程执行")
schedule_manage(action="create", schedule_name="todo-check",
                cron="50 14 * * 1,3,5", description="TODO 填报规范检查",
                content="按 todo-writing-standard 的检查流程执行")
```

两条都要走 `fire=prompt`(默认):提醒要先查表和请假才知道催谁,检查要读表做结构判定,
都需要模型参与 —— `fire=tool` 是直接调一个工具、不过模型,套不进来。

**14:30 与 `company-todo-audit` 的 `todo-cycle-audit`(`30 14 * * 1,3,5`)是同一分钟。**
两者 `schedule_name` 不同,不会互相覆盖,但会同时叫醒会话、都去读同一张看板表。
建之前先 `schedule_manage(action="list")` 看那条在不在:在的话把本文的提醒挪开几分钟
(改参数段的时间点即可,例如 `25 14`),别让两个 prompt-fire 任务撞在一起。
两套体系的关系见 [与 TODO 管理体系的分工](#与-todo-管理体系的分工)。

**cron 用调度器时区解释,不是裸机墙钟。** 建完立刻 `action="view"` 核一遍写进去的 cron 与
下次触发时间;时区没配对会整体偏移(仓里踩过 `once_at` 按裸机墙钟读、与调度器时区差 8h 的坑)。
`cron` 与 `once_at` 不许同时传。

## 引擎段:通用闭环

**这一段不含任何具体层级名、数字、列名、表 token。** 要用时一律写「按 schema 段」「按参数段」
「按载体段」。换公司时这一段一字不动 —— 若发现必须改这里才能适配,说明定义没剥干净,
改的是前四段而不是这里。

四个能力共用一条闭环:**采集 → 按 schema 生成/校验 → 按规则集检查 → 按角色报告 → 按节奏调度**。

### 帮写(主场景)

成员把零散任务发过来(私聊口述、发文档、丢几条消息都行),海豚按 schema 段组织成规范内容:

1. **识别** —— 把零散输入归到 schema 段定义的各层。可结合该成员的工作树快照(`wiki_*`)与
   上期填报(读载体段的上一期列)判断归属,两者都是可选输入,拿不到不阻塞。
2. **补全** —— 补齐 schema 段要求的每层必含要素;最细一层按 schema 段的时间粒度拆解,
   能有 deadline 的一定写。
3. **澄清** —— 缺的关键信息(标准、deadline、验收人)**先问成员,不瞎编**。这是硬约束:
   编一个标准出来,成员确认时未必看得出,错的东西就进了表。
4. **写入** —— 组织好的规范内容**给成员确认,确认后**写进载体段的当期列。

### 检查(定时触发)

按参数段的检查时间点跑,对象是载体段的表:

1. 读当期列,拿到每人的填报文本与空白清单。
2. **结构检查**:按规则集段的按质规则逐项核。
3. **执行检查**:按规则集段的按时(含请假免填)、按量、mentor check 逐条判。
4. **出报告**,按规则集段每条规则的「报告去向」分发。

报告两个视图,**每条违规必须带依据**(哪一期、哪一条规则、缺什么):

```text
boss 视图
整体合规率:12/15(80%)
违规名单:
| 成员 | 期次 | 违反规则 | 依据 |
|---|---|---|---|
| 张三 | 8.19 | 按时 | 当期列空白,无已通过请假记录 |
| 李四 | 8.19 | 按质 | 最细一层 3 条无 deadline |
| 王五 | 8.19 | 按量 | 当期 7 条,超出参数段的条数上限 |
请假免填:赵六(8.19,已通过 2026-08-19 ~ 2026-08-20)
待人工确认:孙七(条数数不准,跨行编号断续)
审批中未计入请假:周八(1 件)

mentor 视图(私聊各 mentor,只含自己名下)
你名下 3 人,2 项违规:
| 成员 | 期次 | 违反规则 | 依据 |
|---|---|---|---|
| 李四 | 8.19 | 按质 | 最细一层 3 条无 deadline |
待你 check:张三 8.16 填报已超时限未见 check 标记
```

投递按参数段:两个视图都**私聊**发送(`feishu_message_send`),mentor 视图只含该 mentor
名下成员 —— 不向无关成员披露别人的违规情况。

### 提醒(定时触发)

按参数段的提醒时间点跑:读当期列找出**未写**的人,剔掉**已通过请假**的(走按时规则那条硬顺序),
对剩下的人**私聊**提醒。提醒文案带规范要点(schema 段的层级结构、deadline 要求),
文案措辞取自参数段与规则集段,不自己造词。

### 补救(检查发现违规时生成规范内容)

| 违规类型 | 生成什么 | 写进哪里 |
|---|---|---|
| **未写**(且无请假) | 从该成员上期填报 + 对话/任务记录提取当前目标,生成规范格式草稿(各层齐全) | 成员确认后写当期列 |
| **结构不规范**(缺要素/缺 deadline/层级错) | 补全缺项生成规范版 | 同上 |
| **超量** | 精简建议(合并/移入下期),**不改表** | 提醒成员自改 |

### 确认机制(贯穿帮写与补救)

**帮写与补救一律「生成 → 成员确认 → 写表」,没有例外。** 海豚不在无人确认的情况下改表内容。

mentor check 超时**只提醒 mentor,不代 check** —— 见规则集段。

## Boundaries

- **请假免填不催不判违规**,但要在报告里列出来并附依据(哪个请假实例、什么区间)。
- **mentor check 只认载体段那一列的标记**,聊天里说过不算;超时只提醒,不代打 check。
- **帮写不替成员编造标准与验收人**,缺的必先问。
- 读表/查假失败要**明说查询失败**,不得顺势判违规。
- 数不准、日期对不上、表结构没读明白 → 归**待人工确认**,不要塞进违规名单凑数。
- 本文只管**怎么写、写没写、写得规不规范**。「做完没」换
  [`todo-completion-standard`](../todo-completion-standard/SKILL.md);
  **填报缺失不是完成度证据**,别拿本文的「未写」去给条目判未闭环。
- 检查报告是**事实判定,不是绩效评价**,不加评价性措辞。

## 别做的事

- 别在引擎段里硬写层级名、条数、时限、列名或表 token —— 那正是换公司时改不动的原因。
- 别把本文的示例值(15 人、8.19、示例表格)当常量用,每次现场探。
- 别静默覆盖非空单元格。
- 别代成员写完就直接落表(必须先确认)。
- 别代 mentor 打 check。
- 别用打卡记录反推请假(缺卡同时对应出差/外勤/忘打卡,反推会静默放宽考核)。
- 别在没查请假前说某人违规。
