# 正负面清单卡片统一设计

## 目标

吸收 PR #843 的 Card 2.0 交互风格，修正会议纪要候选“确认一条就记一条”的错误边界。会议纪要只产生待整理事件包；最终记录写入 HaiTun 机器人独立测试表，正式总表只读；记录通知通过卡片进入私聊复盘。

## 设计原则

1. 候选句不是正式行为事实。候选先按事件边界整理、去重并决定纳入或忽略；补证放到后续分析对话。
2. 候选整理卡不以会议纪要的一句话直接触发写入；纳入后仍须形成完整事件包并重新分析。
3. 任何写入都经过“分析完成 + 写入者确认”两道门。
4. 测试表沿用现有正式六列，不增加字段；内部状态保存在 AppData，用于幂等和卡片恢复。
5. 正式总表只读，不允许候选确认、复核、反馈或复盘写回正式表。
6. 用户可见内容统一显示姓名和中文状态，不显示 open_id、内部规则 ID 或状态机字段。

## 交互流程

### 场景 A：候选整理

Agent 从会议纪要等批量来源得到候选线索后，按涉事人、时间窗口、场合和因果关系形成候选批次。卡片只提供：

- 纳入候选：保留到事件包，尚未写表；
- 暂时忽略：标记为非行为事实、重复信息或当前不处理。

候选整理完成后，Agent 在私聊中重新做四要素检查、证据补充、正负分类、行为分类和重复检查。

### 场景 B：记录确认

对完整事件包生成统一记录确认卡，展示涉事人、事实、影响、分类、证据状态，以及负面行为的正确做法、立即补救和预防措施。动作只有：

- 确认写入测试表；
- 其他修改通过后续私聊重新分析，不在确认卡内提供多余动作。

“确认写入”只写机器人测试表，并在写入成功后发送记录通知卡；复盘需由涉事人点击卡片按钮主动开始。

### 场景 C：记录通知与复盘

记录通知使用 Card 2.0，负面记录附正确做法、立即补救和预防措施，底部提供“开始复盘”按钮。点击后由海豚发起三段式私聊复盘，答案只保存到个人私有草稿，不写回任何表格。

## 状态与幂等

- 事件包状态：`pending`、`kept`、`ignored`、`ready_for_analysis`、`analysis_started`、`case_prepared`。
- 同源候选按来源键幂等；跨源相似进入疑似重复判断，不自动合并。
- 卡片按钮重复点击返回当前终态，不重复写入、不重复提醒、不重复创建复盘。
- 写入失败时保持待处理状态，不能把卡面刷成已完成。

## 兼容范围

吸收 PR #843 的 Card 2.0 结构、卡片原位更新、终态无按钮、回调幂等和姓名展示；不直接引入其任意 ledger 写入、mentor 正式复核、周小结或正式表回写实现。所有写入通过现有测试表路径完成。

## 验收标准

1. 一批会议纪要候选不会产生逐句写入动作。
2. 同一事件的多句候选不会在候选卡中逐句写入；后续以事件包为单位分析。
3. 缺少人、时间、场合、影响或证据时只能进入补充信息流程，不能确认写入。
4. 评价性句子不能直接作为行为事实。
5. 测试表写入、提醒和复盘链路可完整跑通；正式总表调用只读接口。
6. 候选卡、记录通知卡、复盘按钮和重复点击行为有自动化测试覆盖。
