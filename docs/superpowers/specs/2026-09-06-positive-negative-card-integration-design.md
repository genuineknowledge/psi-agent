# 正负面清单判断卡整合设计

## 目标

吸收 PR #843 的卡片交互能力，修正会议纪要候选“确认一条就记一条”的错误边界。会议纪要只产生待整理事件包；最终记录、复核、补充说明和复盘全部写入 HaiTun 机器人独立测试表，正式总表只读。

## 设计原则

1. 候选句不是正式行为事实。候选必须先按事件边界合并、拆分和补证。
2. 一次卡片操作处理一个事件包，不以会议纪要的一句话作为一条记录单位。
3. 任何写入都经过“分析完成 + 写入者确认”两道门。
4. 测试表沿用现有正式六列，不增加字段；内部状态保存在 AppData，用于幂等和卡片恢复。
5. 正式总表只读，不允许候选确认、复核、反馈或复盘写回正式表。
6. 用户可见内容统一显示姓名和中文状态，不显示 open_id、内部规则 ID 或状态机字段。

## 交互流程

### 场景 A：会议纪要候选整理

Agent 从会议纪要抽取候选句后，先按涉事人、时间窗口、场合和因果关系形成事件包。卡片只提供：

- 纳入候选：保留到事件包，尚未写表；
- 合并事件：把当前候选并入另一个事件包；
- 忽略：标记为非行为事实或重复信息；
- 补充证据：进入私聊补证，不改变表格。

所有事件包处理完成后，Agent 重新做四要素检查、正负分类、行为分类和重复检查。

### 场景 B：候选记录确认

对完整事件包生成统一判断卡，展示涉事人、事实、影响、分类、证据状态，以及负面行为的正确做法、立即补救和预防措施。动作只有：

- 确认写入测试表；
- 修改后重新分析；
- 暂不记录。

“确认写入”只写机器人测试表，并在写入成功后触发涉事人私聊提醒和私有复盘。

### 场景 C：结果反馈与复盘

通知和复盘沿用现有工具，但只写测试表或个人私有草稿。反馈卡不允许直接修改正式总表；补充说明追加到测试表的现有备注列时，必须先确认目标是测试表。

## 状态与幂等

- 事件包状态：`pending`、`merged`、`needs_evidence`、`ignored`、`ready_for_analysis`、`written`。
- 同一事件包只能生成一个候选记录；同源候选按来源键幂等，跨源相似进入待人工判断，不自动合并。
- 卡片按钮重复点击返回当前终态，不重复写入、不重复提醒、不重复创建复盘。
- 写入失败时保持待处理状态，不能把卡面刷成已完成。

## 兼容范围

吸收 PR #843 的卡片原位更新、修改表单、终态无按钮、回调幂等和姓名展示；不直接引入其任意 ledger 写入、mentor 正式复核、周小结或正式表回写实现。所有写入通过现有 `positive_negative_case_prepare` / `positive_negative_case_confirm` 测试表路径完成。

## 验收标准

1. 一批会议纪要候选不会产生逐句写入动作。
2. 同一事件的多句候选可以合并为一个事件包，并保留来源句。
3. 缺少人、时间、场合、影响或证据时只能进入待补证，不能确认写入。
4. 评价性句子不能直接作为行为事实。
5. 测试表写入、提醒和复盘链路可完整跑通；正式总表调用只读接口。
6. 卡片所有终态和重复点击行为有自动化测试覆盖。
