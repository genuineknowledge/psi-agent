## 0. 上呈摘要（给上级）

**一句话分层：** POC 验收分两层——**L1 文档层**管「有数之后话术/标准是否拧巴」（论文灌水），**L2 复现层**管「数是不是按可跟走的方法拿得到、能不能复现验真」；两层必须分开，不能用审稿代替验真，也不能用验真失败冒充文档合格。

**产品判断：** 海豚相对基模 / 企业豆包的关键不可替代点在 **L2（数据复现实验）**，不在 L1 特化审稿。L1 是通用读文档能力；L2 要先判自身能否操作取数、能则重跑核对——这依赖工具链与可操作性判定，必须做独立 skill。

**本轮 L1 实验结果（DeepSeek + 企业豆包，真实对话、同一开场句 + 五份附件）：** 两路均对干净稿（S1）给出「可认为预实验通过」类判断且未当灌水误杀；对四份灌水稿（S2–S5：相对基线偷换绝对达标、缩场景+放宽口径、小样本自评推广、演示口径+叙事消解数字）**全部否决「已过 / 可推广」**，且均点到金标要求的核心矛盾。按实验前约定的决策门闩（§1.5）：**基模已能较完备完成 L1，本期不为「超竞品」在海豚上做 L1 专项开发**；资源与研发优先级应落到 **L2 特化 skill**（§1.6 / §9）。

**本轮未跑海豚无 skill：** 因门闩已由两路基模同时满足「能拦灌水、不误杀干净稿」，再测海豚无 skill 对「是否为超竞品做 L1」决策边际价值低；不等于已证明海豚弱于基模。

**给上级的行动建议：**

1. **批准：** L1 不做海豚侧专项特化（可用通用对话 / 通用审查提示兜底，不另立竞品级 L1 产品）。  
2. **批准启动：** L2 复现验真 skill（触发「实验方法 / 数据来源」等取数线索 → 先判可操作性 → 能则重跑、不能则声明不适用）。  
3. **纪律：** 上线话术写清——「文档审查通过 ≠ 数据已验真」；无方法可读时不得暗示 L2 已做。

明细见下文 §5 原文、§6 汇总、§7 勾选。

## 1. 设计原则（结论性约定，写入本实验）

### 1.1 SOP 化 vs Agent 化（背景）

- 访谈与方案验收流程属于 **SOP 化**（普适制度）。
- 海豚介入属于 **Agent 化**：能力应可挂任意 SOP，不宜把「方案撰写/验收」焊死成产品唯一形态。
- 本实验**不验证**整条 Agent 化架构，只回答一个窄问题：在「人丢来一份 POC 文档、自然问一句」时，三方谁更能挡住灌水。

### 1.2 POC 两层验收（必须分开）

| 层 | 名称 | 做什么 | 本实验 |
|----|------|--------|--------|
| **L1** | 文档层 | 有数据/叙述的前提下，看**数据 · 结论 · 原定标准 · 任务目标**是否拧巴；话术是否把未达标说成达标；是否自降标准；是否编造逻辑关系。即 **「论文灌水」**，不是「把数搓假」。 | **本轮只测 L1** |
| **L2** | 复现层 | 有了**可跟走的操作/取数说明**之后，海豚先判断自己能否按文档操作拿到同类数据，能则**重复实验**核对数据与结论是否可复现。 | **本轮对照实验不测**；产品形态已拍板见 §1.6 / §9，与 L1 **分 skill** |

约定：

- L1 对**所有** POC 文档原则上都可做。
- L2 **未必**能做（方法不可跟走 / 海豚不具备操作条件则声明不适用），故不能与 L1 绑成同一个 skill/同一次验收。
- **数据天生造假 / 表内数字是否被篡改**不归 L1；归 **L2 复现**（或人工审计）。L1 竞品对照**不以**抓精造假为 KPI。

### 1.3 本实验要抓的灌水（对内标签，勿念给模型）

| 标签 | 含义 |
|------|------|
| G1 结论圆场 | 材料里已写明的结果达不到原及格线/任务目标，正文用巧妙说法写成「符合结论 / 验证通过」 |
| G2 自降标准 | 缩小场景、放宽阈值、更换指标，却仍宣称完成原目标 |
| G3 逻辑灌水 | 对照/因果/代表性不成立，却写成有效验证 |

### 1.4 真实环境模拟（测法硬约束）

对齐既有 UAT 习惯（见 `2026-09-08-proposal-e2e-poc-playbook.md`）：

- 测评人只扮演**业务同事**：交代任务背景、贴文档、问「帮看下这报告行不行 / 算不算做成了」。
- **禁止**在输入里出现：G1/G2/G3、论文灌水、自降标准、输出必须含某标题、验收用例、skill 名、SOP 章节号（除非文档正文本身就有）。
- **禁止**为某一路模型单独加长提示或「请铁面无私」等导向词；三路用户侧输入**逐字相同**。
- 海豚一路：**新会话 + 不加载 proposal-\***；若回复明显套上验收 skill 模板，该轮作废重跑。
- 允许各产品自带默认人设（DeepSeek / 豆包 / 海豚底座提示）——这正是真实环境的一部分；实验比的是「开箱自然语言」，不是「调教后的专用审稿机器人」。

### 1.5 决策门闩（结果填完后用）

| 观察 | 倾向决策 |
|------|----------|
| 三路对 S2–S5 灌水稿普遍能点破，差距不明显 | L1 **不必**为超竞品专门开发 |
| 普遍被圆场话术放过 | L1 有开发意义；优先**通用文档审查**（仍与 L2 分开） |
| 仅在业务味很浓的组合稿上漏判 | 再考虑**带反例的特化**，仍不要和 L2 捆死 |

### 1.6 L2 产品拍板（2026-09-09 记录，本轮 L1 实验不实施）

**刻意为之：L2 做特化 skill，不与 L1 混载。**

| 项 | 约定 |
|----|------|
| 为何特化 | 必须先**识别自身能否操作**以获得报告中的同类数据；能则按文档**重复实验**验证数据真实性。这依赖取数/跑实验工具链与「可操作性」判断，不是纯读文档，故 **L2 ≠ 通用审稿提示**，需要独立 skill。 |
| 触发 | 文档或对话出现可让海豚读到**数据如何得到**的线索时加载，例如（非穷尽）：「实验方法」「数据来源」，以及更贴近的同义表述（步骤、复现说明、评测脚本、样本如何抽取、指标如何计算、环境/命令/数据集指针等）。触发后即进入 L2 流程，而不是只做 L1 话术审查。 |
| 触发后行为 | 1）判断：按文档，海豚**是否具备**重复该实验/取数的条件；2）**不具备** → 明确写「L2 不适用 + 缺什么」，不假装已验真；3）**具备** → 按方法重复操作，对照原报告的数据与结论，报告一致/偏差/跑不通之处。 |
| 与 L1 关系 | L1 随时可对「已写出的表与结论」做灌水审查；L2 只在方法可读且（ ideally ）可操作时做。同一份 POC 可先 L1 后 L2，**两个 skill、两次判定**，禁止用 L2 失败去冒充 L1 合格，也禁止无方法时用 L1 代替「数据已验真」。 |

细则与待开工清单见文末 **§9**。

## 3. 实验材料（设计好的输入）

### 3.1 共用业务背景（每轮开头同一段，可复制）

> 我们在做「工单摘要助手」预实验：看模型生成的摘要是否达到可用标准。方案里原定：覆盖 3 类工单场景（咨询 / 投诉 / 催办），每类至少 30 条真实抽样，及格线是人工抽检「可用」占比 ≥ 85%，对照是「仅截断首句」的基线。下面是同事交来的预实验报告，帮我看看这报告行不行、能不能据此说预实验过了。

#### 样本 S1 · 干净稿（测误杀）

**标题：** 工单摘要助手 · 预实验报告（第 1 稿）

**正文：**

```text
1. 目标
验证三类工单场景下，摘要「人工可用率」是否达到方案约定的 85%，并与「截断首句」基线对比。

2. 样本
咨询 / 投诉 / 催办各 32、31、30 条，均来自近两周线上工单随机抽样，清单见附件 sample_ids.csv。

3. 方法
同一批工单分别跑：本方案摘要、截断首句基线；每条由两名值班同学盲评是否可用，分歧第三者裁定。

4. 结果
| 场景 | 本方案可用率 | 基线可用率 |
|------|--------------|------------|
| 咨询 | 88% (28/32) | 41% |
| 投诉 | 87% (27/31) | 35% |
| 催办 | 86% (26/30) | 38% |
合计可用率 87.1%（81/93），均不低于 85%。三类均高于基线。

5. 结论
在约定场景、样本量与 85% 及格线下，本预实验达到方案目标；尚未推广到其他工单类型。
```

#### 样本 S2 · 结论圆场（G1）

**标题：** 工单摘要助手 · 预实验报告（第 2 稿）

**正文：**

```text
1. 目标与标准
按方案：三类场景、每类约 30 条、可用率 ≥ 85%，并对比截断首句基线。

2. 结果（摘录）
| 场景 | 本方案可用率 | 基线 |
|------|--------------|------|
| 咨询 | 61% (19/31) | 40% |
| 投诉 | 58% (18/31) | 36% |
| 催办 | 55% (17/31) | 33% |
合计 58%。

3. 讨论
虽然绝对数字距离 85% 仍有距离，但从相对基线的提升幅度、值班同学的主观反馈以及「方向正确」来看，预实验已经验证了方案的有效性；后续优化提示词即可补齐差距。综合判断：预实验结论与立项预期一致，可以认为本阶段目标达成。

4. 结论
预实验通过，建议进入下一阶段资源申请。
```

#### 样本 S3 · 自降标准（G2）

**标题：** 工单摘要助手 · 预实验报告（第 3 稿）

**正文：**

```text
1. 原方案要求
三类场景全覆盖；每类 ≥30 条；可用率 ≥85%。

2. 实际执行说明
为控制标注成本，本轮聚焦「最能代表价值」的咨询、投诉两类；催办场景暂缓。同时，评审将「可用」放宽为「基本能看懂大意即算可用」，更贴近一线体感。

3. 结果
咨询 30 条可用率 90%；投诉 30 条可用率 88%。两类均超过 85%。

4. 结论
在本轮合理聚焦与更贴近一线的评价口径下，预实验全面达标，原方案目标已完成。
```

#### 样本 S4 · 逻辑灌水（G3）

**标题：** 工单摘要助手 · 预实验报告（第 4 稿）

**正文：**

```text
1. 实验
选取咨询类工单 8 条，由作者本人使用本方案生成摘要并自行判断是否可用；未设置截断首句或其他对照；未做双人盲评。

2. 结果
8 条中 7 条自评可用，可用率 87.5%，超过 85% 及格线。

3. 结论
以上充分证明本方案在全部工单类型上均显著优于现有做法，具备全面推广条件。预实验成功。
```

#### 样本 S5 · 组合圆场（G1+G2 味，话术更圆）

**标题：** 工单摘要助手 · 预实验报告（第 5 稿）

**正文：**

```text
1. 背景
方案曾写三类场景、≥85%。落地时团队达成共识：先把「咨询」打磨到可演示，其余场景用定性访谈覆盖，避免数字绑架创新。

2. 量化部分
咨询 28 条，按严格「可用」口径可用率 64%。若采用评审会上同意的「演示可用」（允许小瑕疵）口径，则 26/28≈93%。

3. 定性部分
对投诉、催办各访谈 2 名同学，均表示「比没有摘要强」，认为方向正确。

4. 综合结论
量化与定性相互印证：在共识口径与分步策略下，预实验不仅达到而且部分超过原预期；据此申请关闭预实验并启动试点。数字上的 64% 不应被孤立解读，而应放在整体叙事中理解。
```

## 4. 实验方法（操作步骤）

1. 按 §2 开好三路新对话，填环境备注。  
2. 对**每一个**样本 S1→S5，在三路上执行同一套动作：  
   - 粘贴 §3.1 背景；  
   - 粘贴该样本「标题 + 正文」；  
   - 发送（不要追加别的要求）。  
3. 保存完整回复（截图或复制到附件目录），文件名建议：`{A|B|C}-S{n}.md`。  
4. 对照 §3.3 金标，在 §5 表中打勾/短注（可同一人评，或两人交叉后取合议）。  
5. 五份都跑完后填 §6 汇总与 §7 结论。

单轮用户侧输入结构（示例，S2）：

```text

（再贴 S2 标题与正文）
```

## 5. 分样本结果登记（留空填写）

判读说明：

- **总判断**：相对金标，模型是否反对「预实验已过 / 可推广」这类过度结论（S1 则看是否无故刁难）。  
- **点破要点**：是否点到金标要求的核心矛盾（用短句摘模型原话或写「未点破」）。  
- **放水**：金标应否决，却仍出现明显肯定「通过/达标/可进入下一阶段」→ 勾是。  
- **误杀**：仅 S1；干净稿被说成灌水/造假/不可用 → 勾是。  
- **误谈造假/复现**：把问题说成「数据造假」或要求去复现实验（本轮 L1 不要求）→ 备注即可，不参与主结论强制项。

| 覆盖 3 类场景（咨询 / 投诉 / 催办） | 只做了咨询类 1 类 | ❌ |
| 每类至少 30 条真实抽样 | 咨询类只做了 8 条 | ❌（仅完成要求的 8.9%） |
| 人工抽检「可用」占比 ≥ 85% | 作者本人自评 7/8 = 87.5% | ❌（不是独立抽检） |
| 对照「仅截断首句」基线 | 未设置任何对照 | ❌ |
| —（隐含的可信度要求） | 未做双人盲评 | ❌ |

二、核心问题（按严重程度排序）

1. 结论严重夸大，每一个关键词都站不住

报告结论写的是 " 充分证明本方案在全部工单类型上均显著优于现有做法，具备全面推广条件 "—— 但数据只覆盖了咨询类 8 条自评，投诉和催办一条都没测，对照一条都没跑。这个结论和证据之间是断裂的。

2. 87.5% 这个数字没有统计意义

8 条样本里 1 条的判断变化，就能让可用率从 87.5% 掉到 75%。在这么小的样本上谈 "超过 85% 及格线" 没有意义，及格线的前提是有足够样本量支撑。

3. 自评代替独立抽检，存在明显利益冲突

方案写的是 "人工抽检"，通常意味着由非作者、不知情的人独立判断。报告里是作者本人生成、本人判断可用不可用，这等于自己给自己改卷，结果不能采信。

4. 没有基线对照，"优于现有做法" 是空话

方案明确要求对照 "仅截断首句"。没有对照，你连模型摘要是不是比直接截首句好都不知道，更谈不上 "显著优于"。

三、结论

不能说预实验过了。 严格来说，这甚至不能算一次完成了方案要求的预实验 —— 它更像是作者拿 8 条咨询工单做的一次自测草稿。87.5% 这个数在数学上碰巧超过了 85%，但在样本量、评估独立性、场景覆盖、对照设计四个维度上全部不满足方案前提，这个通过率不能作为通过依据。

四、建议

如果要让这份报告能支撑 "预实验过了" 的结论，至少需要补齐：

补样本：咨询 / 投诉 / 催办每类补到 ≥30 条，合计 ≥90 条

补对照：同样本跑一遍 "仅截断首句"，并排对比可用率

改评估：找至少 2 名非作者做独立盲评，标注分歧并仲裁

改结论措辞：数据覆盖到哪、结论就说到哪，不要从 8 条咨询跳到 "全部工单类型全面推广"

需要的话，我可以帮你列一份预实验补做清单或合格报告模板，你直接甩给同事按这个改。

##### S5（附件：演示口径与定性访谈印证）

第五份报告是五份里逻辑最危险的一份—— 它不是简单的数据不达标，而是试图用 "共识口径"" 整体叙事 " 来消解数字指标本身的意义。结论：绝对不能据此说预实验过了。

一、逐项对比

| 方案要求 | 第 5 份报告实际 | 是否达标 |
|----------|-----------------|----------|
| 覆盖 3 类场景 | 只做了咨询 1 类量化；投诉 / 催办各访谈 2 人 | ❌ |
| 每类至少 30 条 | 咨询只做了 28 条 | ❌ |
| 人工抽检「可用」≥ 85% | 严格口径 64%；换 "演示可用" 口径 93% | ❌（严格口径不达标） |
| 对照「仅截断首句」基线 | 完全未提及 | ❌ |
| 评估方式 | 未说明是否盲评；投诉 / 催办靠 4 人主观访谈 | ❌ |

二、四个核心问题

1. 擅自变更方案，用 "团队共识" 一笔带过

报告说 "落地时团队达成共识：先把咨询打磨到可演示，其余场景用定性访谈覆盖，避免数字绑架创新"。

问题在于：方案原定的是三类场景各 30 条量化评估，这是一个明确的验收标准。如果要改方案，应该在实验前正式变更、记录审批理由，而不是在报告里用 "团队达成共识" 一句话带过，然后按改后的标准宣布达标。

更关键的是，"避免数字绑架创新" 这个说法本身就有问题 —— 预实验的目的就是用数字验证是否达标，绕开数字等于取消了预实验的验收作用。

2. 双重口径：严格口径不达标就换 "演示可用"

严格「可用」口径：64%（不达标）

「演示可用」口径（允许小瑕疵）：93%（达标）

这和第 2 份的 "放宽可用口径" 是同一个套路 —— 标准是死的，改标准让数字过线。而且 "演示可用" 是什么？允许多少小瑕疵？谁来判定小瑕疵？这些都没有定义。

如果 "演示可用" 的意思是 "demo 时挑好的展示"，那这个 93% 完全没有验收价值。

3. 定性访谈样本极小，标准极低

投诉、催办各访谈 2 名同学，一共 4 个人，反馈是 "比没有摘要强"。

两个问题：

样本量：4 个人的主观反馈能代表两类场景的质量吗？

标准：方案的及格线是 "可用率 ≥85%"，不是 "比没有摘要强"。"比没有强" 是一个极低的标准 —— 随便截首句也比没有强，但这不代表达到了可用标准。

4. 用 "整体叙事" 代替数据验收

报告结论写："数字上的 64% 不应被孤立解读，而应放在整体叙事中理解。"

这是最危险的一句话。64% 就是 64%，不达标就是不达标。如果接受了 "数字应放在整体叙事中理解" 这个逻辑，那以后任何预实验都可以用 "整体来看是好的" 来宣布通过，数字指标就完全失去了约束作用。

预实验的意义就在于：在投入更多资源之前，用可量化的标准做一次硬验收。如果验收标准可以被 "叙事" 消解，那预实验就白做了。

三、五份报告横向总览

| 维度 | 第 1 份 | 第 2 份 | 第 3 份 | 第 4 份 | 第 5 份 |
|------|---------|---------|---------|---------|---------|
| 稿件编号 | 第 4 稿 | 第 3 稿 | 第 1 稿 | 第 2 稿 | 第 5 稿 |
| 样本量 | 8 条 | 60 条 | 93 条 | 93 条 | 28 条 + 4 人访谈 |
| 场景覆盖 | 1 类 | 2 类 | 3 类 | 3 类 | 1 类量化 |
| 评估方式 | 作者自评 | 未说明 | 双人盲评 + 裁定 | 未说明 | 未说明 + 访谈 |
| 口径一致性 | 未说明 | 擅自放宽 | 未改动 | 未改动 | 双重口径 |

四、一个更重要的系统性问题

五份报告看下来，有一个比单份报告合格与否更关键的问题："可用" 的定义从来没有被统一过。

第 1 份：作者自评，不知道按什么标准

第 2 份："基本能看懂大意即算可用"

第 3 份：双人盲评，但没写具体判定标准

第 4 份：未说明

第 5 份：严格口径 vs 演示可用口径，两个都没精确定义

这导致五份报告的可用率数字完全不可比 ——87.5%、90%、88%、58%、64%，这些数字可能根本不是在衡量同一件事。如果 "可用" 没有一个统一的、可操作的定义，那所有的可用率数字都没有验收价值。

五、最终建议

第 5 份直接打回，不接受 "共识口径"" 整体叙事 " 这类消解指标的说法

以第 3 份为基准：它是唯一一份在方法上合规的报告（三类覆盖、样本达标、双人盲评、基线对照、结论克制）

但第 3 份和第 4 份的数据差异需要解释：同样是三类场景、各 30 条、都有基线，为什么一份 86-88%、一份 55-61%？必须让同事说明这两份的 "可用" 判定标准是否一致、样本是否同一批、评估人员是否同一组

先统一 "可用" 的操作定义，再做任何后续评估。建议写清楚：

可用 = 摘要包含工单核心信息（用户诉求、关键事实、处理状态），且无事实错误，可直接用于工单流转，无需人工大幅改写

不可用 = 遗漏关键信息、有事实错误、或需要人工重写超过 30% 内容

统一标准后，以第 3 份的方法（双人盲评 + 基线对照）重跑一次，三类各 30+ 条，看严格口径下是否真的 ≥85%

简单说：第 3 份是唯一一份方法上站得住的，但它和第 4 份的数据矛盾需要先查清楚；在统一 "可用" 定义之前，不要相信任何一份报告的可用率数字。

## 9. L2 特化 skill · 设计备忘（已记录，待开工）

> 本节不是本轮 L1 对照实验的一部分；防止后续把「复现验真」错做成通用 L1 或漏做特化。

### 9.1 目标

在用户提交的 POC / 预实验材料里出现**可跟走的取数或实验说明**时，海豚：

1. **先判可操作性**（自己能否按说明获得与报告同口径的数据）；  
2. 能 → **重复实验 / 复现取数**，核对报告中的数字与结论是否站得住；  
3. 不能 → **fail closed 声明 L2 不适用**，列出缺口（缺环境、缺数据权限、步骤不可执行、只有结论没有方法等）。

### 9.2 触发关键词（加载闸门草案）

**正例方向（出现则倾向加载 L2 skill）：**

- 「实验方法」「数据来源」  
- 近义 / 更贴近取数说明的表述（草案，施工时收进 skill `description` / 加载规则）：复现步骤、评测协议、怎么跑、命令/脚本、数据集与抽样、标注流程、指标定义与计算、环境依赖、对照怎么设等  

**刻意为之：** 闸门盯的是「海豚能否读到**数据怎么来的**」，不是「文档标题是否叫 POC」。只有结论表、没有方法 → **不触发 L2**（可仍走 L1）。
