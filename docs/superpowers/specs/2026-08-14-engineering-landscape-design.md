# psi-agent 工程全景图

**日期**: 2026-08-14
**状态**: 讨论稿
**背景**: 真知智能阶段一"验证技术闭环"。psi-agent 是公司第一个商业化产品的工程骨架，当前通过 haiTun Agent 在内部做 AI Native 化，验证 LLM + LOM + Harness 这条路是否走得通。
**"工程"的定义**: 改动成本随时间的斜率。杠杆是基础设施、架构、工程卫生；斜率是度量。今天加一个渠道要 3 天，半年后还是 3 天，工程就是好的。

---

## 一、结论先行

**1. "骨架已搭好，器官待生长"这个自我判断是准确的。**
内核 16.8k LOC 的模块边界（ai / channel / gateway / router / session）清楚，`protocol.py` 181 行的 SSE 契约是平台中立的。这两条是后面所有扩展的地基，质量合格。

**2. 产品四象限里只有一个是完整的。**
B 端有定制面但没有多租户（无租户模型、无权限、无隔离）；C 端 PC 完整（Web + 桌面壳 + 安装包 + 自动更新）；C 端移动端为零；LOM 为零。

**3. 最大的工程缺口不在代码，在"机器产物的准入"。**
差异化是"越用越聪明"。但系统往仓库写东西时**没有闸门**（`ToolRegistry.refresh()` 吞异常继续跑）、写完**没有验证**（机器产物落在 CI 不管的区域）、生效后**没有反馈**（无 metrics / tracing）。三者都缺，所以"越用越聪明"目前只能是信念，不能是可验证的事实。

**4. 一句话概括工程现状**: 写代码和写测试的能力是健康的，让它们生效的回路是残缺的。

## 二、产品顶层架构

```
真知智能 · 融合智能（远期 ASI，符号系统 Scaling Law）
│
├── LOM（知识方程 / 遗忘公理）    ← 近期接入 · 当前为零
├── LLM（any-llm-sdk 多模型）      ← 已通
└── Harness（psi-agent）           ← 本项目
    │
    ├── B 端：无统一形态，按客户需求定制
    │   ├── 定制面  = workspace 目录（tools / skills / systems / config / triggers / schedules）
    │   ├── 样板    = haitun-workspace（95.4k LOC，公司内部行政/人事/SOP）
    │   ├── 基础框架 = 内核 src/psi_agent（16.8k LOC）
    │   └── 缺       : 租户模型 / 权限 / 隔离 / 交付流程 / 定制脚手架
    │
    └── C 端（暗线）
        ├── PC
        │   ├── Web Server = gateway（6.1k）+ spa-v2（13.7k）  ← 当前入口
        │   ├── 桌面壳     = pywebview 109 行 + pystray 100 行
        │   ├── 账号       = 代理到 account.genuineknowledge.cn（10 条 /auth/*）
        │   ├── 分发       = Inno Setup + 阿里云 OSS + version.txt 比对更新
        │   └── 多平台应用 = 未来方向 · 当前仅 Windows
        └── 移动端
            ├── 小程序（计划）  ← 为零
            └── APP（计划）      ← 为零
```

## 三、工程全景图：做了哪些、做得怎么样、还要做什么

评级标准：**A** 可依赖，可以在上面盖楼 · **B** 能用，有已知短板 · **C** 有雏形，撑不住下一阶段 · **D** 基本为零

### 3.1 内核 / 基础框架

| 部件 | 规模 | 评级 | 做得怎么样 | 还要做什么 |
|---|---|---|---|---|
| 模块边界 | 5 模块 16.8k | **A** | ai / channel / gateway / router / session 职责清楚，各带 AGENTS.md | 维持 |
| SSE 协议契约 | `protocol.py` 181 行 | **A** | OpenAI 兼容，平台中立；辅助帧规则刚从 5 份副本收敛到 1 处（#664） | 无 —— 这是移动端能复用的关键资产 |
| Router | 2.2k | **A-** | routing / aggregation / fallback 三种上游可组合（#625） | 无紧急 |
| Session | 4.0k | **B+** | tool / trigger / schedule 三类注册表 + 热加载 `refresh()` | 见 3.4 准入层 |
| Channel | 3.5k | **B** | cli / repl / feishu / telegram；feishu 最重（940 行 client） | 新渠道接入成本待验证 |
| Gateway | 6.1k | **B-** | 20+ manager 模块，职责分得开；但 `server.py` 959 行、`_openapi.py` 899 行偏重 | 拆分这两个文件 |
| 传输层 | `_sockets.py` | **A** | 默认 Unix socket / 命名管道（本机），显式给 URL 才 TCP —— 默认不暴露网络，安全姿态正确 | 移动端要连时需设计鉴权，见 3.3 |

### 3.2 B 端

| 部件 | 评级 | 做得怎么样 | 还要做什么 |
|---|---|---|---|
| 定制机制 | **B** | workspace 目录即定制面，不改内核就能换一套业务，机制本身是对的 | 沉淀成脚手架，而非拷贝 haitun |
| 样板实现 | **B+** | haitun 95.4k LOC（tools 45.4k / skills 35.5k / tests 29.7k），真实业务跑着 | 提炼哪些是通用能力、哪些是海豚专有 |
| 租户模型 | **D** | 无租户概念 | 客户从 1 到 2 时必须先有 |
| 权限 / 隔离 | **D** | 无 | 同上 |
| 定制交付流程 | **D** | 无文档化流程 | 新客户接入 SOP |
| B 端可观测 | **D** | 无 | 客户现场故障目前无法远程定位 |

### 3.3 C 端

| 部件 | 评级 | 做得怎么样 | 还要做什么 |
|---|---|---|---|
| PC Web（spa-v2） | **B+** | React + Vite，services 层抽得干净（api / sse / chatStream 分离），35 个 service 模块 | 见 3.4 门禁 |

### 3.4 验证 / 卫生（斜率的核心）

| 部件 | 现状 | 评级 | 问题 |
|---|---|---|---|
| 测试编写量 | 内核 22.3k + haitun 29.7k + 其余 examples，共 50k+ LOC | **A** | 写得足够多 |
| 内核测试执行 | `testpaths = ["tests"]` 全跑，17 个集成测试 | **A-** | 正常 |
| haitun 测试执行 | 66 文件 29.7k LOC 中，进门禁的只有 `tests/integration/` 下 491 LOC = **1.6%** | **D** | 改坏 haitun tools，CI 是绿的 |
| 前端测试执行 | 10 个 vitest 文件，`test: vitest run` 已配 | **D** | CI 里 grep 不到任何调用，零执行 |
| 前端构建门禁 | 只在打 tag 时 `npm run build` | **C** | PR 阶段前端连编都不编 |
| Lint / 类型 | ruff（13 类规则）+ ty 全量 | **A** | 正常 |
| 覆盖率 | `--cov` 已配 | **C** | 无阈值、无上报，等于没有 |
| 机器产物准入 | 无 | **D** | 见 3.5 |

### 3.5 机器产物准入（自进化的前提）

| 环节 | 现状 | 评级 |
|---|---|---|
| 热加载机制 | `ToolRegistry.refresh()` 支持 added / updated / removed / skipped 增量重载 | **B+** 机制在 |
| 写入闸门 | 无。`refresh()` 失败时 `except Exception: logger.warning(...)` 吞掉继续跑 | **D** |
| 写入后验证 | 无。机器产物落在 `examples/haitun-workspace/`，CI 覆盖 1.6% | **D** |
| 生效后反馈 | 无。`_logging.py` 36 行，无 metrics / tracing / error-tracking 依赖 | **D** |
| 回退能力 | 无 | **D** |

内核里 147 处 `except Exception`、其中 65 处后接 `logger.warning/debug` 或 `pass`。在内核的健壮性设计里这是合理的；**但在机器产物的加载路径上，吞异常等于放行坏产物**。

## 四、缺口归因

3.4、3.5、3.6 的可观测性看起来是三件事，其实是同一个结构缺失的三个切面：

> **系统能自己往仓库里写东西，但仓库没有"接收"这个动作的概念。**

- **闸门**（准入）= 写入时不检查
- **验证**（门禁）= 写入后不跑测试
- **反馈**（可观测）= 生效后不度量

近期 LOM 接入后，知识会自动增长和淘汰，写入量再上一个台阶。**现在这套缺三环的结构会成为主要风险源**，而且是那种"出了问题查不出来"的风险。

另一类缺口性质完全不同 —— B 端租户 / C 端移动端 / 多平台 PC 是**未开工**，不是欠债。它们不影响当前斜率，影响的是能不能开新战场。

## 五、优先级建议

| 优先级 | 事项 | 为什么这个顺序 |
|---|---|---|
| P0 | 门禁补全：haitun 29.7k 测试进 CI、前端 vitest 进 CI、PR 阶段编前端 | 成本最低、当天见效。是 P1 的前提 —— 没有能跑的测试，准入层无从判断"合格" |
| P0 | 覆盖率设阈值 + 上报 | 同上，几行配置 |
| P1 | 机器产物准入层 | 直接服务 LOM 接入。设计：机器写的 tool/skill/知识过什么门才生效、坏了怎么回退、`refresh()` 不再静默吞异常 |
| P1 | 最小可观测性 | 让"闭环跑通"从人工判断变成可累积的量化证据。阶段一的交付物本身需要它 |
| P2 | haitun 定位与边界理清 | 它是阶段一的证据本身，不是 example。目录名、依赖方向、通用能力提炼 |
| P2 | 收敛重复维护面 | spa 下线时间、三条构建路径定主路径 |
| P2 | gateway 拆分 | `server.py` 959 行、`_openapi.py` 899 行 |
| P3 | B 端租户 / 权限 / 隔离 | 客户从 1 到 2 时的前置条件。To B 暂无外部客户，可等 |
| P3 | C 端移动端 | 前置条件是 gateway 远程 API + 鉴权设计。SSE 协议已中立，这块资产可直接复用 |
| P3 | 多平台 PC 打包 | 桌面壳只 209 行，迁移成本不高 |

**取舍说明**: P0 和 P1 是"压斜率"，P2 是"止血"，P3 是"开战场"。当前处在阶段一，斜率优先于战场 —— 因为阶段一的产出物是"这条路走得通"这个结论，而结论的可信度直接由验证回路的完整性决定。

## 六、待确认

1. LOM 接入的时间表 —— 决定 P1 准入层的紧迫程度
2. 三组（入口 / 本体 / Agent）独立运作下，psi-agent 的人力实况 —— 决定 P0/P1 能否并行
3. C 端移动端是否有对外时间承诺 —— 若有，P3 需上提，且要先做 gateway 远程 API 的鉴权设计
4. haitun 是否计划拆仓 —— 影响 P2 的做法
