## 一、结论先行

**本节是全文摘要。只读这一节就够拿到全部结论，后面各章是证据和做法。**

### 一句话

造东西的能力是健康的，**让东西生效、让状态可见的机制是残缺的**。工程效率的下降主要来自后者，不是来自代码质量。

### 四条结论

**1. 造的能力好，验的能力缺。**〔实测〕内核 17595 行，覆盖率 **80%**，全仓只有 2 处"忽略检查"标记，近 100 次合并 100% 走评审。这几个数字放任何团队都算优秀。但占仓库 **84%** 的产品代码没有任何自动检查，生产上跑的是哪个版本查不出来，C 端用户用得怎么样完全不知道。

**2. 仓库不知道自己的状态。** 每次改动前要人工确认的事越来越多——这版含什么改动？生产跑哪个版本？三份能力包一样吗？改这里会不会影响 C 端？全靠人查、人记。

**3. 内核与业务的边界反了。** 内核认识业务（10 个文件写死 "haitun"），业务却接不牢内核（6 个挂钩靠函数名对上，拼错了静默跳过）。**代价现在就在付**：ToC 用户装的是 ToB 的交付物，桌面目录名改不动。

**4. 一个数字概括**：4416 条自动测试，**2958 条永远不会被执行**——占三分之二。

### 八个问题，按严重度

| # | 问题 | 一句话 | 修法 |
|---|---|---|---|
| 1 | 挂钩静默失效 | 6 个 hook 拼错名字照常运行，功能悄悄消失 | 业务层显式声明清单，声明了接不上就启动失败 |
| 2 | 内核写死业务名 | 10 个文件含 "haitun"，含 C 端桌面目录名 | 分三类：内部标记改中性、探测路径改配置、用户可见的单独立项 |
| 3 | 机器产物无门 | 机器写的代码加载失败只记日志，没人会发现 | 先只做"可见"（`/health` 能查失败项），准入机制暂不做 |
| 4 | 三分之二测试不跑 | 2958 条 haitun 测试 + 29 个前端测试文件 CI 一条不跑 | 接进 CI，覆盖率设下限 `fail_under` |
| 5 | 仓库不知自己状态 | `--version` 不可用；一份能力包已落后 7 天无人知 | 版本可查 + 能力包同源校验 |
| 6 | 生产跑挂载源码 | 不是装包，是挂 `/app/src`，会漂 | 改装包，或把三层核验固化进 CI |
| 7 | 重复维护面 | 两套前端、三条打包路径、C 端无回滚预案 | 定主路径，补回滚预案 |
| 8 | 可观测性为零 | 无指标无追踪；服务器只剩 2.6G 内存，塞不下监控套件 | 日志轮转 + 结构化落关键指标 + C 端最小遥测 |

问题 1-3 是内核边界与耦合，也是下面两个拆分的**前置条件**。

### 两个拆分的评估结论

方向都对，切法都要改。判据一条：**这里出现差异，你想不想要？**产品线本就该分化（想要），设施不该分化（不想要）。

**拆 gateway**〔实测〕按 54 条路由归属判定，而不是按"文件里有没有 feishu 字样"——后者会把 ToC 专有件误判成通用件：

| 归属 | 行数 |
|---|---|
| ToC 专有（`/spa*` `/ui/*` `/workspace/places` 等） | 617 |
| **ToB 专有**（`/feishu/route` `/feishu/routes`） | **269** |
| 共用（`/sessions*` `/ais*` `/auth/*` 等） | 2470 |

交接清单要在新 ToB gateway 保留 19 个文件，真正属于 ToB 的约 **269 行**，复制比约 **9:1**，且复制物里混着 ToC 专有死码。**建议三层**（`_common/` + `toc/` + `tob/`），不是两份。

**拆 workspace**〔实测〕ToC 现在**没有自己的 workspace，装的就是 haitun-workspace**（`_defaults.py:115-118` 注释原文）。难点不在数量大的那层：tools（149 个 py）和 skills（145 个目录）是一能力一文件，好切；**systems 9 个文件 5444 行是按行混入的**，工作量集中在此，按文件数估工期会严重低估。

**基础版要定义成模板，不是共享库**：三份（模板 / ToC / haitun），不是两份。模板由内核 6 个 hook 契约定义，不是"haitun 减掉业务"——否则 haitun 每次演进模板就落后一次。

### 顺序

```
阶段一 让仓库能自我陈述 → 阶段二 内核边界加固（问题 1-3）
                              ↓ 必须先做
                         阶段四 两个拆分
```

拆分会**新增副本**（一份变多份），而仓库现在没有任何检测副本漂移的手段——一份能力包落后 7 天，是手工算哈希才发现的。**所以阶段一的同源校验、阶段二的挂钩反馈是拆分的前置条件，不是可选项。**

### 需要拍板的两件事

1. **交接清单里的 feishu_gateway 代码在哪**——本仓库 635 个远程分支、全部历史提交都没有该目录，"拆分完成"无从验证
2. **基础版 workspace 是模板还是共享库**——决定它要不要持续同步，两种做法工作量和风险完全不同

> **一条基线事实**〔实测〕：Windows 上跑内核全量是 **57 failed / 1394 passed**。这 57 条是 asyncio 子进程的固有限制，**是基线不是回归**，CI 在 Linux 上不受影响。但本机开发者因此无法用"全绿"当判断标准，这是个隐性成本。

### 问题 1：内核给业务预留的挂钩，接错了不会报错

**这是什么**〔实测〕

内核允许业务层（workspace）提供 6 个函数来定制行为，比如"怎么生成系统提示词"、"每轮对话前要不要注入点东西"、"历史太长了怎么压缩"。这就是"设备"给"菜谱"留的接口。

内核找这些函数的方式是：**按名字去找。找到了就用，找不到就当没有，继续正常运行。**

代码在 `src/psi_agent/session/system_prompt.py:258`（`_extract_async_func`）：

```python
def _extract_async_func(module, name):
    func = getattr(module, name, None)
    if func is None or not inspect.iscoroutinefunction(func):
        return None      # ← 找不到，静默返回"没有"
    return func
```

六个名字分别是 `system_prompt_builder`、`system_prompt_rebuild_checker`、`compact_history`、`turn_context_builder`、`system_before_turn`、`system_after_turn`。

**为什么要紧**

把 `turn_context_builder` 拼错成 `turn_context_bulider`，agent 会**完全正常地运行**，只是从此再也不知道当前时间。没有报错、没有警告、日志里也没有异常。要等到有人发现"agent 怎么老是搞错日期"才会去查。

这 6 个挂钩是**内核对外的全部扩展面**——业务层想加任何能力都得从这里进，记忆能力（2389 行）就是走这条路。也就是说：仓库 84% 的产品代码，接入方式是"名字拼对了就生效，拼错了就静默消失"。

**拆 workspace 后会立刻变严重**：一份变多份，每份都要自己接对 6 个名字。现在靠"只有一份、人记得住"兜着，拆完兜不住。

同一模式在别处也有。`ensure()` 构建提示词失败时（`system_prompt.py:115-117`）：

```python
except Exception as e:
    logger.error(f"Failed to build system prompt: {e}")
    # 然后就继续跑了，系统提示词是空的
```

系统提示词是 agent 的全部行为准则。它构建失败后 agent 会**带着空白准则继续服务用户**。

**怎么修**〔推断，可以不同意〕

不是把所有静默都改成崩溃——内核对业务代码的容错本身是对的设计。要区分两类：

- **可选能力**：没有就没有，静默跳过是合理的（比如注入当前时间）
- **声明了的能力**：业务层明确说"我要提供知识检索"，那么加载失败就必须报错，不能装作没这回事

做法是让业务层**显式声明**自己提供哪些挂钩（比如在 workspace 放一个清单文件），内核按清单核对：清单里写了但找不到 → 启动失败并说清是哪个名字对不上；清单里没写 → 正常跳过。

这样"拼错名字"从"永远查不出来"变成"启动就告诉你"。

配套改一处：挂钩加载成功后记一条日志，说明哪几个接上了。现在成功是无声的，只有失败才有日志，导致"没接上"和"接上了但没触发"从日志上无法区分。

### 问题 2：内核里写死了业务名字，散在 10 个文件

**这是什么**〔实测 @ main b1bbad23〕

"haitun" 在内核里出现 **26 次 / 10 个文件**（含注释）。集中在 `gateway/_defaults.py`(10)、`gateway/__init__.py`(3)、`session/event_protocol.py`(3)，其余 7 个文件各 1-2 次。真正影响行为的四处：

| 位置 | 内容 | 性质 |
|---|---|---|
| `gateway/_defaults.py:54` | `DEFAULT_USER_WORKSPACE_NAME = "haitun交付"` | **C 端用户桌面上的文件夹名** |
| `gateway/_defaults.py:112` | 写死去找 `examples/haitun-workspace` | 探测路径 |
| `gateway/_free_model.py:19` | `PLACEHOLDER_API_KEY = "haitun-default"` | 内部标记，与前端同契约 |
| `session/event_protocol.py:22` | `SOURCE_HAITUN = "haitun"` | 事件来源标记 |

另外，飞书在 `channel/feishu/` 之外的 **22 个内核文件**里出现。

> 本文早期版本写"19 处"，该数字口径不明、无法复现，已更正。**排期按文件数 10，不是处数 26**——同文件多处通常一次改完。

**为什么要紧**

设备说明书写着"适用任何菜系"，但设备内部有根线刻着"川菜专用"。

三个具体后果：

1. **微内核的承诺已经破了。** `AGENTS.md` 写"不改内核就能换一套业务"，实际换业务要改内核。第二个 ToB 客户进来时，这 10 个文件是必须现改的地方。

2. **一笔只会越来越贵的债。** `haitun交付` 是 C 端用户桌面目录名。现在改名会让已装机用户的目录失效，而 C 端用户还在增长。

3. **ToC 侧没有自己的默认值可填。** `_defaults.py:115-118` 注释原文：Windows 安装布局下"`{app}` 就是 haitun-workspace"。ToC 发出去的就是 ToB 的交付物。目录名改不动的根子不是配置写错，而是 ToC 侧不存在一个属于自己的 workspace 可指向（详见第五章）。

**值得肯定的一点**：内核对 fusion-memory 的引用是 **0 处**，记忆能力（2389 行 / 10 个文件）完全长在 workspace 侧走挂钩接入。**这证明分层本身是成立的**，问题不在设计，在通道缺反馈（问题 1）和这 10 个文件的例外。清理目标就是让 haitun 变得和 fusion-memory 一样：内核完全不认识它。

**怎么修**〔推断，可以不同意〕

分三类处理，不要一刀切：

- **纯内部标记**（如 `"haitun-default"`、`SOURCE_HAITUN`）：改成中性名字，或改成从配置读。改动小，无外部影响。
- **探测路径**（如去找 `examples/haitun-workspace`）：改成从配置文件读一个"默认业务包路径"，业务名字不进代码。
- **已经暴露给用户的**（如 `haitun交付` 目录名）：**不能直接改**。需要单独设计：新装用户用新名字，老用户保持原样并在若干版本后引导迁移。这一条要单独立项，不要混在清理里做。

### 问题 3：机器自己写的代码，进系统没有门

**这是什么**〔实测〕

系统能自己往仓库写新能力（新 tool），内核支持热加载。但加载失败时的处理是（`session/tool_registry.py:504-510`）：

```python
except Exception as e:
    logger.error(f"Failed to load tool file {py_file!r}: {e!r}")
    continue      # ← 记一行日志，跳过这个文件，继续
```

**为什么要紧**

关键区别：**人写的**代码加载失败，记日志跳过是对的——人会看日志、会发现、会修。**机器写的**代码加载失败，等于这个能力悄悄不存在了，而且没有人"记得"自己写过它。

系统能往仓库写东西，但仓库**没有"接收"这个动作的概念**。缺四样：

| 环节 | 现状 |
|---|---|
| 写入时检查（闸门） | 无。写进去就算成功 |
| 写入后验证（门禁） | 无。机器产物落在 CI 完全不管的目录（见问题 4） |
| 生效后反馈（度量） | 无。不知道新能力被用了几次、成功率多少 |
| 出错后回退 | 无预案 |

这件事和前两个问题是同一个病：**内核对业务层的一切失败都选择静默**。挂钩接不上静默、提示词构建失败静默、工具加载失败静默。单独看每一处都是"合理的容错"，合起来看是**系统没有任何办法陈述自己少了什么**。

**怎么修**〔推断，可以不同意〕

先做最便宜的一半——**把静默变成可见**：

- 机器产物加载失败时，不只记日志，还要能被查询（比如 `/health` 里报"有 N 个能力加载失败，分别是哪些"）
- 加载成功也记一条，让"从没加载过"和"加载了但没用上"能区分开

准入设计（什么样的机器产物才允许生效、坏了怎么退回上一版）**建议暂不做**。理由：当前机器写入量不大，而准入机制本身会成为新的设计债——门定严了挡住正常迭代，定松了等于没有。先把上面"可见"这一半做掉，攒够"哪些产物真的坏过"的实际数据，再决定门要开多大。

### 问题 4：三分之二的测试永远不会跑

**这是什么**〔实测〕

4416 条测试，CI 只跑 1458 条。剩下 **2958 条属于 haitun 产品本体，一条都不跑**。原因是 `pyproject.toml` 里一行配置：

```toml
testpaths = ["tests"]
```

haitun 的 65 个测试文件在 `examples/haitun-workspace/tests/`，不在这个范围。前端同理：两套前端 29 个测试文件，`package.json` 配了 `"test": "vitest run"`，但 CI 里没有任何地方调用它。

**为什么要紧**

**占仓库 84% 的代码改坏了，CI 是绿的。** 唯一的真实产品级验证资产，同时也是唯一不被执行的——测试写了、钱付了，只是没收货。

**怎么修**〔推断，可以不同意〕

这是本文里最便宜的一条，改几行配置：

- CI 增加一步，跑 haitun 那 2958 条测试。注意本地跑的时候有个坑：命令行给的路径会被 `testpaths` 静默覆盖，必须写成 `pytest -o testpaths= <路径>`，且 `-o` 要在路径**前面**，否则会静默跑成全量（这个坑已经踩过，见团队记录）
- CI 增加两步，分别跑两套前端的测试
- 如果这 2958 条里有当前跑不过的，**不要跳过它们**，而是先记录当前实际通过数作为基线，然后逐条修。跳过等于回到现在的状态

顺带把覆盖率钉住：现在配了统计但没设下限，所以 80% 只是"今天的事实"，不是"守住的承诺"。设 `fail_under = 78`（留 2 个点余量），掉下去 CI 就红。

### 问题 5：仓库不知道自己的状态

**这是什么**〔实测〕

这是把前面几轮排查中反复撞到的同一堵墙集中起来说。以下每一条我都实际试过：

| 想知道的事 | 现在怎么查 |
|---|---|
| 生产上跑的是哪个版本？ | 查不到。`psi-agent --version` 不是合法参数 |
| 三份能力包是否一致？ | 只能手工 ssh 上去逐文件算哈希 |
| C 端用户装的什么版本、用得怎么样、报了什么错？ | 完全不知道，一片黑 |
| 覆盖率有没有掉？ | 没有下限，掉了不会有人知道 |
| 当前 C 端版本包含哪些改动？ | 答不出来（27 个本地分支 26 个未合并） |
| 文档和代码是否还对得上？ | 靠人守。gateway 的 AGENTS.md 与代码已经差 7 天 |

**我用手工核查发现的一件事**：三份能力包里，有一份**已经落后 7 天**。

| 容器 | 能力文件数 | 内容哈希 | 最后更新 |
|---|---|---|---|
| 主容器 | 187 | `73c7e9…` | 08-15 |
| chengxx | 187 | `73c7e9…` | 08-15 |
| **luolin** | **181** | `318b08…` | **08-08** |

luolin 那份缺 6 个文件，另有 17 个文件内容不同，包括 `browser.py`、`search.py`、`memory_search.py` 这些核心能力。

**为什么要紧**

落后本身可能是有意的（也许他需要稳定版本），但**没有任何机制会告诉我们**——我是手工算哈希才发现的。后果很具体：luolin 报一个问题，我们对着最新代码排查，查不出来，因为他跑的是 8 月 8 号的版本。

ToC 侧更严重：**有真实用户，我们对他们的运行状况一无所知**，出了问题可能一周都不知道。

这是本文认为的**根本问题**。工程效率是"改动成本随时间的斜率"，斜率变陡不是因为代码变差——代码指标都健康——而是**每次改动前需要人工确认的事在变多**。

**怎么修**〔推断，可以不同意〕

按"让系统自己说"的原则，逐条消除人工核查：

1. **版本可查**：`psi-agent --version` 能用，输出版本号 + git 提交号。构建时注入，运行时可查。这是所有其他排查的前提
2. **能力包同源校验**：一个脚本算能力包哈希，各容器启动时上报或 CI 定期比对，不一致就告警。发现 luolin 漂移这件事应该是自动的，不该靠人 ssh
3. **覆盖率下限**：见问题 4
4. **分支清理**：27 个本地分支只留在用的。`chore/release-1.0.1/2/3` 这几个各只领先 1 个提交，烂在那没意义。`kanban/board` 落后 610 个提交
5. **仓库卫生**：根目录两个对话记录 txt 没进 `.gitignore`；`docs/haitun-delivery`（9 份）和 `docs/onboarding`（3 份，含两份 SOP）还没入 git，需要定去处
6. **提交模板加一行**："本次改动影响 ToC / ToB / 两者"。不是形式主义 —— 影响 ToC 的改动值得多花半天灰度，影响内部的可以直接上，而现在这个区分只在改动者脑子里

### 问题 6：生产上跑的代码会漂

**这是什么**〔实测〕

容器里的 psi-agent **不是安装好的软件包，而是直接挂载的源码目录**（实测位置 `/app/src/psi_agent/__init__.py`）。

**为什么要紧**

正常做法是打包 → 装进镜像 → 跑镜像里那份，镜像做好即固定。现在跑的是挂载进去的源码，**外面源码变了容器里跑的就变了**。这正是 8-18 那次事故的机制根源。团队后来加了"三层核验"防它，但那是靠人记得做的流程补丁，机制没变。

**怎么修**〔推断，可以不同意〕

根治是改成运行安装好的包，不挂载源码。若短期改不动（挂载可能是为了调试方便），退一步把三层核验固化进 CI 或发布脚本，让它不依赖人记得做——**但这只是缓解，不是修好。**

### 问题 7：重复维护面

**这是什么**〔实测〕

三处同时维护多套：

1. **两套前端**：spa（8763 行）和 spa-v2（13980 行）。近两个月两套都在改
2. **三条打包路径**：PyInstaller、Nuitka、OSS。上周三个配置都动过
3. **两处相似的隔离机制**：私密目录机制和独立容器机制，同时对同两个人生效，其中一个已经压过另一个（详见附录）

对比一个信号：三条打包配置上周都改了，而 CI 配置从 7-21 起没动过。**精力在发版机制上，不在验证机制上。**

**为什么要紧**

不影响正确性，纯粹是重复劳动——一个功能改两遍前端，一个打包问题在三处确认。ToC 侧最近的事故（功能整体回退、安装器父进程没关闭）都出在打包这层，三条路径并存就是三个可能出问题的地方。

**怎么修**〔推断，可以不同意〕

不需要设计，只需要拍板：

- spa 定一个下线日期，之后只修致命问题
- 三条打包路径定一条主路径，其余降级为实验或删除
- 隔离机制二选一，另一条清理掉（含遗留数据，详见附录）

### 问题 8：可观测性为零

**这是什么**〔实测〕

依赖清单里没有任何监控、追踪、错误上报组件。日志模块 `_logging.py` 只有 36 行。

结果是：所有生产问题排查靠人肉，产出是手写的 markdown。`docs/haitun-delivery/` 下 9 份交付文档、提交记录里"停机 68s""逐字节 100/100"这类数字，全是人工测量手工记录的。

**为什么要紧**

**查一次很贵，而且不累积**——下次同类问题还是从零查。更关键的是：内部提效是我们唯一的真实反馈回路（自己公司当第一个 ToB 客户，这个决策是对的），但这个回路现在**不产生可累积的数据**。

**怎么修**〔推断，可以不同意〕

**不要上完整监控套件** —— 那台服务器只剩 2.6G 可用内存，塞不下。从最便宜的做起：

1. **容器日志轮转**（现在没有，4.3 万行还在长，40G 盘已用 51%）。这是纯运维配置，当天可做
2. **落几个结构化数字**：每轮对话的 token 数、耗时、是否触发了历史压缩、工具调用成败。写进日志即可，不需要新组件
3. **C 端一条最小回路**：版本号 + 崩溃上报。这是唯一能让我们知道 C 端状况的东西
4. 顺带注意：现在日志里会打印 workspace 完整路径，私密目录路径会明文进日志。做隔离时文件系统层做了，日志层没做

## 五、双 gateway 与 workspace 拆分评估

---

团队近期方向。本节评估切法，不评估方向——方向是对的。

### 5.0 一条判据〔推断〕

拆分会产生副本。判断一个副本是否健康，只问一句：**这里出现差异，你想不想要？**

| 差异类型 | 例子 | 结论 |
|---|---|---|
| 想要 | ToB 有合同法务能力，ToC 没有 | 产品定义，越早分开越好 |
| 不想要 | ToC 修了历史截断 bug，ToB 没跟上 | 一个 bug 付两次钱，第二次没人记得付 |

产品线**本就该分化**，这不是问题。问题只在第二类。下面两个拆分，一个属于第一类，一个混了第二类。

### 5.1 拆 gateway：方向对，切法要改

**判定方法**〔实测〕：不能用"文件里有没有 feishu 字样"判断归属——一个文件零 feishu 引用，可能是通用设施，也可能是**ToC 专有**（因为它属于另一条产品线，自然不提飞书）。所以按**路由归属**判定：gateway 共 54 条路由，看每条路由服务谁。

| 归属 | 路由 | 承载文件 | 行数 |
|---|---|---|---|
| **ToC 专有** | `/spa*`（6 条）、`/ui/*`（3 条）、`/workspace/places`、`/browse`、`/reveal` | `_spa_shell` `_tray` `_webview` `_attention` `_ui_prefs` `_workspace_manager` | 617 |
| **ToB 专有** | `/feishu/route`、`/feishu/routes` | `_feishu_manager` + `server.py` 约 60 行 | 269 |
| **共用** | `/sessions*` `/ais*` `/routers*` `/auth/*` `/summaries` `/titles` `/defaults` 等 | `_session_manager` `_history_manager` `_todo_manager` `_ai_manager` `_router_manager` `_chat_manager` `_summary_manager` `_title_manager` `_auth_manager` `_auth_store` `_oauth_manager` `_state` `_manager` `_free_model` | 2470 |

`_workspace_manager.py`（185 行）是这次判定纠正出来的典型：它零 feishu 引用，但做的是**本机目录选择器**——枚举桌面、文档、下载、Windows 盘符（`_workspace_manager.py:74-84`），调用方是 `spa-v2/src/components/PathPickerDialog.tsx`。容器里的 ToB 用户没有桌面也没有 D 盘。**它是 ToC 专有，不是通用设施。**

**结论**：交接清单要在新 ToB gateway 保留的 19 个文件里，**真正属于 ToB 的约 269 行**，其余是共用设施和 ToC 专有件。复制比约 **9:1**，且复制物里混着一部分 ToC 专有代码——那部分进 ToB gateway 是纯死码。

**建议改成三层，而不是两份**：

```
gateway/_common/    ← 共用设施（约 2470 行），单一来源
gateway/toc/        ← ToC 专有（约 617 行）+ 前端壳
gateway/tob/        ← ToB 专有（约 269 行）
```

ToB gateway 会很薄。它本来就该很薄。

**这三个数字是按路由粗分的**〔实测 + 推断〕：路由归属是实测，但"哪些文件只服务这些路由"有交叉——`server.py`(1031 行) 和 `_openapi.py`(915 行) 三类都碰，没有计入上表，实际拆分时这两个大文件本身要先按路由切开。**所以 2470 / 617 / 269 是量级，不是可以直接排期的工作量。**

**另外三处不自洽**：

| 问题 | 事实 |
|---|---|
| 保留 `_spa_shell.py` 却删掉所有 `/spa` 路由 | 它的 4 个引用方是 `server.py`、`_tray.py`、`_webview.py`、`__init__.py`，后两个也在删除名单里。留着没有意义 |
| 保留 `_free_model.py`（哨兵 key `haitun-default`） | ToB 业务名字会同时长在两个 gateway 里。拆分本该是消除这种耦合的时机，方案却复制了它 |
| 验收标准第 7 条"原 gateway 不再包含飞书逻辑" | 做不到。feishu 出现在 `channel/feishu/` 之外的 **22 个内核文件**里。这条得改成可验证的说法，否则拆完无法验收 |

**一个必须先澄清的事实**〔实测〕：交接清单的验收标准写着拆分已完成、C 端已移除。核查结果——本仓库 **635 个远程分支、全部历史提交，没有任何一个包含 `src/psi_agent/feishu_gateway/`**；这份文档本身也未进主线，只出现在 kanban checkpoint 提交里。所以它目前只能当**设计意图**评审，不能当已交付成果验收。那些代码在哪，需要先确认。

### 5.2 拆 workspace：方向对，难点不在数量大的那一层

ToC 和 ToB 共用一个 workspace 确实是错的。而且比"共用"更准确的说法是——

**ToC 现在没有自己的 workspace，它装的就是 haitun-workspace。** `gateway/_defaults.py:115-118` 的原文注释：

```python
# Soft default for Windows install layout: {app} IS haitun-workspace
# (tools/ + skills/ at cwd; no examples/ nesting).
```

这也解释了问题 2 里那个改不动的桌面目录名：不是配置写错了，是 ToC 侧压根不存在属于自己的默认值可填。

**难度分布和直觉相反**（实测 951 个文件）：

| 层 | 规模 | 业务混入方式 | 难度 |
|---|---|---|---|
| tools | 149 个 `.py`，58 个提飞书 | 一能力一文件 | **易**，选或不选 |
| skills | 145 个能力目录 | 一能力一目录 | **易**，选或不选 |
| 根级 md | 8 个文件 1403 行 | 通用为主 | **易** |
| **systems** | **9 个文件 5444 行** | **按行混入，不按文件** | **难，工作量集中在此** |

systems 是 hook 层，业务是按行嵌进去的：

| 文件 | 行数 | 飞书引用 | haitun 引用 |
|---|---|---|---|
| `system.py` | 1756 | 0 | 10 |
| `prompt_sections.py` | 769 | 19 | 8 |
| `prompt_constants.py` | 478 | 7 | 1 |
| `curator.py` / `supervisor*.py` / `threat_patterns.py` | 2441 | 0 | 1 |

文件边界切不开前三个，必须逐行拆。**按文件数估工期会严重低估。**

### 5.3 基础版必须定义清楚：模板，不是共享库〔推断〕

如果两条产品线本就该各自演进，那"基础版"到底是什么？

| | 模板 | 共享库 |
|---|---|---|
| 同步 | 初始化拷一次，之后永不回头 | 持续同步，改一处两边变 |
| 类比 | `cargo new` | 依赖包 |

团队说的"起始形态"听着是模板。但同一句话里还说"也可直接作为 ToC 的 workspace"——**这两个身份冲突**。ToC 是活的产品，一定会长出自己的东西；那一刻要么基础版被迫吸收 ToC 业务（模板被污染），要么 ToC 从基础版分叉（那就不是"直接作为"）。

**建议：三份，不是两份。**

| 名称 | 身份 | 演进方式 |
|---|---|---|
| workspace 模板 | 任何新 workspace 的起点 | 只随 hook 契约变 |
| ToC workspace | 产品 | 从模板生成后独立演进 |
| haitun workspace | 产品 | 独立演进 |

**模板由内核的 hook 契约定义，不是由"haitun 减掉业务"定义。** 内容 = 那 6 个函数名的最小可用实现 + 根级 8 个 md。验收标准是"能空跑起来"。

这一条很关键：如果模板定义成 haitun 的差集，haitun 每次演进模板就落后一次——那才是真的漂移（5.0 表里的第二类）。定义成 hook 契约的实现，它压根不追 haitun。

### 5.4 顺序

```
阶段二（挂钩加反馈 + 清 10 个文件的业务名字）
   ↓ 必须先做
6.1 抽 _common/  ·  6.2+6.3 抽模板
   ↓
ToC workspace 从模板生成 → 桌面目录名才有得可改
```

两个拆分都**新增副本**，而仓库目前没有任何检测副本漂移的手段（问题 5：luolin 漂 7 天无人知，是手工算哈希才发现的）。阶段一的同源校验和阶段二的挂钩反馈都是拆分的前置条件，不是可选项。

## 附录：两套隔离机制的现状

这一节记录一个具体发现，供后续讨论隔离方案时参考。不属于本文主线。

生产上有两套并行的隔离机制，且**同时对同两个人生效**：

```
PSI_PRIVATE_OPEN_IDS        = ou_c77e…(luolin), ou_716d…(chengxx)
PSI_FEISHU_EXTERNAL_SESSIONS = ou_c77e…=http://psi-agent-luolin:8081,
                               ou_716d…=http://psi-agent-chengxx:8081
```

`_feishu_manager.py:162` 里，独立容器分支在私密目录逻辑**之前**就返回了。所以对这两个人，私密目录机制**根本执行不到**，已是死代码。

磁盘上的证据：`workspace/.private/ou_c77e…/` 有 57 个文件，最后写入 08-21（切容器的时间点），之后无人读写。两个独立容器的 workspace 里都没有 `.private` 目录。

**这份数据现在既不被读取，也没有迁移，仍在备份范围内** —— 涉及人事财务数据，需要明确处理。

两点供后续讨论：

- 隔离配置目前活在环境变量里，配错一个字符会**静默退回不隔离**（`external_sessions()` 的注释明确写了"解析失败的片段静默跳过"）。安全机制的默认值应该是拒绝而非放行
- 容器隔离与"自进化"存在结构性张力：自进化要求能力和知识能流动合并，容器隔离把流动切断了。luolin 分叉 7 天是这个张力的第一次显形。如果隔离要产品化，值得考虑"数据面隔离、能力面统一"的方向——这也正是现有 agent / workspace / AppData 三区拆分想表达的意思，只是生产上没按它走
