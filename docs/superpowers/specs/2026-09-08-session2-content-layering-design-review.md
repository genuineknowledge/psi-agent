## 一、本轮实测新发现

每条都给了复现方式。凡未实测的,§六 单独列出。

### F1 · `tools` 与 `get()` 的覆盖方向相反(已在 main)

同一 tools dir 放两个文件、同名工具 `echo`:

```
files 顺序:  ['a_official.py', 'z_personal.py']
tools['echo'].description  ->  PERSONAL DOC      (后加载的胜出)
get('echo')() 返回          ->  OFFICIAL          (先加载的胜出)
```

代码依据:

- `tool_registry.py:434-437` `tools` property 用 `result.update(entry.tools)` 逐文件覆盖 → **后胜**
- `tool_registry.py:441-445` `get()` 遍历 `_files` 命中即返回 → **先胜**

main 上同名工具极少,所以这个分歧一直没露头。**分层把"同名覆盖"变成核心动作**(个人层派生官方工具就是同名),
于是它立刻变成用户可见的错误行为:模型看到个人层的描述和参数 schema,执行的却是官方层那份函数体。
参数不兼容时报参数错误,兼容时静默给出错误结果。

**这修正了红线二的表述。** "分层只进装表期,绝不进 `get(name)`" 这条对 —— 可达性必须保全集。
但它不完整:`get()` 的**遍历顺序**也必须与装表期的覆盖方向一致。否则"看不见 ≠ 调不到"保住了可达性,
却调到了错的那一个。可达 ≠ 调对。

现有用例把这个分歧写成了"允许":

```python
# tests/psi_agent/session/test_tool_registry.py:664
async def test_get_last_file_wins(tmp_path: Path) -> None:
    """get() searches files in insertion order, returns first match."""
    ...
    assert await func() in ("a", "b")  # glob order is filesystem-dependent
```

名字叫 `last_file_wins`、docstring 说 `returns first match`、断言两个都接受。三者互相矛盾,
且断言恒真 —— 典型的绿而不吃劲。这条要重写成方向确定的断言。

### F2 · 缺陷②:去掉 `session_id` 省不掉任何一次编译

统计 `compile()` 实际调用次数(5 个工具文件):

```
session 1 (session_id=AAA) 编译: 5 个文件
session 2 (session_id=BBB) 编译: 5 个文件   <- 不同 session_id
session 3 (session_id=AAA) 编译: 5 个文件   <- 相同 session_id,照样全编
```

第三行是关键:`session_id` 完全相同,`sys.modules` 里那 5 个模块还在,**仍然重编 5 个**。

因为 `module_name` 只是 `sys.modules` 的注册键,复用判定根本不看它 ——
走的是 `tool_registry.py:568` 的 `old_files` 比对,而 `old_files` 是 **ToolRegistry 实例内的
`_files`**。`ToolRegistry.load()` 每次新建实例、`old_files=None`(`:452`),所以必然全量重编。
复用只在同一实例的 `refresh()` 路径上发生。

**所以"拆键就能复用"不成立。** 把 `session_id` 从键里去掉,唯一效果是让两个会话共享
`sys.modules` 槽位 —— 那是隔离风险,不是收益(实测第三次 load 后 `sys.modules` 里
`psi_tool_` 前缀有 10 个,正是两个 session_id 各一套)。

真要拿到跨会话复用,必须**新增一个进程级、以 `(file_hash, layer_id)` 为键的模块缓存**,
在 `_exec_tool_files` 里 compile 之前查。这是新增机制,不是改一行键。

连带影响两处:

- 排期文档的判据"第二个会话的编译文件数显著低于 114",在"只改键"的实现下**永远红**。
  红不是因为实现坏,而是因为改键不产生复用 —— 这种判据会被后来人放宽或删掉。
- 阶段 C 第 3 项工作量被低估:从"拆一个键"变成"加一层进程级缓存 + 定义 layer_id"。
  9-11~9-15 这个窗口要重新估。

实测数字修正:那 114 文件 / 104 万字节的重编,**不是 `session_id` 造成的**,
是 `load()` 不带 `old_files` 造成的。归因写错会导致改完没效果。

### F3 · dotted 私有包完全逃出 stash 隔离(方案未覆盖)

两层各放一个同名 `_pkg/sub.py`,内容不同:

```
layer A tool sees: LAYER-A
layer B tool sees: LAYER-A     <- 应为 LAYER-B
VERDICT: CONTAMINATED
残留在 sys.modules: ['_pkg', '_pkg.sub']
```

根因在过滤条件,`tool_registry.py:105-107`:

```python
for name in list(sys.modules):
    if not name.startswith("_") or "." in name:
        continue
```

`"." in name` **显式跳过所有带点的模块名**。所以 `_pkg` 的子模块 `_pkg.sub` 从不入 stash,
父包 `_pkg` 虽然裸名、但它的 `__file__` 是 `_pkg/__init__.py`,其 `parent` 是 `_pkg/` 目录
而非 tools 目录,`:113` 的 `same_dir` 比对也不成立 —— 两层都漏。

**这正好打在 feishu 上**:`agents/feishu/tools/_feishu/` 是 dotted 包,15 个模块。
`_feishu_impl` 是裸名(进 stash),它 import 的 `_feishu.mentor_ledger` 不是(不进 stash)。
所以候选 A 只给裸名槽位加层 id **不够** —— 官方层与个人层若各带一份 `_feishu/`,
仍然互相覆盖。

阶段 B 的实验若只按方案写的"两层各放一个同名 `_helper.py`",会得到通过的结论,
而生产照样串味。**实验必须包含 dotted 用例。**

> **【2026-09-08 实测更正】** 上面这段把范围说小了。探针实测**裸名 `_helper.py` 也串味**
> (P1 红,两个顺序都红),所以"裸名进 stash 所以裸名没事"这个推断不成立 —— 多层同时打开时
> stash/restore 的前提整体失效。dotted 是**更严重的第二重**缺陷,不是唯一缺陷。
> 因此候选 A 不是"补上 dotted 就够",而是应改用 A1(每层独立 meta path finder)。

### F4 · 元工具当前零分歧,五个文件全部 byte-identical

```
IDENTICAL  _tool_index.py       (6622 bytes)
IDENTICAL  tool_describe.py     (2154 bytes)
IDENTICAL  tool_search.py       (2581 bytes)
IDENTICAL  tool_search_code.py  (3106 bytes)
IDENTICAL  skill_manage.py      (6582 bytes)
```

`git log` 显示两侧都只被 `30e0f28a` 一个 commit 碰过,之后没有任何单侧改动。

那条"上游改动只跟到一侧(desktop 新版 / feishu 旧版)"的教训是真的,但它发生在
`prompt_sections` 那条线上,**不是元工具**。方案把它安到元工具头上,是张冠李戴。

结论:提共享层现在**不是在修分歧,是在防分歧**。判断见 §五。

### F5 · `22710` 的循环导入在 glob 覆盖范围之外

```
agents/feishu/tools/_feishu_impl.py:1030      from _feishu.mentor_ledger import ...
agents/feishu/tools/_feishu/mentor_ledger.py:31   import _feishu_impl as _core
```

两端都带下划线前缀。`tool_registry.py:559` 明确 `if py_file.name.startswith("_"): continue`,
且 `_feishu/` 是子目录,`glob("*.py")` 不递归 —— **这对模块从不被扫描直接加载**。
它们只在公开工具 import 时被间接拉起(实测 39 / 121 个公开工具文件 import `_feishu_impl`)。

所以 `sorted()` 加不加,都不改变这对模块之间谁先谁后。sorted 改变的是**哪个公开工具先被 exec**,
从而间接决定这条 import 链从哪一端起头。

"必须同批"的结论仍然成立(两者都是加载顺序的函数),但**判据搭错了层**:
"改 glob 前后各跑一次 A/B 导入实验"测的是 `22710` 自身,与 sorted 之间没有因果连接 ——
去掉 sorted 它也不会红。正确的判据形状见 §四 判据 10。

### F6 · glob 排序已有判据,但它已绿且与 sorted 无关

`test_load_does_not_depend_on_glob_order`(`:728`)在 main 已存在,实测 5 passed。
而 main 的 `:558` 是裸 `glob("*.py")`,**没有 sorted**。

它能绿是因为真正的修法是 `_tools_dir_on_sys_path` 把 tools 目录整个扫描期挂在 `sys.path` 上
(`:541`),顺序因此变得无关。用例名字说的是"不依赖顺序",测的也确实是这个 —— 用例没问题,
问题在排期文档给它派了错的变异复核:**"去掉 sorted 确认用例真的红"在这条上必然不红**,
因为 sorted 现在不存在,而它已经绿了。

于是"加 sorted"这个动作**目前没有任何能变红的判据保护**。要么给它配一条真正依赖顺序的判据
(同名跨层覆盖的确定性,即判据 5 的加强版),要么承认它只是防御性加固、不单独立判据。
推荐前者 —— 因为 F1 已经证明覆盖方向确实需要确定性。

## 二、阶段 A/B/C/E 逐条质疑

### 阶段 A · 收债 · 判据不完整

现在的判据只有"全量 pytest 落在 57-62 failed 基线内"。**那是回归判据,不是收债完成判据。**
49 个文件一个都不入库,pytest 同样落在基线内。

补两条完成判据:

1. 冻结快照的 49 个文件**逐个有处置结论**(入库 / 丢弃 / 待查),清单可核。
   总数对齐 `MANIFEST.md5` 的 49 行,不允许"漏掉一个"。
2. 判定为入库的,仓库内该文件 md5 与快照一致(**LF 归一化后**比对)。

`_card_dsl.py` 那 603 行漂移单独查,不进第 2 条的自动比对。

顺序上阶段 A 必须早于阶段 G(官方层 `:ro`),这一点排期文档已经写对,且是全局唯一的死结。

### 阶段 B · 序列化点判断正确,但实验范围不够

"这一步的结果决定阶段 C 的走法"这个判断是对的 —— 它是真序列化点,不能与阶段 C 并行。

三处要扩:

- **必须含 dotted 用例**(F3)。只测裸名 `_helper.py` 会假通过。
- **必须构造"两层同时打开"**。现有 `test_two_workspaces_bind_their_own_private_helper`(`:775`)
  是**先后** load 两个 dir(`load(first)` 完再 `load(second)`),靠的正是 scope 进出的 stash/restore。
  分层是两层同时生效 —— 这恰恰是方案说"前提失效"的那件事。现有用例绿,**不代表分层能绿**。
- 判据 7 与 8 是一对矛盾需求(同层各自见自己那份 / 跨层派生要能见官方层),
  方案说"候选 A 才能同时满足"。这个断言本身要在实验里被验证,不能直接当结论。

详细实验设计见 §三。

### 阶段 C · 四件事合并正确,但第 3 项要重新定义

**合并判断:对。** 四件事全落在 `tool_registry.py` 的扫描路径(`:541`-`:627`)上,
且都会动 `_exec_tool_files` 的签名或循环体。分阶段做等于同一处改三遍、每遍重跑同一套判据,
还要处理三次中间态。合并省掉的是重复的回归成本,不是省掉判据。

四件事的耦合关系(比排期文档说的更紧):

```
工具扫描下沉  ── 决定 _exec_tool_files 搬去哪、签名长什么样
glob 排序     ── 改的是同一个循环的迭代源
缓存键        ── 改的是同一个循环体内的 module_name 与复用判定
22710         ── 病灶是这个循环 exec 公开文件的先后
```

三处要改:

- **第 3 项的归因错了**(F2)。"拆键就能复用"不成立,要改成"新增进程级 `(file_hash, layer_id)`
  模块缓存"。工作量上升,窗口要重估。
- **红线三的机制说明要改**(F5)。结论(同批)留着,理由换成"两者都是公开文件 exec 顺序的函数"。
- **要补 F1 的修法**:`get()` 的遍历顺序与装表期覆盖方向对齐。这一项排期文档完全没有,
  但它是分层的正确性前提,不是优化。

红线一(schedules 保持 `workspace_path`)复核过代码,`agent.py:373-377` 确实是四行里唯一
用 `workspace_path` 的,且 `:350-362` 的 docstring 详细写着"一个 schedule 必须恰好被一个
Session 激活,否则提醒会被乘以活跃会话数"。这行有明确设计意图,**保持不动**是对的。

### 阶段 E · 判据在本地量不出来

"请求字符数与 M2 时期(83725)同量级或更低"这条判据**本地无法执行**。83725 是生产实测
(3 小时流量、496 次调用、44 个 distinct),本地没有可比输入,量出的绝对值没有意义。

改成相对形式:同一份固定输入(固定工具全集 + 固定域划分),量 `build_tool_defs` 输出的
字符数,做三档比较:

| 档 | 期望 |
|---|---|
| 全量暴露(无门) | 基准,应接近 285566 的比例 |
| M2 硬编码门 | 约为全量的 29.3%(对齐 83725/285566) |
| 新分层机制 | ≤ M2 档 |

比值可比,绝对值不可比。生产侧的绝对数字留到阶段 G 用档位开关量,那时才有真实流量。

"先删 M2 再上新机制"是本地量数据的顺序、"两者同一次部署"是上线约束 —— 排期文档已经把这
两件事分清了,这个处理是对的。

`get(name)` 仍能调到全部 210 个:这条要独立用例,且按 F1,还要加一条"调到的是**哪一层**那份"。

## 三、阶段 B 隔离实验设计

目标:判定候选 A(槽位键带层标识)在**多层同时生效**下能否同时满足判据 7 与 8,
并测出 dotted 包这条已知漏洞的修法边界。

### 3.1 怎么量

不改主线实现。新建一个独立实验文件 `tests/psi_agent/session/test_layer_isolation_probe.py`,
构造真实的多层 tools 目录,断言每个工具**解析到哪一份私有模块**(用内容标记回读,
不看 `sys.modules` 的内部状态 —— 那是实现细节,会让用例绑死在某个修法上)。

四个用例矩阵,两个维度:模块形状 × 是否跨层引用。

| 用例 | 形状 | 场景 | 期望 |
|---|---|---|---|
| P1 | 裸名 `_helper.py` | 两层各一份同名,内容不同 | 各自见自己那份(判据 7) |
| P2 | dotted `_pkg/sub.py` | 同上 | 各自见自己那份(**F3,现在必失败**) |
| P3 | 裸名 | 个人层工具 import 官方层私有模块 | 能见到(判据 8,派生场景) |
| P4 | dotted | 同上 | 能见到 |

关键约束:**必须两层同时打开**,即一次装表期内两层都在 `sys.path` 作用域中,
而不是 `load(A)` 完再 `load(B)`。这是与现有 `:775` 用例的本质区别,也是整个风险的所在。
实验里用一个最小的双层装载壳来模拟(不动 `ToolRegistry` 本体),壳的唯一职责是
"同时打开两层、逐层 exec"。

同时量一个副作用指标:实验结束后 `sys.modules` 里残留的 `_` 前缀模块数与
`sys.path` 长度必须回到实验前(现有 `test_load_leaves_sys_path_unchanged` 已守 `sys.path`,
私有模块残留还没人守)。

### 3.2 什么结果算通过

先在 main 原样跑一遍,记录基线 —— 预期 **P1/P3 绿、P2/P4 红**(P2 已实测 CONTAMINATED)。
这个基线本身就是交付物:它把 F3 从推断变成用例。

> **【2026-09-08 实测更正】这个预期错了。** 探针跑出来 **P1 也红**(两个顺序都红),
> 不是只有 dotted 那一类逃逸 —— 多层同时打开时 stash/restore 的**前提整体失效**。
> 因此下文"候选 A 只需给槽位加层 id"的判断作废,**兜底方案 A1(每层独立 meta path
> finder)升为首选**,理由是它不依赖"同一时刻只有一个目录作用域打开"这个已被证伪的前提。
> 另外 **P3/P4 的绿不能当好消息**:当前隔离度为零,所以"下层看得见上层"当然通得过;
> 它绿是因为根本没隔离,不是因为派生机制成立。隔离真做上去后 P3 要重新受考验。
> 实测详情见 `2026-09-08-session2-execution-delivery.md` §二。

候选 A 实现后,判通过要**四条全绿 + 三条附加**:

1. P1~P4 全绿。
2. 副作用指标归零(无模块残留、`sys.path` 复原)。
3. 判据 9(模块级单例跨 refresh 存活)不被打破 —— 现有 `:798` 用例仍绿。
   这条是反向约束:隔离做得太狠会把 `_background_process_registry` 的进程表清掉。
4. 变异复核:把层标识从槽位键里去掉,P1、P2 **必须红**;把跨层可见性关掉,P3、P4 **必须红**。
   四条用例分成两组、各由不同的实现开关控制 —— 若某一组去掉开关还全绿,说明它测的不是自己声称的那件事。

第 4 条是这次实验的核心质量关。判据 7 与 8 是矛盾需求,**只有它们分别被不同的变异打红,
才证明两者都吃劲**。若一个变异同时打红两组,说明用例耦合了,得重写。

### 3.3 失败了有什么退路

候选 A 失败的具体形态,按可能性排:

**形态一 · dotted 包无法用槽位键隔离。** 最可能。Python 的包导入走 `sys.modules` 的
父子链(`_pkg` 必须能被 `_pkg.sub` 找到),重命名父包等于要接管 import 机制。

退路 A1:**给每层装一个 meta path finder**,按当前打开的层解析私有模块,不改 `sys.modules` 的键。
比重写 stash 比对干净,代价是引入一个 importlib 层面的组件。

退路 A2:**只让最高层的 dotted 包生效,低层 dotted 包不参与分层**。
即 dotted 私有包按"整包替换"语义(个人层有 `_feishu/` 就整包盖掉官方层),不做逐模块合并。
牺牲的是"个人层只覆盖 `_feishu/` 里一个模块"这种用法 —— 需要确认产品上是否真的需要。
`_feishu/` 15 个模块互相 import,逐模块混合本身就危险,整包替换可能反而是对的语义。

**形态二 · 判据 7 与 8 真的不可兼得。** 若跨层可见(判据 8)必然意味着共享槽位,
那候选 A 不成立。

退路 B1:**派生走显式声明**。个人层工具要用官方层私有模块时,用带层前缀的显式导入
(`from official._helper import x`)而非裸名。派生场景保住了,代价是派生模板要改、
且已有的派生内容需要迁移。这与候选 B 的区别:候选 B 是"看不见",B1 是"换个名字看得见"。

退路 B2:**范围缩小到当前真实需求** —— 只支持官方层 + 个人层两层,企业层暂不放私有模块。
两层的组合比 N 层的一般解简单得多。企业层内容按方案本来也是走 PR 进 git 的,
可以约定"企业层只放 skills/triggers,不放带私有模块的 tools"。

**形态三 · 时间不够。** 若实验拖过 9-11,阶段 C 无法按窗口开工。

退路 C1:**分层暴露(阶段 E)与内容分层(阶段 C)解耦上线**。这两件事排期文档捆在
9-19 同一次部署,但它们的耦合只来自"都要重打镜像"。阶段 E 不依赖多内容根 ——
它按域划分的是**单层内**的工具集合。所以最小可上线切片是:阶段 E + 删 M2 + 档位开关,
内容分层延后。这条退路要提前和会话 1 对齐部署窗口,不能临时决定。

若走 C1,阶段 A 收债**仍然必须做完**,因为它绑的是 `:ro` 挂载,而不是绑代码。

### 变异复核的执行纪律

这个仓库栽过两次,两次都是"变异了但照不出来":

- 一个分支撞四次兜底分支,提前返回吃掉了结论
- docstring 说测 AI 层,实际调的是 Session 层函数

所以每条变异复核记录三件事:**改了哪一行、哪个用例红了、报错信息是不是指向被改的那件事**。
第三件是防兜底分支的:若改的是覆盖方向、红的却是一条 import 错误,说明用例没走到那一层。

一条变异只应打红它对应的判据。若一个变异同时打红多条,先怀疑用例耦合。

## 五、元工具是否提共享层:推荐不提,改为加同步判据

**推荐:不提共享层。** 加一条同步判据,把"两份必须一致"变成会变红的机器检查,
并据此**解除阶段 E 的硬前置**。

三条理由:

1. **当前零分歧**(F4)。五个元工具文件 byte-identical,且只被 `30e0f28a` 一个 commit 碰过。
   提取一个共享层来修一个不存在的分歧,是拿抽象换零收益。那条"上游改动只跟到一侧"的
   实际教训发生在 `prompt_sections`,不在元工具头上。
2. **提共享层必然要改 `agents/desktop/`,而本轮边界明确不碰 ToC 侧。** 共享层只改一侧
   等于制造真正的分歧 —— 正是它要防的那件事。要做就得两侧一起动,那就跨了边界,
   且要和实习生的 ToC 排期对齐。成本远超收益。
3. 方案自己写着"共享层容易退化成一堆 `if product_line ==`,名不副实的抽象比重复更贵"。
   在零分歧的状态下,这个风险是确定的,收益是假设的。

**替代方案(推荐做的):** 加一条测试,断言这五个文件在两个 agent 包里内容一致
(逐文件 md5 / 或直接内容比对)。分歧一出现就红在 CI 上,而不是等到生产少工具。
成本是一个用例,收益覆盖了"提共享层"想要的全部实际保障。

清单固定在这五个:`_tool_index.py`、`tool_describe.py`、`tool_search.py`、
`tool_search_code.py`、`skill_manage.py`。用例里写清"新增元工具要加进这个清单"。

**对阶段 E 的影响:硬前置解除。** 排期文档说"元工具是否提共享层卡在阶段 E 开工前",
理由是"分层暴露若只跟到一侧,ToB 这边模型就找不到工具"。有了同步判据,这个风险由
CI 覆盖,阶段 E 不必等这个决定。**阶段 E 的实际前置只剩:分层暴露的改动必须同时落到两侧**,
而这一点由同步判据保证。

一个留给你的判断点:若你倾向长期把协议契约提共享(方案的建议),那它应该是**独立一件事**、
和 ToC 侧一起排,不要挂在会话 2 上。我不建议在这轮做。
