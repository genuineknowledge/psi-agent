# 方案落地：跟进 + 验收（设计与决策）

| 字段 | 值 |
|------|-----|
| **Feature** | `proposal-followup-and-acceptance` |
| **日期** | 2026-09-05 |
| **状态** | 访谈后默认 **F1**（2026-09-08 CEO）；**2026-09 迭代:** 跟进并入撰写/审查 skill（检查或「可进入深评」通过 → 按 `proposal_id` 同步定时；失败只改稿）；intake/followup 为壳；验收仍 `proposal-acceptance-poc` / `proposal-acceptance-doc` |

先说清楚这篇在讲什么、不讲什么。

前面已经交付的是方案**形成期**：要不要写（一层提醒）、怎么写/查缺（**执行跟进与验收 SOP v2.0** 四期）、评审给什么建议档位。那些解决的是「这篇方案该不该写、写得合不合规」。

**刻意为之(2026-09 迭代):** 权威是 **v2.0 四期**，不是旧 RFC+11。跟进定时不单列；执行性闸门要求实施期里程碑绝对 DDL + 验收门；硬闸门通过或评审「可进入深评」即同步定时，同方案改版顶替 `prop-<id>-*` 组。

这篇补的是：**跟进**和**验收**。方案硬闸门通过之后——

- **跟进**：落地过程中，步骤清不清、到点有没有人推一把（含 DDL 前半天提醒）；
- **验收**：节点上按门类型索要 POC 或交付文档，材料到达后减读/对照建议。

**不算「方案」的：** 周期看板里那种 TODO 审查、缺写考核——那是另一条线，不要混进这篇。  
**海豚不能干的：** 替组织说「验收通过了 / 这个里程碑过了」。它最多给辅助材料，最终过不过还是人说了算（全文统一叫 **非 binding**）。

形成期：`proposal-need-remind` → `proposal-writing-standard`（含通过后定时）→ `proposal-review-standard`（可进入深评亦定时）。

整条链可以记成：

```text
丢进方案 → writing-standard(检查/补救；通过即同步 prop-<id>-*)
  或审查「可进入深评」→ 同步定时
  → 材料到达 → acceptance-poc | acceptance-doc → 人拍板
```

---

## 1. 真正要拍板的只有一件事：跟进做到哪一层

验收这边我们想得比较直：上级读验收材料累、亲手试用累，海豚就帮「减读」和「减试」——这两件事做成什么样比较清楚，**不需要**再搞一套「松验收 / 严验收」的产品哲学二选一。

跟进这边不一样。同样叫「跟进」，松和紧差很远：

- **松**：到点提醒你「这步该动了」，你自己勾一下「我做完了」就行；
- **紧**：到点不只是提醒，还要你**交得出阶段成果**（链接、附件、说明），交完海豚再拿去做一轮验收辅助，看看这阶段对照标准缺什么。

这是组织怎么管执行的选择，不是工程细节。所以标成 **决策点 F**。

**2026-09-08 CEO 访谈映射（已拍板倾向）:** 跟进默认 **F1（提醒 + 勾选 + 人看验收建议）**；拒绝把 Agent 做成监控工具与双重验收；POC/有数据闭环处可另做客观评测，**不**等于全里程碑开 F2。产品默认 `mode=remind`；F2/F3 接口预留。

### 决策 F 三个选项分别是什么意思

**F1 · 提醒层（松）**

海豚把方案里的里程碑拆成步骤，做成飞书上能逐条勾的进度卡，到了约定日期就推一把：「这步到点了，进度怎样？」执行人点勾 = **自己说做完了**。

- 好处：实现快、打扰小，现有 todo 勾选卡那套基本能复用。  
- 坏处：可以空勾、可以瞒报；进度好看但验收时才发现没东西。跟验收能力**解耦**——不会因为你勾了就自动去跑验收。

**F2 · 监督层（紧）**

拆步还是要做，但 DDL 到了语义变了：发的不是「请勾选」，而是**成果求取卡**——你得交链接 / 附件 / 说明，光勾选不算过关。交上来之后，海豚按成果类型去调后面的验收能力（读文档抽要点、或对可测交付做自检），吐一份「本阶段跟进自检」给验收人看。

- 好处：关卡上有证据，跟验收闭环，上级少追问「到底做没做」。  
- 坏处：打扰大，可能敷衍上传；还要事先说清——逾期不交怎么办？只标红、通知上级、还是挡住下一个里程碑？这些选 F2 时要一并定。

**F3 · 组合（建议拿出来讨论的默认倾向）**

日常小步继续走 F1（提醒 + 勾选），**真正的里程碑截止日**升成 F2（求成果 + 跑验收辅助）。日常不烦死人，关卡上又有证据。

拍 F3 时还得口头对齐两句：

1. 哪些节点算「里程碑」（能升级求取的），哪些永远只是子步骤勾选；  
2. 子步骤是否**永远**不发求取卡（推荐：是，避免天天交材料）。

### 选之前工程怎么干

- 验收两条能力可以先做（反正无分叉）。  
- 跟进可以先把 **F1 提醒层**做出来。  
- **F2 监督层**接口预留，默认先别开，等 F 拍板再打开或改默认 `mode`。

请上级回复时尽量写清楚：选 **F1 / F2 / F3**；若选 F3，附带「里程碑怎么划」和「逾期怎么办」的偏好。

## 2. 跟进：设计方案（白话把流程讲清楚）

### 2.1 不管选松还是紧，底下有一块是共用的

方案文档里通常已经有「实施步骤 / 里程碑 / 成功标准」一类章节。跟进不是再发明一套考核表，而是：

1. **读这份方案**，把里程碑拆成「人能勾、系统能催」的步骤；  
2. 每步尽量带上：建议截止日期、谁负责（能从方案或对话里拿到就写上）；  
3. 用飞书交互卡把步骤亮出来，用定时任务到点推送。

几条纪律（和现有 todo 习惯对齐，避免做成花架子）：

- **有分拆价值才拆**，不要为了「卡面好看」硬拆一堆空步骤；  
- 清单挂在**这份方案**上，**不要**并进公司看板 TODO 的「缺写 / 失实」那套周期审计——那是另一套语义；  
- 建议落一个 skill：`proposal-followup`，里面用参数区分模式，例如 `mode: remind | supervise`，默认值跟决策 F 走。

### 2.2 若选 F1：提醒层具体怎么走

```text
读方案里程碑
  → 拆成步骤清单（含建议 DDL）
  → 发多行进度卡（一行一步，可逐条勾）
  → 临近/到达 DDL：推送提醒（文案 + 卡或链接）
  → 用户点勾 = 自报「这步做完了」
  → 台账/卡片状态更新
  → 到真正要验收时：由人另开对话，再叫验收能力（不因勾选自动验收）
```

交互上优先复用已经跑通的 **多行 todo 勾选卡**（`feishu_todo_card_send` / tick / untick）和调度（`schedule_manage`）。  
可选：勾选时软提示「建议附个成果链接」，但**不阻断**——毕竟 F1 的哲学就是相信自报、少打扰。

### 2.3 若选 F2：监督层具体怎么走

```text
读方案里程碑（每步/里程碑必须能指回方案里的某条验收标准原文或编号）
  → 拆步 + 发卡（过程中仍可用勾选表示「我在做」）
  → DDL 到达：发「成果求取卡」
        必填：成果类型 + 链接/附件/说明
        文案明确：这是交阶段成果，不是打勾了事
  → 用户提交
  → 按类型路由到验收能力：
        偏文档/报告 → 主要跑「要点提取」
        偏可运行交付 → 主要跑「试用自检」
        只有空话说明 → 标「证据不足」，不要假装测过
  → 产出「阶段跟进自检」报告（标准覆盖了哪些、缺什么、试用看到什么）
  → 通知验收人；人决定本里程碑过不过
```

和 F1 的关键差别一句话：**DDL 关卡以成果提交为准，勾选不能代替求取。**

逾期未交时，系统至少要能标成「逾期未提交」。要不要升级通知上级、要不要挡住下一步，属于选 F2/F3 时一起定的附带规则，本文不替上级猜。

### 2.4 若选 F3：怎么叠在一起

- 子步骤、日常催办 → 走 F1。  
- 方案里标成里程碑（或评审时约定的关卡）的 DDL → 走 F2。  
- 对执行者的体感：平时像普通进度提醒；大节点才要「交作业」；交完才看到海豚帮验收人扫过一遍的材料。

## 3. 验收：设计方案（路径固定，不是第二个决策点）

验收要解决的痛点很具体：

1. **减读**：验收文档又长又散，对照方案标准通读很费时间；  
2. **减试**：交付做没做、关键路径通不通，验收人往往得亲手点一遍。

所以固定做两个能力，不做成「要不要上验收辅助」的二选一：

### 3.1 要点提取（建议 skill 名 `proposal-acceptance-extract`）

给人用的说法：把验收文档按**本案验收标准**收成一份「字段包摘要」——标准里要看的点，文档里写了啥、没提啥、有没有跟标准打架。

硬纪律（必须写进 skill，不能靠模型自觉）：

- 数字、结论都要能指回原文，**禁止编造**；  
- 摘要不是「验收通过」；文案里要写清这是辅助材料；  
- 标准没覆盖到的内容，老实标「未提及 / 无法从材料判断」，别脑补成符合。

### 3.2 试用 / 自检（建议 skill 名 `proposal-acceptance-trial`）

给人用的说法：先按标准列出一份**说得清的测试计划**，再在允许的范围内跑一截自检（默认偏安全：设计步骤 + 只读检查），把「测了什么、看到什么、哪些没法测」写进报告。

深度可以记成几档，避免一上来就动生产写操作：

| 档 | 含义 | 本期默认 |
|----|------|----------|
| L0 | 只把测试步骤设计清楚 | 要做 |
| L1 | 只读执行（打开、查看、对照） | 要做 |
| L2 | 受限写操作试用 | **后期**，要单独过安全 |
| L3 | 压测 / 长稳 | **后期** |

硬纪律：

- **没有真实观测，不许写「符合 / 通过」**；  
- 环境或权限导致不可测 → **挡回说明原因**，不要假装测过；  
- 同样非 binding。

### 3.3 跟监督层怎么接

选了 F2/F3 时，跟进 DDL 交上来的成果，**直接复用**上面两个 skill，不要再发明第三套「跟进专用验收」。  
差别只在触发方式：人在对话里喊验收，或跟进卡提交后自动/一键调用；报告标题可以标明「由跟进 DDL 触发」。

## 4. 建议落地顺序

1. ~~先做验收 Extract + Trial~~ → **已先落通用** `proposal-acceptance-suggest`（分钟级建议 + L0/L1；深档特化后续）。  
2. ~~再做跟进 F1~~ → **已落** `proposal-followup`（提醒 + 勾选卡 + DDL）。  
3. F2/F3 监督层：访谈后**默认不开**；接口预留。  
4. 触发条件 / 准确度特化（今晚–明日）：形成期三 skill + 跟进/验收的加载闸门与题库 POC。  
5. 挑 **一个真实的中事方案**做试点；没数据之前不要对外喊「省了百分之多少时间」。

## 5. 和决策绑在一起的主要风险

| 风险 | 白话 |
|------|------|
| F 一直不定，或口头说「要监督」实际只上了提醒 | 执行方以为勾了就行，验收人以为系统在卡成果，两边预期拧着 |
| 只上 F1 又不管空勾 | 进度条很满，一验收全是窟窿 |
| F2/F3 求取太密 | 对抗、糊弄上传；报告被当成「已经验收通过」——所以文案和非 binding 纪律不能省 |
| 方案本身里程碑含糊、标准不可观察 | 跟进卡拆出来也没意义；这其实是反推撰写期要把标准写可测 |

---

## 6. 可贴会的三句话

1. **跟进要拍板：** 到点是提醒勾选（F1），还是强制交成果并跑验收辅助（F2），还是日常提醒、里程碑才监督（F3）？  
2. **验收不做二选一：** 固定「要点提取减读 + 试用自检减试」，海豚不替人宣判通过。  
3. **请批：** 决策 F（含 F3 怎么升级、逾期怎么办）+ 用哪个真实方案做试点。
