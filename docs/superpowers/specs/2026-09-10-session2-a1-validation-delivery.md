## 一、A1 需要的 4 处支架

每一处都是量出来的而非设计出来的 —— 都是先写判据、判据红了才发现少了这一层。

### 支架 1 · 裸名别名必须**瞬态**绑定

CPython 解析带点子模块的父包时用的是**裸名**。只把模块改名到 `psi_layer_<id>._helper`，遇到 `from _pkg import sub` 会直接 `KeyError: '_pkg'`。

修法：只在**提问的那个工具文件执行期间**把裸名绑上去，执行完立刻释放。

**为什么不能永久绑**：永久绑定等于把裸名重新变成全局槽位，隔离当场失效 —— 那就回到了 A1 要解决的原问题。`leak_plain_aliases` 开关就是这个变异，它会让隔离类判据转红。

### 支架 2 · `psi_layer_<id>` 自己必须作为包存在于 `sys.modules`

**归因更正**：上一轮认为触发条件是嵌套深度（"只有 `_pkg/sub.py` 这种两段式才需要"）。实测触发条件是**父包是否被当作包解析**，与深度无关。四种形态都触发：

- `from _pkg import sub`
- `__init__` 里 `from .sub import X`
- `__init__` 里 `from . import sibling`
- `sub` 里 `from . import sibling`

仓库实际用量：`^from _[a-z0-9][a-z0-9_]* import` 命中 6 处（feishu，形态 2），`agents/desktop/tools/_fusion_memory/` 13 处（形态 7/8）。

> **这一处上一轮完全没有判据看守。** 我把 `_ensure_scope_package` 短路掉，判据仍然全绿（只有一条次要的映射断言红）。根因是原判据 P2 自己的设计：三个**同层**导入者按 glob 顺序 exec，第一个把 `sub` 绑成父包的属性，后面两个于是再也不会向上解析 —— 判据吃的是属性查找，不是包解析。
>
> 补法是新增 **A1-P6**：每层只放**一个**导入者，杜绝"前一个导入者替后一个把路铺好"。这正是 [[green-test-is-not-load-bearing-test]] 那类问题 —— 一个分支被提前吃掉，判据绿着但不吃劲。

### 支架 3 · 缓存命中的路径也要重绑裸名别名

`_module_cache` 命中时会跳过 exec，如果不在这条路径上也重绑裸名，**同层第二个带点导入者失败而第一个成功** —— 一个只在缓存热了之后才出现的故障。

### 支架 4 · 搜索顺序必须跟**层优先级**，不是**打开顺序**（本轮新增）

打开顺序在生产里就是 glob 顺序，**没有任何一层能控制它**。按打开顺序找，等于让文件系统决定哪一层的私有模块胜出。

**这条只有三层才照得出来。** 两层时"除提问层以外的其余层"是个单元素集合，排序与不排序结果恒等 —— 结构上不可能有反例。所以上一轮的两层探针不是漏测，是**测不出**。

落地时 `Layer` 用显式字段带优先级，而不是靠列表顺序或从 `layer_id` 推断：

```python
layer_id: str
tools_dir: Path
priority: int
```

列表顺序就是打开顺序（本条要消除的东西）；`layer_id` 在生产里是 tools 目录路径，从路径推优先级是另一种猜。两者都是这个字段存在的理由，留任何一个当兜底都是把 bug 挪个地方而不是修掉。

## 二、语义结论：提问层优先胜过优先级优先（实测）

一个自然的想法是"高优先级层的私有模块应该盖住低优先级层的"，与 `tools` 的 last-wins 对齐。**实测这个语义会拆掉 A1。**

`priority_over_asking_layer` 开关让 P1/P2/P3/P6 与 R3/R7 全部转红。其中 R3 用的是**两份真实 `_feishu`** 拷贝，不是构造的玩具用例。

原因：`_` 开头的私有 helper 是某一层的**实现**，不是它对外可寻址的**表面**。官方层的 `feishu_x.py` 去 import `_feishu.mentor_ledger`，它要的是**自己那份**；个人层恰好也有一个 `_feishu/`，不构成"更该用个人层那份"的理由。层的可寻址表面是 `tools` 的公开工具名，last-wins 在**那里**是对的。

所以优先级只用于**跨层兜底时的先后**（提问层没有该模块，才去别层找，此时按优先级降序），不用于**覆盖提问层自己的实现**。

219 条，跑在 `origin/main@86150708` 上。**数字是在新基线上重量的，不是照搬**——比上一轮基线前进 12 个 commit。

### 3.1 真实模块而非构造用例

- **R1（15+15）**：feishu `_feishu/*` 15 个模块 **15/15** 在 hook 下加载，断言作用域名 + 背后文件路径；另 **15 条反向判据**确认 `psi_agent.*` 与第三方**没有**被劫持、且仍在裸名下。反向判据是必要的 —— 只证"该管的管了"不能排除"不该管的也管了"。
- **R3**：真实 `_feishu` 拷两份进两个临时层，用 `_LEDGER_NAME_PREFIX` 作标记，**同时**经工具自己的带点导入和 `_feishu_impl` 的 re-export 两条路读。
- **R6（29）**：desktop 29 个私有 helper，只做加载观测，从磁盘参数化。
- **R2（15+1）**：环路判据写成与 `_KNOWN_CYCLIC` **相等**而非 `xfail`：

  ```python
  assert verdict["ok"] or cyclic, (...)
  assert cyclic == expected_cyclic, ("...若是变好, 说明 A1 顺手修了环路")
  ```

  这样**变好也会红**。"A1 顺手修了环路"和"A1 弄坏了什么"一样是结果，`xfail` 只能抓后者。实测 12 个环路 A1 既没修也没弄坏。

### 3.2 变异复核

8 个开关逐个转红，且**只**红它自己该红的那几条。`EXPECTED_BREAKAGE` 把"开关 → 应该红的判据"写成可执行断言，实现漂移会被抓住而不是静默通过。

**跨卡不遮蔽自查**（我自己做，不采信卡的自述）：

- 去掉 `sorted` → 只红 4 条顺序判据，A1 的 119 条**不动**。（**ext4 上是 6 条**，多出的两条见第八节 —— 同一个变异在两个文件系统上红的条数不同，这本身就是"这条判据是跨文件系统的"的证据。）
- 让 `find_spec` 恒返回 `None` → R7 三个参数里 `via_name` 读到裸 `'_shared'`，而 marker 仍读到 `'enterprise'`。**只比 marker 会有 2/3 假绿** —— 这就是为什么判据要回读模块自己的 `__name__` 而不只比标记值：标记值可能是 `sys.path` 顺序凑对的，`via_name` 才落在 hook 这一层。

### 3.3 加载顺序判据怎么落在正确的层

判据 stub `compile()` 记录**真实 exec 顺序**（compile 对每个真正 exec 的文件恰好调一次，且在文件体之前），并用独立 session id 绕开 `_module_cache` —— 否则缓存命中会跳过 compile，判据量到的是空集还显示通过。

**故意没写"跑两次结果相同"这条判据**：它在单一文件系统上恒绿，不吃劲。

### 3.4 Lint

按**退出码**核，不看输出末尾：`ruff check` / `ruff format --check` / `ty check --python` 均为 0。worktree 里 `ty check` 必须带 `--python`，否则 768 个诊断而基线只有 4 个。

## 八、ext4 上复量（补齐第六节那处缺口）

**结论：ext4 上的偏离比 NTFS 严重一个量级，且这条判据在 ext4 上比在 NTFS 上更吃劲。**
如果只在 Windows 上验，会得出"偏离十几个位置、影响有限"的偏乐观印象。

### 1. 数字（`scripts/check_tool_glob_order.py`，两个平台同一把尺）

| 目录 | 文件数 | NTFS 错位 / 逆序对 | ext4 错位 / 逆序对 |
|---|---|---|---|
| `agents/feishu/tools` | 134 | 16 / 21 | **134 / 4370** |
| `agents/desktop/tools` | 65 | 13 / 19 | **64 / 944** |

ext4（GitHub `ubuntu-latest`，kernel 6.17，`df` 确认 ext4）上 feishu **134 个位置全部错位**，
第一个就偏得很远：`glob` 先给 `organization_memory_add.py`，字母序要 `assignment_accept.py`。
根因是 ext4 的 htree 按**文件名哈希**返回目录项，与字母序基本无关；NTFS 的 B+ 树按名字排序，
只在大小写与 `_`/字母的比较规则上与 Python 的字节序分歧，所以只错十几个。

**两个指标而不是一个**：*错位*数（位置比对）是上一轮 NTFS 报的口径，*逆序对*数才是加载顺序
真正在乎的东西 —— "A 必须在 B 之前"是 `sys.path` 前言文件需要的性质。ext4 上 4370 个逆序对
意味着任意一对文件的相对顺序都可能是反的。

**三种目录形状各量一遍**，因为单量一种会假报 0：git 按索引序（即字母序）写文件，
而 ext4 小目录在某些条件下按创建序返回，于是"刚检出的仓库"这一种形状可能恰好是字母序。
实测三种形状（as-checked-out / 倒序新建 / churn 过）在两个平台上**结果完全一致**，
所以这个担心在本例没有发生 —— 但判据保留三种，因为它为 0 时才需要区分。

### 2. 变异复核在 ext4 上真跑了（不是"应该会红"）

把 `tool_registry.py:614` 的 `sorted(...)` 去掉，推一个临时分支上 CI 实测：

| | NTFS（本地） | ext4（CI） |
|---|---|---|
| 转红条数 | 4 | **6** |

ext4 多红的两条里，一条是本轮新补的 `test_real_filesystem_glob_does_not_decide_exec_order`
（另一条是 `test_duplicate_name_metadata_and_callable_come_from_same_file`）。

**这一条在 NTFS 上不转红、在 ext4 上转红**，正是它存在的理由：原有 3 条顺序判据都 stub 掉
`glob` 来喂一个已知的坏顺序 —— 那是观察排序层的唯一办法，但也意味着它们**不咨询任何真实
文件系统**，在 NTFS / ext4 / APFS 上一样绿。换句话说，上一轮的顺序判据虽然全绿，却**结构上
无法回答"这个文件系统实际返回什么"**。新补的两条让真实文件系统进回路（文件按倒序创建、
不碰 `glob`），其中一条直接复刻 59 文件故障的形状：`a_preamble.py` 装 `sys.path`、
`z_consumer.py` 靠它裸名导入，两个文件按消费者优先创建。

临时变异分支已删除，`git diff --stat` 确认工作树干净、`src/` 无残留。

### 3. 长期看守

CI 新增 `tool-load-order` job（`ubuntu-latest`），每次推送跑两件事：先把 ext4 的偏离数字
打进日志（只报数不判定 —— 偏离为 0 是关于文件系统的事实，不是本仓库的失败），再跑
`test_tool_registry.py` 与 `test_layer_isolation_a1_probe.py` 两个文件，**128 条 / 1.35s**。

**为什么单独一个 job 而不塞进 `lint`**：`lint` 是 `publish` 的门（`needs: lint`），把测试挂进去
会让发版连带依赖测试；且 `lint` 现在五步全是静态检查、语义单一。单独 job 还能并行，红的时候
标题直接说明是加载顺序而不是"lint 挂了"。

**为什么只跑两个文件**：session 子树全量本地 5 分 38 秒，且在 Windows 上有 13 条 asyncio
环境失败。把全量搬上 CI 会把"看住加载顺序"变成"修 CI 全量红"的无底洞。

### 4. 这一节没验到的

- **只覆盖 ext4 与 NTFS 两种**。APFS（macOS，团队有人用）和容器里的 overlayfs（生产实际跑的
  文件系统）都**未量**。生产是 overlayfs 而不是裸 ext4，本节的 ext4 数字不能直接当生产数字用；
  量法已经是脚本，接上 macOS runner 或在生产容器里跑一次即可，本卡没做。
- **判据只看住"排序生效"，看不住"排序是对的顺序"**。真正的依赖关系（哪个前言文件必须在谁
  之前）没有声明式表达，字母序恰好满足现状而已。一旦某个前言文件改名到字母序靠后，判据全绿
  但生产会重演 59 文件故障。这是结构性缺口，不是本卡能补的。
