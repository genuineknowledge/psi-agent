# 新人入职 SOP 定时卡片与 HR 日报

状态：设计待评审
日期：2026-08-05
背景来源：`rookieSOP.txt`（V2，创建人 罗霖）

## 问题

新人入职要走完 `rookieSOP.txt` 里 40 余个勾选项，分布在 Day 1 到 Day 1-7 的多个模块。
现状靠人工催办和纸面清单：新人不知道自己还差什么，HR（罗霖）也没有跨人的进度视图。

要解决两件事：

1. 给新人按 SOP 设定时任务，以**可持续交互**的卡片形式推送——一张卡能逐项勾选，不是点一次就废。
2. 每天给 HR 发一张汇总卡，直观简洁，带一个「查看详情」的飞书表格链接。

## 关键约束（已核实）

- `feishu_message_send_card(multi_use=True)` 把卡片消费粒度从整张卡降到单行（PR #623）。
  勾一行只结那一行，其余行仍可点，卡片原地重绘。这是「持续交互」的机制基础。
- `fire=tool` 定时任务到点直调工具，**不经过 LLM**：内容固定的推送稳定可靠。
- `fire=prompt` 定时任务到点跑完整 agent 回合，LLM 可调工具：**聚合类内容必须走这条**。
- 飞书任务 API 只能列「调用者自己的」任务，无法跨人聚合。所以进度不能只存飞书任务。
- 卡片单卡上限 40 行，超出需拆卡。

## 不采用 `feishu_todo_card_*` 的原因

分层实际是三层，`todo_card` 不是必经之路：

```
_feishu_impl.send_card_impl(..., multi_use=True)   ← 框架能力
  ├─ feishu_message_send_card(..., multi_use)      ← 通用卡片工具
  └─ feishu_todo_card_send()                      ← 待办清单的一个预设模板
```

`feishu_todo_card_send` 把每行硬绑到「飞书任务 + applink 跳转」，回调固定去 `PATCH` 任务完成时间。
而 SOP 项是**验收确认**（「连上 WiFi」验收「能上网」），不需要在飞书任务中心跟踪，详情要链到
SOP 文档而非 applink。因此本设计直接建在 `feishu_message_send_card(multi_use=True)` 上，
自定义卡片结构与 handler，不复用也不修改 `todo_card`（避免与刚合入 main 的文件冲突）。

## 架构

```
入职入口（可替换，见「待核对项」）
   rookie_sop_card_send  ──→ 按模块发 multi_use 卡（Day 1 全部发齐）
                             每行 action = rookie_tick_<item_id>
                                      │
                                      ↓ 勾选回调
                             rookie_sop_tick ──→ 写明细表 + 重算总览行
                                      │          框架自动原地重绘该行
                                      ↓
                    ┌─ 飞书多维表格（一个 base，两张表）──┐
                    │ 明细表：一人多行，唯一事实来源       │
                    │ 总览表：一人一行，从明细重算的投影   │
                    └────────────┬───────────────────────┘
                                 │
        ┌────────────────────────┴────────────────────────┐
        ↓ 9:30 fire=tool                                  ↓ 18:30 fire=prompt
   rookie_sop_remind                              rookie_sop_digest
   读明细算欠项，仅有内容时发催办卡                聚合在途新人 → HR 卡 + 总览表链接
                                                  顺带重算总览做兜底对账
```

新增 4 个工具、1 张表、2 个定时任务、1 个触发器、1 个 skill。

## 数据模型

SOP 清单本身定义在 agent 包 `config/rookie_sop.yaml`（模块、项、验收标准、窗口天数、
适用角色），与现有 `config/handbook_onboarding.yaml` 同一模式——改 SOP 不用改代码。

一个 base 里两张表：**明细表**是唯一事实来源，**总览表**是为 HR 读取而维护的投影。

### 表一：明细表（唯一事实来源，一人多行）

一行 = 一个新人的一个 SOP 项。研发 33 行、非研发 28 行。

| 字段 | 类型 | 说明 |
|---|---|---|
| `记录键` | 文本 | `{open_id}:{item_id}`，幂等去重 |
| `姓名` / `open_id` | 文本 | 来自事件 payload |
| `模块` | 单选 | 环境准备 / 认识人 / 协同体系 / 工作规范 / 核心制度 / 每周节奏 / 开发环境 |
| `项` | 文本 | 如「连上 WiFi」 |
| `验收标准` | 文本 | SOP 原文，如「能上网」 |
| `状态` | 单选 | 未完成 / 已完成 / 不适用 |
| `完成时间` | 日期 | 勾选时写入 |
| `入职日` / `截止日` | 日期 | 截止日 = 入职日 + 模块窗口天数 - 1 |
| `Mentor` | 文本 | 仅供 HR 侧筛选，**不在新人卡片上体现** |
| `适用角色` | 单选 | 全员 / 仅研发 |

明细表建两个视图供人工排查：「按姓名分组」和「逾期项」筛选视图。

### 表二：总览表（HR 详情链接的落点，一人一行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `open_id` | 文本 | 主键，幂等 upsert 用 |
| `姓名` | 文本 | |
| `入职日` / `入职第N天` | 日期 / 数字 | |
| `角色` | 单选 | 待确认 / 研发 / 非研发 |
| `进度` | 文本 | 如 `12/33` |
| `完成率` | 数字 | 百分比，便于排序 |
| `逾期项数` | 数字 | 便于排序，一眼看出谁要盯 |
| `逾期项` | 文本 | 逗号分隔的项名 |
| `状态` | 单选 | 进行中 / 已出新手村 |
| `最后更新` | 日期 | 每次重算时写入 |

**为什么必须双写**：飞书 bitable 的「查找引用」字段（type 19）API 建不出来，
公式列也写不进去，所以无法让表格自己把明细汇总到总览。只能由工具维护。

**一致性规则**：总览行永远**从明细整体重算**，不做增量加减。
`rookie_sop_tick` / `rookie_sop_role_set` 写完明细后，重新读该 `open_id` 的全部明细行、
算出所有字段、按 `open_id` 整行覆盖写入总览。这样即使某次写入失败或漏掉，
下一次勾选就会自动修正，不会累积漂移。18:30 的日报聚合同样重算一遍并顺带修正总览，
构成兜底对账。总览表因此是纯投影：删掉重建也不丢信息。

表格由**机器人身份**创建持有，定时任务用机器人 token 读写，不依赖任何真人授权
（避免离职或 token 过期导致中断）。HR 通过一次性显式授权查看。

## 卡片设计

### 模块卡（Day 1 全部发齐）

几乎所有 SOP 模块的窗口都从 Day 1 开始，只是**截止日**不同（开发环境是 Day 1-7，
第一天就该可见可做）。所以 Day 1 发齐全量，之后每天只做按截止日驱动的催办。

```
【入职路线图 · 环境准备】          Day 1 截止 · 进度 2/5
─────────────────────────────
● ~~连上 WiFi~~                    ✅ 8/5 10:12
● ~~领取校园卡~~                   ✅ 8/5 11:03
□ 找到工位          验收：知道"我的座位在哪"     [标记完成]
□ 开通飞书账号      验收：能登录飞书、看到团队群  [标记完成]
□ 开通 TODO 账号    验收：能打开 TODO 库         [标记完成]
─────────────────────────────
遇到问题先问 Haitun · [查看完整 SOP]
```

每行一个 action `rookie_tick_<item_id>`，统一映射到 handler `rookie_sop_tick`。
`business_context_json` 带 `open_id` / `name` / `module` / `item_id` / 表格 `app_token`，
使回调不依赖会话历史。

### 开发环境卡（唯一带角色判断的卡，两段式）

初始只显示角色选择：

```
【入职路线图 · 开发环境】               Day 1-7 截止
─────────────────────────────
先确认你的角色，我们再决定这部分要不要做：
   [我是研发]      [我不是研发]
```

该模块第一项是 `role_confirmed`（确认角色），**不是** `dev_only`，全员适用、且只能靠点击
其中一个角色按钮才能完成——这样进度分母里永远有一项只能靠回答角色才能拿到，
不答角色卡就没法靠其余项目"凑够"分母而误发毕业卡（曾经的缺口：不答角色 + 27 个通用项
做完会误判 all_done）。

选「我不是研发」→ `role_confirmed` 标已完成，其余 5 个 dev_only 项标 `不适用`：
不计入进度分母、不参与催办、不出现在 HR 汇总欠项里。

```
【入职路线图 · 开发环境】               ✅ 不适用
─────────────────────────────
■ ~~确认角色~~                     ✅ 8/5 10:12
你选择了「非研发」，这部分不需要完成。
```

选「我是研发」→ `role_confirmed` 标已完成，原地展开 5 个勾选项（读 AGENTS.md / 配环境 /
Git 工作流 / Code Review / 仓库权限），此后与其他模块卡行为一致。

两个 action `rookie_role_dev` / `rookie_role_nondev`，handler 为 `rookie_sop_role_set`，
点击任一按钮都会把 `role_confirmed` 一并标完成（一次点击，不设第二个"确认"按钮）。

### 每日催办卡（9:30，`fire=tool`）

读表算欠项，**仅在有内容时发**：

```
【入职提醒】                          入职第 3 天 · 进度 12/33
─────────────────────────────
⚠️ 已逾期 1 项
□ 找到工位            Day 1 截止    [标记完成]

📌 今天到期 2 项
□ TODO 写法规范       Day 2 截止    [标记完成]
□ 闭环要求            Day 2 截止    [标记完成]

下一个到期：核心制度（Day 3，还剩 3 项）
```

- 全部完成、或无逾期无到期 → 静默不发（避免日推麻木，消息量随完成度自然衰减）
- 催办卡同为 `multi_use`，可直接在提醒上勾选，不必回翻主卡
- 全部完成时发一次「出新手村 🎉」终局卡，随后删除该新人的催办定时任务

### HR 日报卡（18:30，`fire=prompt`）

内容需现算聚合，因此必须走 agent 回合：

```
【新人入职进度日报】                        8月5日
─────────────────────────────
在途新人 3 人 · 整体完成率 71%

✅ 张三    33/33   今日出新手村
⚠️ 李四    9/28    逾期 2 项（工位、校园卡）
🕐 王五    3/28    入职第 1 天，正常

需要关注：李四逾期 2 项已超 2 天
─────────────────────────────
        [查看详情表格]
```

- 无在途新人 → 不发（避免空报）
- 有在途新人但一切正常 → 仍发，内容为「全部正常，无需关注」。
  HR 需要能区分「没消息是因为没问题」和「没消息是因为系统挂了」。
- 「查看详情表格」是普通链接按钮（指向 `https://feishu.cn/base/<app_token>`），非交互 action

## 工具清单

| 工具 | 触发方式 | 职责 |
|---|---|---|
| `rookie_sop_card_send` | 入职事件 / 手动 | 按 `rookie_sop.yaml` 建明细行 + 建总览行 + 发全部模块卡 |
| `rookie_sop_tick` | 卡片回调 | 写明细完成状态，再重算该人总览行（框架负责重绘卡片） |
| `rookie_sop_role_set` | 卡片回调 | 记录角色，标 `role_confirmed` 已完成；非研发则把其余 5 个 `dev_only` 项标 `不适用`，重算总览行 |
| `rookie_sop_remind` | 定时 9:30 `fire=tool` | 读明细算欠项，有内容才发催办卡；全完成发终局卡并删定时 |
| `rookie_sop_digest` | 定时 18:30 `fire=prompt` | 聚合在途新人发 HR 卡 + 总览表链接；顺带重算总览兜底 |

「重算该人总览行」是三个写入工具共用的内部函数（读该 `open_id` 全部明细 → 算字段 →
按 `open_id` 整行覆盖），不单独作为工具暴露。

配套 skill `feishu-rookie-onboarding`（何时用、回调怎么处理、零文本结束的约定），
与现有 `feishu-handbook-onboarding` 同构。

## 口径定义（避免实现时歧义）

- **进度分母**：该新人**适用**的项数。开发环境模块的 `role_confirmed` 不是 `dev_only`，
  永远计入分母（Day 1 起，角色未选时也一样）——这是防止新人靠不答角色卡就"凑够"
  分母误报毕业的关键。角色选「非研发」后，其余 5 个 `dev_only` 项从分母中移除
  （所以非研发是 `n/28`，研发是 `n/33`）。**角色未选时分母是 33** —— 5 个 `dev_only` 项
  与角色选择同在一张卡上、Day 1 就可点，所以从落地起就计入分母（种成 `未完成`）；
  「可点却不计分母」会让新人看到的进度对不上。选「非研发人员」后那 5 项才被标
  `不适用`、分母降到 28。`role_confirmed` 始终计入分母。
- **入职第 N 天**：以表格 `入职日` 为第 1 天，按**自然日**计数（不跳过周末，
  因为 SOP 的 Day 1-7 本身也是自然日窗口）。
- **截止日**：`入职日 + 模块窗口天数 - 1`。SOP 的「Day 1-3」表示第 1 到第 3 天，
  故窗口 3 天的截止日是入职日 +2。
- **逾期**：当前日期 > 截止日 且状态为 `未完成`。`不适用` 永不逾期。

## 定时任务的归属与数量

`schedule_manage` 的定时任务写在 **session workspace** 下（`schedules/<name>/TASK.md`），
而飞书给每个 open_id 各自一个 Session。这决定了两条链路的定时任务数量不同：

- **催办（新人侧）**：每个新人**各一份**，名为 `rookie-remind-<open_id 后 8 位>`，
  落在该新人自己的 Session workspace 里。因此 `fire=tool` 的 `tool_args` 里可以写死
  该新人的 `open_id`，到点无需判断「今天该提醒谁」。新人出新手村后删除自己这一份。
- **汇总（HR 侧）**：**全局一份**，落在罗霖的 Session workspace 里，
  名为 `rookie-digest-daily`。`fire=prompt` 到点让 LLM 读全表聚合所有在途新人。

这样划分的好处：催办不需要"一个任务遍历所有新人"的中心化逻辑（那会让单点失败影响所有人），
而汇总天然是跨人的、只需一份。

## 幂等与并发

- **建卡**：`记录键 = {open_id}:{item_id}` + 事件 `idempotency_key`，重复入职事件不会重复建行或重复发卡。
- **勾选**：依赖 #623 的 per-action 墓碑 `{message_id}.{action}.consumed`（`touch(exist_ok=False)`，
  原子）。同一行重复点必然被拒一次，跨进程跨重启有效。写表操作本身也按 `记录键` 幂等。
- **连点**：框架的 `CardActionBatcher` 把在途回合期间的点击合并进下一回合，按
  `(message_id, 点击者)` 分键。收到 `<feishu_card_action_batch>` 时**每条都要处理**，但只回一条消息。
- **不得**用 `feishu_message_edit_card` 改这些卡：它不重新注册回调，编辑后按钮全是死的。

## 待核对项（先按现有实现，核对后再改）

两处都被隔离在**入口层**，后续调整不波及卡片、表格与汇总逻辑：

1. **入职触发方式**：现按 `feishu.hr.user_created`（通讯录新建员工，
   payload 含 `open_id` / `user_id` / `name` / `department_ids` / `employee_type`）。
   若真实流程是 HR 先在表里登记、通讯录后建，则改为表驱动或手动触发——
   建卡入口是独立工具，触发方式可换。
2. **Mentor 来源**：`user_created` payload 里没有 mentor 字段。先留空，
   HR 侧可在表格里手工补。不在新人卡片上体现，因此不阻塞主流程。

## 测试

- `rookie_sop.yaml` 解析：模块窗口天数 → 截止日计算（`入职日 + 窗口 - 1`），含跨月边界。
- 进度分母口径：研发 33 项、非研发 28 项，角色未选时 Day 1 分母是 33（`role_confirmed`
  计入、5 个 `dev_only` 项不计入）；回归验证不答角色卡时即便 27 个通用项全部完成，
  `role_confirmed` 未完成也不能误判 `all_done`。
- 定时任务归属：建卡时为该新人建 `rookie-remind-<后8位>`；出新手村后该份被删除。
- 建卡幂等：同一 `open_id` 重复触发只建一份行、发一套卡。
- 勾选写表：回调 → 明细状态与完成时间；重复回调被拒且不重复写。
- 总览重算：勾选后总览行的 `进度` / `完成率` / `逾期项数` / `逾期项` 与明细一致；
  人为改坏总览行后，下一次勾选能把它算回正确值（验证"重算而非增量"）。
- 角色分支：选非研发后开发环境模块标 `不适用`，且不进催办与汇总分母，总览 `角色` 同步。
- 催办边界：全部完成时静默 + 发终局卡 + 删定时任务；无到期无逾期时静默。
- 汇总聚合：多新人混合状态（正常/逾期/完成/非研发）下的计数与文案正确。
- 批量回调：`<feishu_card_action_batch>` 下每条都被处理。

均为纯函数与 fake client 层面的单测，与现有 `test_tool_discovery.py` 的
assignment 测试同构，不需要真实飞书凭据。

## 明确不做

- 不改动 `feishu_todo_card_*` 与任何刚合入 main 的卡片框架文件。
- 不做 Fusion Memory 双写（明细表已是唯一事实来源）。
- 不做总览表的增量更新（一律从明细重算，避免漂移）。
- 不做 SOP 内容的 Agent 自动问答（`handbook_onboarding` 与 Haitun 主对话已覆盖）。
- 不做签字确认、背调材料收集等 SOP 里的线下环节。
